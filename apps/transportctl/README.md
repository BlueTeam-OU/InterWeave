# transportctl

Offline/local administrative CLI for diagnostics, trust/config administration, identity recovery/verification, and service management. It never becomes a network peer on its own.

**Current status:** Stage 13, active workspace member. The admin commands speak IPC major 3 (ADR-0067 decision 7) to a running daemon over its admin socket, every method below a 3.0 method -- the IPC 2.x each names is the minor it arrived at on major 2 -- and a daemon of a release before Stage 22's, which speaks major 2, answers the hello `VersionIncompatible`: `status [--json]`, `endpoints list [--json]` (each row's id, in the text form the alias the client resolves for it from `config.yaml` and the endpoint overlay -- never sent -- and the daemon's state; the alias is `-` for an entry that carries none and `(unknown)` when `config.yaml` does not load or names no such endpoint, neither in the alias grammar; `--json` is the method's result as the daemon sent it, which `ipc/endpoint-list` describes, with no alias), `endpoints revoke|enable|disable <endpoint>`, `endpoints default <endpoint>|--none`, `trust list [--json]`, `trust allow|revoke <peer>` (IPC 2.1's `admin.trust`, Stage 15; each takes `--endpoint <endpoint>` from IPC 3.0, ADR-0067 decision 6, to read or write that endpoint's own set instead of the operator's list: `trust list --endpoint` prints both directions -- the set the daemon names, `own`, `authored` or `inherited`, then one row per peer and direction with its source -- and with `--json` each direction's `ipc/trust-list` pages, one a line, inbound first, a page without `next` ending a direction; `trust allow|revoke --endpoint` writes both directions of the set, the first write giving an endpoint that has none a copy of what it admitted; there is no `trust seed`, the seed being the human client's call), `peers list [--json]` (IPC 2.2's `admin.peers.list` under `admin.status`: the dial gate's state per allowlisted peer, never an address -- and, for a peer not connected, how long ago a connection to it was last up or that none has been since the daemon started), `peers add|remove <multiaddr-with-peer-id>` and `peers addresses [--json]` (IPC 2.7's `admin.peers` capability, ADR-0062: a bootstrap address added to or removed from the profile's bootstrap-peers overlay, in force without a restart, and every address listed -- `config.yaml`'s as `authored`, which cannot be removed here, then the added ones, each marked when the profile's static-bootstrap provider is disabled; the address is passed as typed, and the daemon's method judges it, its grammar and its special-use floor included, so a refusal exits 1 naming the rule -- `refused special_use`, `refused grammar`, `refused bound`, `refused provider_disabled`, `refused authored` -- and changes nothing), `peers show [--json]` (IPC 2.8's `admin.peers.own_addresses`, ADR-0062 decision 4: this node's own addresses, one per line and nothing else, in the daemon's order -- confirmed external first, the circuit route only when relay-only, then listeners in bind order -- each ending in its `PeerId` and in the classes an add admits, so a line pipes into another node's `peers add`; `--json` adds each row's `kind` and whether rows past 64 were dropped), `shutdown [--grace <ms>]` (no `--grace`: none sent, the daemon's default). `--json` prints the method's result object as the daemon sent it -- for `trust list`, one `ipc/trust-list` page per line. An `<endpoint>` is the derived EndpointId (52 characters, `12D3KooW…`), sent as typed, or an alias, resolved to its id before anything is sent over `config.yaml` read without its keys and the endpoint overlay read without a write back (ENDPOINTS.md section Configured endpoint set, A 2026-11-19 and 2026-11-21): no file under `endpoint-keys/` is read and nothing in the profile is written. An alias no entry carries, or one given against a `config.yaml` that does not load, exits 1 naming the alias, and nothing is sent; a text that is neither grammar is a usage error. When no daemon answers, the profile lock tells "no daemon is running" from "a daemon holds the lock but its socket does not answer".

The endpoint-key commands never touch a socket either, and never write `config.yaml` (ADR-0067 decision 4, ENDPOINTS.md section Configured endpoint set): each prints the entry, and the person, the operator or the deployment's renderer writes it. Neither takes the profile lock, since a running daemon reads an endpoint key only at its load, through the entry naming it. Both print the EndpointId alone on the first line and then the entry's members as `config.yaml` writes them, `key: <EndpointId>.key` and, with an alias, `alias: <alias>`; `--json` prints one object, `{"id", "key", "alias"}` (`alias` `null` when none was given).
- `endpoint init [--alias <alias>]` mints an endpoint key pair from the system's CSPRNG into `<state_dir>/endpoint-keys/<EndpointId>.key`, owner-only in an owner-only directory, at filesystem custody. An alias outside its grammar is a usage error; one an entry of the composed configuration already carries exits 1 and nothing is minted -- when `config.yaml` is there and loads without its keys. Beside one that does not load (a profile whose entries still carry `id`), the mint goes on and stderr says the alias was not checked.
- `endpoint adopt --alias <label>` brings over `<state_dir>/identity-keys/<label>.key`, the key a release before Stage 22's sealed under a label: at filesystem custody alone, its public key checked against its secret, it writes `endpoint-keys/<EndpointId>.key` with the derived id in its header (same custody, same secret), syncs it and its directory, reads it back, and only then removes the old file. Refused by name, with both files left as they were: a Keystore record, a header whose public key is not the secret's, a header naming another label. Run again after an interruption between the two files it checks the new file, replaces nothing, mints nothing and removes the old one. With no old file there is nothing to adopt: it exits 1 and never mints -- naming `endpoint init` for an endpoint that never had a sealed key, or, when `config.yaml` loads and an entry carries the alias, naming that entry's key.

The identity commands never touch a socket (ADR-0033, `IDENTITY-RECOVERY.md`):
- `identity init` mints the profile's key and prints its `PeerId`, one line and nothing else (ADR-0055 decision 4). It takes the profile lock, so it is refused while the daemon runs, and it never replaces a key that exists. With no `config.yaml` yet it writes the profile's default key file, which a configuration naming no `key_file` reads: the fleet mints the key, puts the `PeerId` in its roster, then renders the configuration. A configuration that exists but does not load is refused.
- `identity show` prints the `PeerId` of the existing key, under the lock as `init` is.
- `identity backup [--to-file <new path>]` takes the profile lock, so it is refused while the daemon runs. It emits the recovery record to stdout only when stdout is a terminal, otherwise only to a new file created `0600`.
- `identity verify [--expected-peer-id <peer>]` is the drill. It takes no lock and touches no key, profile or socket.
- `identity restore --new | --replace --replacing <peer>` takes the lock before asking for the phrase. `--new` restores into a profile with no key. `--replace` restores only over the identity it names. The key written is loaded back and its `PeerId` checked before success is reported, and nothing but the key is written. Before it reads the phrase or record, from a terminal, a pipe or a file, either form prints ADR-0043's warning on stderr (IDENTITY-RECOVERY.md section Restore semantics item 11): a phrase restored here while its identity is still running on another node puts one `PeerId` on two nodes, which ADR-0043 forbids, and this host cannot check that. It is a line, not a question and not a refusal; the restore goes on.

The phrase, or a recovery record, is read from stdin only: through `rpassword` with echo off on a terminal, otherwise from the pipe, bounded. Two limits of that crate are handled in `src/phrase.rs`:
- Its Ctrl-C raises `SIGINT` before it restores the terminal, so a handler is registered first.
- Its buffer leaves unzeroed fragments when it grows, a limit stated there. What it returns is held in `Zeroizing`.

Exit codes: 0 done, 1 refused (the reason, or the daemon's error code, printed), 2 a usage error, 3 the daemon unreachable. A recovery phrase is never an argument. `transportctl --version`, alone, prints the workspace version with the commit as build metadata (`0.1.0+<twelve hex digits>`, ADR-0065), stamped by `tools/stamp/commit_stamp.rs`.
