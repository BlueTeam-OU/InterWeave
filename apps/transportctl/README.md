# transportctl

Offline/local administrative CLI for diagnostics, trust/config administration, identity recovery/verification, and service management. It never becomes a network peer on its own.

**Current status:** Stage 13, active workspace member. The admin commands speak to a running daemon over its admin socket: `status [--json]`, `endpoints list [--json]`, `endpoints revoke|enable|disable <endpoint>`, `endpoints default <endpoint>|--none`, `trust list [--json]`, `trust allow|revoke <peer>` (IPC 2.1's `admin.trust`, Stage 15), `peers list [--json]` (IPC 2.2's `admin.peers.list` under `admin.status`: the dial gate's state per allowlisted peer, never an address; a daemon older than 2.2 is told so before any request), `peers add|remove <multiaddr-with-peer-id>` and `peers addresses [--json]` (IPC 2.7's `admin.peers` capability, ADR-0062: a bootstrap address added to or removed from the profile's bootstrap-peers overlay, in force without a restart, and every address listed -- `config.yaml`'s as `authored`, which cannot be removed here, then the added ones, each marked when the profile's static-bootstrap provider is disabled; the address is passed as typed, and the daemon's method judges it, its grammar and its special-use floor included, so a refusal exits 1 naming the rule -- `refused special_use`, `refused grammar`, `refused bound`, `refused provider_disabled`, `refused authored` -- and changes nothing), `peers show [--json]` (IPC 2.8's `admin.peers.own_addresses`, ADR-0062 decision 4: this node's own addresses, one per line and nothing else, in the daemon's order -- confirmed external first, the circuit route only when relay-only, then listeners in bind order -- each ending in its `PeerId` and in the classes an add admits, so a line pipes into another node's `peers add`; `--json` adds each row's `kind` and whether rows past 64 were dropped; a 2.7 daemon is told so before any request reaches it), `shutdown [--grace <ms>]` (no `--grace`: none sent, the daemon's default). `--json` prints the method's result object as the daemon sent it -- for `trust list`, one `ipc/trust-list` page per line. A trust command against a daemon older than 2.1 is refused before any request: the port comes back without `admin.trust`. When no daemon answers, the profile lock tells "no daemon is running" from "a daemon holds the lock but its socket does not answer".

The identity commands never touch a socket (ADR-0033, `IDENTITY-RECOVERY.md`):
- `identity init` mints the profile's key and prints its `PeerId`, one line and nothing else (ADR-0055 decision 4). It takes the profile lock, so it is refused while the daemon runs, and it never replaces a key that exists. With no `config.yaml` yet it writes the profile's default key file, which a configuration naming no `key_file` reads: the fleet mints the key, puts the `PeerId` in its roster, then renders the configuration. A configuration that exists but does not load is refused.
- `identity show` prints the `PeerId` of the existing key, under the lock as `init` is.
- `identity backup [--to-file <new path>]` takes the profile lock, so it is refused while the daemon runs. It emits the recovery record to stdout only when stdout is a terminal, otherwise only to a new file created `0600`.
- `identity verify [--expected-peer-id <peer>]` is the drill. It takes no lock and touches no key, profile or socket.
- `identity restore --new | --replace --replacing <peer>` takes the lock before asking for the phrase. `--new` restores into a profile with no key. `--replace` restores only over the identity it names. The key written is loaded back and its `PeerId` checked before success is reported, and nothing but the key is written. Before it reads the phrase or record, from a terminal, a pipe or a file, either form prints ADR-0043's warning on stderr (IDENTITY-RECOVERY.md section Restore semantics item 11): a phrase restored here while its identity is still running on another node puts one `PeerId` on two nodes, which ADR-0043 forbids, and this host cannot check that. It is a line, not a question and not a refusal; the restore goes on.

The phrase, or a recovery record, is read from stdin only: through `rpassword` with echo off on a terminal, otherwise from the pipe, bounded. Two limits of that crate are handled in `src/phrase.rs`:
- Its Ctrl-C raises `SIGINT` before it restores the terminal, so a handler is registered first.
- Its buffer leaves unzeroed fragments when it grows, a limit stated there. What it returns is held in `Zeroizing`.

Exit codes: 0 done, 1 refused (the reason, or the daemon's error code, printed), 2 a usage error, 3 the daemon unreachable. A recovery phrase is never an argument.
