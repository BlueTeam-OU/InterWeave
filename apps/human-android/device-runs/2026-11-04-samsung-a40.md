## The keys and where they live

`key-info`, 14:22, before any lock change:

| alias | inside secure hardware | user authentication required | invalidated by biometric enrolment | size |
|---|---|---|---|---|
| `interweave.idk1.human-android.human` (the identity's key) | true | false | false | 256 |
| `interweave.iwk1.human-android.background-compatible` (the seed's) | true | false | false | 256 |
| `interweave.store.human-android` (the store key's) | true | false | false | 256 |

So the store key is sealed on the real Keystore, under its own alias
(SPIKE-011's carry), and both it and the identity's key are inside
secure hardware. The phone has no StrongBox (`2026-11-03-samsung-a40.md`),
so that hardware is the TEE. `KeyInfo.getSecurityLevel` exists from API
31 only and was not read here.

None of the three keys is bound to the person's authentication. That is
the code's choice, not the phone's: `keystore.rs`'s one store-side
`KeyCipher`, which seals the store key and the identity's key, passes no
user presence whatever the alias or the profile's policy,
and the seed follows the profile's `key_unlock_policy`, here the default.
Android invalidates on a lock-screen change or a biometric enrolment only
the keys that require authentication, so the expected answer to TM-54's
row is that nothing is invalidated. The runs below show it.

## Before the row: the start refused a configuration (14:22)

The first cold start after the install answered `-3`: "the network
service did not start: ... config.yaml can be changed by another account:
owned by uid 10400, mode 0666: other-writable". The file had been
rewritten at 13:33, during the instrumentation run that held the phone
before this one, and its directory remade at 13:31. The cause is this
lane's: `stand_in::provision_replacing`, which the instrumentation's
`provision` case calls, wrote the file with `fs::write`, whose mode is the
process's umask, and the instrumentation's process left it 0666.
797eef6c writes it owner-only whatever the umask
(`crates/human/android-platform/tests/stand_in.rs`). On the phone the file
was set back to 0600 with `run-as ... chmod`, and the next start ran
with no refusal; its content was not changed. A start that runs answers
`1` here, not the `0` of 2026-11-03: the profile that run provisioned
asks to stay reachable (`jni.rs`: 1 for `StayReachable`). That run's
holder, p2p-network-dev-02, says its Wi-Fi drop case wrote the file and
could not put it back (QUESTION 01a1a740): against the profile before
it, the only changes are availability `stay-reachable` and an added
`runtime.android` block. So the rows below ran under that edit. No key
is bound to the profile's availability, so it changes nothing they show. The identity's
key is opened at the start, and a refusal of it is logged as "the
identity's key is not usable" (`log_key_refused`); no start below logged
one.

## What these runs do not show

- **An invalidated key, and what the app shows for one.** With no key
  bound to authentication there is nothing for a lock change to
  invalidate. The `KeyPermanentlyInvalidatedException` and
  `UnrecoverableKeyException` branches of `KeystoreCipher.kt` (custody's
  `KeyInvalidated`) need a `user-presence` profile, whose seed key is
  bound to authentication, as `device-runs/2026-10-20-gate-b.md` set one
  up. Making one replaces the phone's identity and needs a person through
  onboarding; it was not run. The identity's key and the store key never
  take that branch, by the code above.
- Removing the screen lock altogether (PIN to none). It was not run.
- The StrongBox branch: the phone has none.
- `KeyInfo.getSecurityLevel` (API 31+).
