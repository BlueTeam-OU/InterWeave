# Gate (b) device runs, 2026-10-20

Plan §20 gate (b): "instrumented tests on a real device (API level
recorded) for each line of 'Platform tests'". These lines were not
instrumented cases on the day of the window. architect-cto-01's rule
(INFO 01a15915) applies: run them by hand, read them through logcat
and dumpsys, and record the steps and what was seen here. The
instrumented cases are carried by name to the next branch.

Devices:
- **Samsung A40**: SM-A405FN, Android 11, API 30. Destructive steps
  are allowed on it, at the owner's word.
- **Pixel 9a**: Android 17, API 37. Non-destructive steps only, at the
  owner's word: the app's data stays.

Every adb step went through `.agent-fabric/bin/phone-run`, and its
helper is `line.sh` (in the run's scratch, quoted below). The
person-facing steps were done by the owner's hands. The app's window
is FLAG_SECURE whenever an identity is not ready, so screencap gives
nothing there; the owner read those screens.

## Samsung A40, API 30, build c3a3c8ea (APK sha256 501225b2…)

Setup: a fresh install (InterWeave was not installed). Before the
first launch a user-presence config was written with `run-as` at
`interweave/config/profiles/human-android/config.yaml`: the stand-in
document plus `runtime.android.key_unlock_policy: user-presence`.

### User-presence restart diagnostic (by hand)

| step | how | seen |
|---|---|---|
| first run | the owner created an identity | onboarding sealed behind a BiometricPrompt; the runtime started, "start answered 0" |
| cold launch past 60 s | `am force-stop`, then `am start` 70 s after the last authentication | "Unlock InterWeave" raised before anything bound; no NetworkService |
| grant | fingerprint | "start answered 0"; the runtime started |
| cancel | Back (API 30's prompt with DEVICE_CREDENTIAL has no Cancel button) | Chats reads Offline; on build 04605e70 no notice and no Unlock (the defect fixed in c3a3c8ea) |
| leave during the prompt | Recents | onError 10 (user cancelled), counted as a cancel |
| return after a cancel | Recents, then InterWeave | no prompt; the locked notice with Unlock showed (c3a3c8ea) |
| Unlock | tap, then PIN | the prompt raised, granted; "start answered 0"; Chats reads "Online, limited" |
| process death | Home, `am kill`, then `am start` | no pid after the kill; a COLD launch raised the prompt before the service started |

### Backup and device-transfer exclusion (bmgr)

`bmgr transport <t>`, then `bmgr backupnow` for the app and for a
package that allows backup (the positive control). Afterwards the
transport was put back to the one selected before
(`com.google.android.gms/.backup.BackupTransportService`).

| transport | org.interweave.human | control: com.android.providers.settings |
|---|---|---|
| com.android.localtransport/.LocalTransport | Backup is not allowed | Success |
| com.google.android.gms/.backup.migrate.service.D2dTransport | Backup is not allowed | Success |

On API 30 `dataExtractionRules` is not read, so this measures
`allowBackup="false"`. The API 31+ rules are the Pixel's line below.

### Foreground-service lifecycle (foreground-only profile)

The profile is `foreground-only` (the default). While the window is
open, the NetworkService is bound, not foreground. Leaving the app
ended the session: "stopped: session closed true", and the service
started again on return. The `stay-reachable` foreground service is
the next section.

### Stay-reachable foreground service and process death

The profile was switched to `availability_mode: stay-reachable` with
`run-as` (user-presence kept), then launched and unlocked by the
owner, who pressed Home.

| step | how | seen |
|---|---|---|
| backgrounded | Home | the notification reads "Stay reachable on"; NetworkService `isForeground=true`, channel `reachable`, `startRequested=true` |
| process death | `am crash org.interweave.human` (`am kill` does not end a foreground-service process, and `run-as kill` is refused on this build) | ActivityManager: "Scheduling restart of crashed service … for start-requested"; new process 9539 started for the service |

What the restarted service does under user-presence after the restart
(the `background_restart_requires_user_authentication` diagnostic) was
not read before the phone was handed back.

## Pixel 9a, API 37, build 35c71169 (APK sha256 2faa357a…, androidTest 1d289d62…)

Installed with `install -r` over the owner's build of 2026-10-19; the
data was kept. The profile on this phone is the owner's:
`stay-reachable`, background-compatible.

### Backup and device-transfer exclusion (bmgr)

The phone's transport is Seedvault
(`com.stevesoltys.seedvault.transport.ConfigurableBackupTransport`),
and Backup Manager was disabled. The first run, with it disabled,
refused the control as well, so it measured nothing and is void.
Backup Manager was then enabled for the run under LocalTransport, and
afterwards put back as it was (Seedvault selected, Backup Manager
disabled).

| transport | org.interweave.human | control: com.android.providers.settings |
|---|---|---|
| com.android.localtransport/.LocalTransport | Backup is not allowed | Success |

There is no GMS D2dTransport on this phone, so device transfer under
API 31+ `dataExtractionRules` is not measured here. It stays the
open line.

### Foreground-service lifecycle and process death

| step | how | seen |
|---|---|---|
| open | `am start` | NetworkService `isForeground=true`, `types=0x00000200` (remoteMessaging), notification channel `reachable`, ONGOING_EVENT |
| backgrounded | Home | still foreground; NO_CLEAR added |
| `am kill` | backgrounded | the process stays (a foreground service's) |
| process death | `am crash` | "Scheduling restart of crashed service … for start-requested"; new process 11310, foreground again; the runtime started with no person ("start answered 1") |
