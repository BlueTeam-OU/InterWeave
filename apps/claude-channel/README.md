# claude-channel

The Claude Code Channel bridge's executable (plan §19 step 3): a stdio MCP server, started by its MCP host (the Claude Code plugin in push mode), over the transport daemon's data socket. It is a composition root. `crates/claude/channel-core` holds the rules (notification conversion, reply tokens, the tool surface), and `crates/local/ipc-client` holds the connection. It names nothing under `crates/transport/*` or `crates/discovery/*` and no libp2p crate (`check_claude_layering.sh`), and no CommonMark parser by default (`check_bridge_default_features.sh`).

**Current status:** active workspace member since Stage 16 batch 3. It is the stdio MCP server: the protocol era, the seven tools, the session loop with its reconnect, and the binary (`claude-channel --profile <name> --endpoint <id> --delivery push|pull [--log-level error|warn|info|debug]`). Its own lines go to stderr and to a bounded log file, `<state>/claude-channel/<endpoint>.log` under the profile's state directory, owner-only, rotated to `.log.1` before it passes 1 MiB; the level defaults to `info`, and `status.log` names the file (`src/log.rs`). `--delivery` is required: `push` sends each message as Claude Code's `notifications/claude/channel` and advertises that capability; `pull` advertises neither and adds an eighth tool, `receive(max)`, which takes the messages waiting in one bounded queue (bounded at the session's granted event queue; it drops nothing it took: full, the bridge stops draining its session, the session-bound tools refuse at once with "the pull queue is full: call receive first", a call in flight is cancelled and answered the same, a join or leave so cancelled is kept pending and re-issued once a take lifts the pause, and `status` shows the depth, `paused`, `paused_since` and `pending`). The Claude Code plugin passes `push`. The plugin that starts it is `packaging/claude-plugin/interweave`. Two real daemons and the host run were plan §19 steps 4 and 5, done at Stage 16's close (2026-10-06).

## One event on the host line is at most 320 KiB

`CHANNEL-EVENT.md` §Content (A 2026-10-22): one event, as the host receives it, is at most 320 KiB. The largest legal payload passes that only through JSON escaping — a `;ce=br` `HumanChatV2` payload decoding to 196,608 bytes of control characters is about 1.18 MB escaped once — so a text whose event would pass the bound is carried as the base64url of its bytes with `meta.payload_encoding=base64url`, which for that payload is 262,144 characters. The size is measured before the line is written (`channel-core`'s `host_event_bytes`), with every `meta` key set, and it is the larger of the two modes': the push line whole, or a pulled event as it stands inside `receive`'s tool-result text, where it is escaped a second time (a control character six bytes on the push line, seven pulled). A pull event carries exactly what the push would, so one measure decides for both, and a text a push line alone could have carried may go as base64url in push mode too. The bound is the event's: a `receive` answer carries up to `max` events and its line is theirs together. What a given MCP host accepts on one line remains SPIKE-001's carried measurement. `tests/fake.rs` proves both sides in both modes — the control-character decode as base64url under the bound, a 48 KiB text payload still `utf8` — and `serve.rs`'s `the_measure_is_the_lines_own_length` ties the measure to the lines this server writes.
