# human-cli

`interweave-human`, the command-line human client: ADR-0059 decision 9's "a cli way to do everything", plan section 29 step 4's command half, split out by architect-cto-01's request of 2026-10-22.

It is the desktop client's composition with no display: the same store, facade (`crates/human/app-core`) and model (`crates/human/ui-model`), over the daemon's data socket. A verb is a script of what a person does in the window (view a conversation, type and press Send, press Cancel on a row, confirm a trust change), and the model resolves it into the commands the facade carries out (`src/session.rs`, `src/verbs.rs`). A view never reaches past the facade, and this one is no exception. `identities` and `peers` are the exceptions the model leaves: no model holds an endpoint's administration or the profile's bootstrap addresses, so they call the daemon's admin methods, as `transportctl` does, `identities` narrowed to the profile's human endpoints. `store health` and `store discard` work on the store's files and key alone.

`interweave-human --help` prints every verb and every exit code. `interweave-human --version`, alone, prints the workspace version with the commit it was built from as build metadata, `interweave-human 0.1.0+<twelve hex digits>` (ADR-0065 decision 6); beside any other argument it is a usage error.

## Batches

- **Batch 1 (on main, #368):** `status`, `conversations`, `messages`, `read [--keep]`, `send`, `cancel`, `retry`, `unkeep`, `listen`, `trust list|allow|revoke`, `identities list|enable|disable|default`, `store health`.
- **Batch 2:** `card show|set|share`, `proposals`, `proposals read [--accept|--decline]`, `contacts`, `contacts show|rename|photo|delete`.
- **Store at rest** (ADR-0060): `store health` reports the key and the files, and `store discard` discards and recreates a store that needs recovery.
- **Batch 3:** `peers`, `peers add|remove <address>` and `peers show` (ADR-0062), on the daemon's `admin.peers` methods.
- **Batch 4:** `identity show [<endpoint>]` and `identity new-key [--confirm key-change]` (ADR-0063 decision 6), `proposals read --accept-key-change <id>`, `contacts route delete <contact> <peer>/<endpoint>`, `peers add -|--file <file>`.
- Creating, renaming and removing an identity (ADR-0061's display name and photo per endpoint), and moving a route between contacts, are Stage 22's.

## What a script can rely on

These were ruled with architect-cto-01 on 2026-10-22.

### Exit codes

| code | meaning |
|---|---|
| 0 | done |
| 1 | refused: by this tool, by the store or by the daemon |
| 2 | a usage error (the usage is printed on stderr) |
| 3 | no daemon answered for the profile |
| 4 | another client holds this profile's message store |
| 5 | the message store cannot be used: it needs recovery, is not private to this user, cannot be opened now, or (`store health`) cannot hold new messages now |
| 6 | a message is still on its way when `--wait` ends: it stays pending in the store, and its id is printed |

Why a verb failed is said on stderr, in English for a person. A script reads the exit code, never the wording.

### Output

- `--json` is accepted by every verb that reads (`status`, `conversations`, `messages`, `read`, `listen`, `trust list`, `identities list`, `store health`, `card show`, `proposals`, `proposals read`, `contacts`, `contacts show`, `peers`, `peers show`, `identity show`) and by `send`, `cancel`, `retry`, `unkeep`, `card share`, `store discard` and `identity new-key`. It prints one JSON object per line. Every control character, line separator and bidirectional control in a string is escaped, so a line is always one line.
- `send`, `retry`, `cancel` and `unkeep` print `<id> <status>`, or `{"id": ..., "status": ...}` with `--json`. `send` and `retry` print it also when they fail with exit 1 or 6, so a script holds the id to retry or cancel.
- Every status and state is a fixed token, never a translated label:
  - a message's `status` is one of `sending`, `not-confirmed`, `needs-attention`, `accepted`, `published`, `cancelled`, `unread`, `read`, `kept`;
  - `session` is one of `ready`, `opening`, `reconnecting`, `no-daemon`, `refused`, `storage-degraded`, `closed`;
  - `connectivity` is one of `online-direct`, `online-relay`, `online-partial`, `offline`, `unknown`. `unknown` never means `offline`;
  - `listen`'s `event` is one of `message`, `proposal`, `outbound`, `session`, `connectivity`, `path`, `disconnected`.
- `accepted` means the remote endpoint's bounded queue admitted the message (`AcceptedV2`). It does not mean a person read it.
- Times are Unix milliseconds in JSON (`local_at_ms`, `sent_at_ms`, `last_activity_ms`). `sent_at_ms` is what the sender asserts: shown, never an order.
- A card this identity shared is a message of its own in `messages`, `read` and `listen`, with no text and `"card": {"name", "has_photo"}` the card as it went (`null` on every other message); as text, a `card:` line with its name.
- Text output is for a person and may change. Text from a peer is printed with every control character but newline and tab replaced, and every line separator and bidirectional control, so a message cannot drive the terminal or reorder what it shows. A field printed on a line (a name, an address, a path, an error on stderr) has its newlines and tabs replaced too, so it never splits the line.

### A conversation and a message id

- A conversation is `<peer>` (its default endpoint), `<peer>/<endpoint>`, or `#<channel>`, as `conversations` prints it.
- A message id is `p<row>`, `u<row>` or `k<row>`: the message's row in the store's pending, unread or kept table. It names the same message to the next run while the row stays in that table. Reading or keeping a message moves it to another table and so gives it another id, which the verb prints. No id survives a discard and recreate of the store.

### What a run sees

- **One client at a time.** This client and the desktop client use one store and one endpoint lease (ADR-0041). Whichever starts second is refused, by name, with exit 4.
- **What a one-shot verb sees.** It sees what the store holds plus what arrives while it runs. Messages arrive only while some client holds the lease. `listen` holds it.
- **Reading verbs work without a daemon.** `conversations`, `messages` and `read` show what the store holds, and say on stderr why the session did not open. `status` exits 0 and reports the session as `no-daemon`.
- **Verbs that need the daemon** (`send`, `retry`, `trust`, `identities`, `peers`) fail with exit 3 when none answers.
- **Keep happens at read time.** Keep is `read <conversation> --keep <id>`, in the same run that read the message. A message read and not kept lives only for the run that read it (RETENTION.md), so a Keep of a message read in an earlier run cannot exist. Every `--keep` id must name a message received in that conversation, checked before anything is marked read. Should anything fail after the read, what was read is still printed before the exit code says so.
- **Pending messages are sent by whichever run opens the session.** A `send` that exits 6 leaves its message pending. Any later run that opens the session (`status` included) attempts it again, until it is accepted or cancelled.
- **`--wait <ms>`** (default 5000) bounds how long a verb waits for the session and for an answer.
- **`listen`** prints until SIGINT or SIGTERM, then exits 0, its lease released. What it prints as a `message` stays unread in the store.
- **`send <conversation> -`** reads the message from stdin, without the one trailing newline a shell adds.
- **`identities default --none`** clears the profile's default endpoint only when it is a human one; another client's default is `transportctl`'s to clear. It reads the default, then clears it: two admin calls, so a `transportctl` change between them is not seen. `identities default <endpoint>` makes one of this client's endpoints the default, whichever endpoint held it before.
- **The identity's key.** Every run opens the key of the profile's first human endpoint, or makes it on the first run, by the desktop client's rule. A key file this build refuses is named on stderr and left as it is; the run goes on with no key, and `card show` and `card share` are refused.
- **`identity show`** prints the identity in front (the profile's first human endpoint, whose key every run opens) and its fingerprint, the 16 hex characters ADR-0063 decision 1 defines; `identity show <endpoint>` another human endpoint of the profile, whose key file is read and never made or changed. `--json` prints `{endpoint, fingerprint, key_problem}`. An identity with no key this client can use prints `fingerprint` `null` and `key_problem` (`absent` for another identity with no key file, else the kinds `card show` names: `lost-on-device`, `below-device-protection`, `other-device`, `newer-version`, `damaged`, `exposed`, `key-folder-unsafe`, `not-now`, `missing`) and exits 1. An endpoint that is not one of the profile's human endpoints is refused with exit 1.
- **`identity new-key`** is the window's Make a new key: offered only for the identity in front when its key cannot be used and the kind offers a new key, as the window offers it: every kind but `key-folder-unsafe`, `not-now` included (a run of any verb opens the key again, which is Try again here). A usable key is refused with exit 1, and so is a key folder that is not safe, the refusal naming the folder: the person makes it a folder only this account owns and runs again, and no new key is made. Without `--confirm key-change` it says what a new key would do (the old key file deleted, the identity's cards still on their way cancelled, contacts told of a key change when the card is next shared; `--json`: `{endpoint, key_problem, deletes_old_key, cancels_pending_cards}`), changes nothing, and exits 1. With it the key is made and the new fingerprint printed, with each conversation to share the card in again (`share again <conversation>`; `--json`: `{endpoint, fingerprint, share_again}`); a key not made is exit 1, and says whether the old file was already gone.
- **A card proposal is decided in the run that shows it.** `proposals` lists every proposal held and reads none. `proposals read <conversation>` shows that conversation's proposals, which reads them (RETENTION.md: a card is unread content until shown), and accepts or declines the ones named with `--accept` and `--decline` in the same run. A proposal shown and not decided is gone when the run ends; the sender can share the card again. Every id is checked before anything is read, and what was shown is printed whatever fails after.
- **A proposal's id** is its card's unread row, `u<row>`, as `proposals` prints it.
- **What a proposal says is the sender's claim**, except the `PeerId`, the route and the key's fingerprint. `key.state` is `new`, `same` or `changed`; a `changed` key is shown with the fingerprint the route recorded, and accepting it replaces the key on that route alone. A key change is accepted only with `--accept-key-change <id>` (ADR-0063 decision 4: the client never accepts a changed key on its own): `--accept` naming one is refused with exit 1 before anything is read, the refusal naming the flag, and `--accept-key-change` naming a proposal that is not a key change is refused the same way, so a script that confirmed a key change never accepts something else under it. `accept` says what accepting would do: `creates` a contact, `updates` the named one (a name or photo the person set stays), or `matches` the named one, when the card changes nothing; such a proposal is only declined, and `--accept` naming it is refused with exit 1 before anything is read.
- **`card set <name> [<surname>]`** sets the whole own card. `--photo <file>` reads at most 32 MiB, which the client re-encodes to the card's bound; `--no-photo` removes it; with neither, the photo stays as it is.
- **A contact's name or photo set with `contacts rename` or `contacts photo`** is the person's: no later card replaces it.
- **`contacts delete`** deletes the contact, its routes and their recorded keys. They leave the store's files before it returns, unless another process is reading the store's log at that moment, in which case they leave it at the next write that releases content, or the next open or close. The next card from one of its routes is a new proposal, its key `new`. The trust allowlist is separate and is not changed.
- **`contacts route delete <contact> <peer>/<endpoint>`** deletes one route of a contact and the key it recorded, the contact staying with its other routes, and prints `<peer>/<endpoint> deleted from <contact>`; it leaves the store's files as a deleted contact does. A contact's only route is refused with exit 1, saying `contacts delete` removes the contact, and nothing is written; so is a route the contact does not hold. No command makes a contact with a second route yet (moving a route between contacts is Stage 22's), so today every contact's route is its only one.
- **`listen`** prints a card that arrives as a `proposal` event, and leaves it unread.
- **`peers add <address>`** sends the address as typed, and the daemon judges it against the configuration's grammar and the special-use floor. It prints `added` or `unchanged`. A refusal is exit 1 naming the rule (`grammar`, `special_use`, `bound`, `provider_disabled`, `authored`); the daemon's detail is not shown. An address added is dialled only for a peer this profile trusts: adding one grants no trust. `peers remove` prints `removed` or `unchanged`, and refuses an authored address. `peers --json` lists `{address, source: authored|added, dialled}`.
- **`peers add -`** reads a list of addresses from stdin, **`peers add --file <file>`** from a file: one address per line, each trimmed of spaces and tabs, empty lines dropped, as the window's add page takes typed lines; at most 64 KiB is read. The list is added all or none in one call (`admin.peers.add_addresses`, IPC 2.9; an older daemon is refused with exit 1): it prints `added <address>` or `unchanged <address>` per line, in the order given. An empty list, or one of more than 16 addresses, is refused with exit 1 before anything is sent. The list is read and those rules judged before any socket is opened, so a list they refuse is exit 1 whether or not a daemon runs. A refusal by the daemon is exit 1 naming the address by its number in the list (empty lines not counted) and the rule's token as the daemon names it (`grammar`, `own_peer`, `special_use`, `bound`, `superseded`; `provider_disabled` refuses the list whole), and nothing was added. Like `peers show`'s output, a list from another node's `peers show` pipes in as it is.
- **`peers show`** prints this node's own addresses, one per line and nothing else, in the daemon's order (confirmed external first, then relay circuits when none is confirmed, then listen addresses), so the text pipes into another node's `peers add`. It filters nothing the daemon sends. `--json` prints one object, `{peer, addresses: [{address, kind: confirmed_external|relay_circuit|listen}], truncated}`; `truncated` is `true` when the daemon dropped rows past its bound of 64. A daemon older than IPC 2.8 is refused with exit 1.
- **`store health`** prints `health` (`healthy`, `degraded`, `needs-recovery`, `not-private`, `unavailable`), `protection` (`filesystem-only` on the desktop), `key` (`present`, `absent`, `invalidated`, `unusable`), `files` (`none`, `plaintext`, `encrypted`, `export-unfinished`, `scrub-unfinished`, `rename-unfinished`, `unlisted`), and the pending, unread and kept counts when the store opens (`null` in JSON when it does not). Where the store's directory is refused, its key and files are not looked at: `unknown` in text, `null` in JSON. Anything but `healthy` is exit 5. It never prints a byte of the key.
- **`store discard`** acts only on a store that needs recovery; one that opens is refused with exit 1, and one refused for another class (not private, cannot be opened now) with exit 5. Without `--confirm` it lists what it would remove (`discard`: `everything` or `unfinished-plaintext`, the files, whether the key goes) and what is lost, removes nothing, and exits 1. `--confirm <scope>` must name the scope it lists, or nothing is removed and it exits 1, so a script that confirmed one loss never takes a larger one. `everything` loses every contact and its routes, pending, unread and kept messages, the conversation list, the record of messages already shown, the client's settings and the person's own cards, and the store's key; never an identity, its key, trust or the transport's configuration. `unfinished-plaintext` removes the half-scrubbed plaintext only, and the next open takes the complete encrypted copy. After a discard the store is opened again, which recreates it (`done`, `recreated` in JSON); the ids of the old store name nothing.
- **`trust allow` and `trust revoke`** of a peer already in that state exit 0, printing `(already)`.

## Tests

- `src/verbs_tests.rs` and `src/cards_tests.rs`: each verb through the model and the facade, against the in-memory node pair app-core's own tests use, over a file store where the next run is the claim.
- `src/store.rs`: `store health` and `store discard` over a real profile directory and the desktop's key custody: a discard refused without its scope removes nothing, a confirmed one recreates an empty store under a new key, a store that opens is never discarded.
- `tests/process.rs`: the binary's `--help`, a usage error, batch 4's flags out of place, and a refused profile.
- `tests/version.rs`: `--version` against the root manifest's version and `git rev-parse HEAD`, and `--version` beside another argument as exit 2.
- `tests/desktop-e2e/tests/human_cli.rs`: every verb of batches 1, 2 and 3 run as the binary against two real daemons, and batch 4's: `identity show` and `identity new-key` on a damaged key file, the key change accepted only with `--accept-key-change`, `contacts route delete` refused on a contact's only route (`a_key_change_is_made_and_accepted_only_on_its_flags_across_two_daemons`; the success path of a route delete is the unit tests', over a seeded second route, since no flow makes one), and `peers add -` and `--file` (`a_list_of_addresses_is_added_whole_or_refused_by_its_line`). `card set --photo <file>` is run once with a real image (`a_photo_set_from_a_file_reaches_the_contact_and_the_key_stays_in_its_file`): the photo is prepared, shared, proposed with a photo and accepted as the card's, and across that run the identity key's secret is in no IPC frame or payload the client sent, in no log of either daemon and in nothing the client printed. `contacts photo <file>` is not run with an image anywhere: its file read and bound are tested here (`a_photo_file_past_the_bound_is_refused_unread`), and what the facade does with the bytes is app-core's.

## Release

The Linux release archive carries the binary as `bin/interweave-human`, and `packaging/linux/install.sh` puts it beside `transportctl` in `~/.local/bin` (`uninstall.sh` removes it). It runs as the account the daemon runs under, against the same profile.
