# ui-slint

The human client's reference views (plan §17 (8)): Slint components bound to `ui-model`, shared by the desktop and Android apps when they arrive (Stage 15, Stage 17). A view reads a `UiModel` and nothing else. A person's actions leave it as `ViewEvent`s, so it never calls the facade, the store or IPC. Among `crates/human/*` it is the only crate whose graph names `slint` (P2).

**Current status:** active workspace member since Stage 14 batch 8. It is tested through Slint's testing backend: the accessibility tree, default actions and keyboard focus, with no window system. Since Stage 15 batch 4 the desktop app shows it in a real window.

## The contract

The surface was agreed with the client's role, which owns this crate from Stage 15, before it was built (relay seqs 10823, 10826, 10849, 10867, 10870, 10879, 10882, 10885).

**Graph.** By default the crate takes `slint` 1.18.1 with no windowing backend and no renderer: `std` and `compat-1-2` only. The `desktop` feature adds the window the owner chose on 2026-10-04 (plan §18 (14)):
- winit, with the software renderer and the platform accessibility adapter;
- `unstable-winit-030`, the only public way to read the window's focus.

The desktop app turns `desktop` on. `i-slint-backend-testing` is pinned to the same exact version and used for tests only. The pins are exact because the `i-slint-*` crates make no semver promise. `deny.toml` admits the Royalty-free licence for the Slint crates alone, by the owner's decisions of 2026-10-01 and 2026-10-04. Its attribution is the badge on the download page, not a screen (architect-cto's ruling): the release page's template, `apps/human-android/release/release-page.md.in`, one page for every platform, whose `tests/release_page.rs` holds it.

**Event loop (desktop).** The app cannot name Slint, so the loop's pieces are here:
- `View::handle()` runs the loop;
- `invoke_on_window` hands a turn over from another thread;
- `defer` schedules a turn after the current event;
- `quit_event_loop` ends the loop;
- `View::on_window_focus` reports winit's focus, which drives `set_window_focused`.

**Rendering.** `View::render(&UiModel)` updates the lists by key: a changed row is replaced in place, and rows are inserted and removed where they changed. It never replaces a whole model, because that moves keyboard focus and a screen reader's place back to the start.

**Input.** A Slint callback cannot see the model, so it decides nothing. It queues what the person pressed, by identity: the item and the action as rendered, or the notice that was shown. `View::take_events(&UiModel)` then resolves each press against the model it is given:
- A row button and a committed swipe queue the same input, the item and its `RowAction`. It is emitted only if `intent_for(key, action)` still answers it, so a press or a swipe whose action has gone -- a row accepted under the finger -- yields nothing, never a different action.
- A notice action is emitted only while its notice is still shown.
- A send goes through `send_draft`.
- Selection and window focus go through `conversation_viewed(key, focused)`, so a conversation is read only when it is shown while the window has focus.
- A render that shows a conversation with unread items marks the view "viewed". A message that arrives while the person reads it is therefore read at the end of the next take, if the window then has focus and the conversation is still shown. `render` does not wake the root, which is mid-render: the root takes after it renders.
- A take stops after the first input the root must apply before the next is judged: a draft edit, so a send queued after it reads the edited text; the trust settings opened or closed; an input in them; and a selection that leaves them, which cancels a change still waiting; and Peers opened or closed, or an input on it. The root applies it and takes again. A take also stops before a Back that follows an intent of its own take, so the snackbar that intent may open exists before Back closes it.

The queue's order is the person's order: no queued input is ever moved relative to another, and nothing a person did is held outside it. Coalescing happens only in place. Two flags wait outside the queue, neither a person's act: a render's "viewed" and the conversation pane shown or hidden, both resolved once it has drained, against the window as it is then. A narrow window's Back is queued, and waits for the root to apply an earlier press's intent before it closes the snackbar that was up when the person left.

The queue holds `INPUT_CAP` presses:
- When it is full, the newest press is refused and counted. An edit is never refused: it is the composer's state, and refusing it would lose what the person typed.
- A focus change is state too. It is never refused, and it replaces a queued focus change only when that is the last input. A snackbar's closing and leaving for the list are state too: never refused, they coalesce (one closing per snackbar, one Left until a selection or the trust settings follow it). With all of these, the queue holds at most six times the cap plus nine (`queued_inputs`), provided the root takes until a take returns nothing before it returns to its event loop. A root that stops between takes can let one more edit wait per conversation selected meanwhile: still finite, but not that number.
- A new edit replaces a queued one only while nothing later for that conversation follows it.
- A render never writes the draft over an edit that is still queued.
- `set_wake` lets the root run a take as soon as a window callback queues input. The hook runs with none of the view's state borrowed, so it may take at once. The root's own calls (`select`, `set_window_focused`, `render`) do not run it.

**Swipe** (`design/2026-10-16-message-swipe.md`). Each message row sits in Slint's `SwipeGestureHandler`, the one element that takes a drag away from the controls inside it, and only in the directions `swipe_offer` gives it; a conversation row offers a left swipe only when `conversation_hide_offered`. What a drag means is decided in Rust (`gesture.rs`), not by the handler's own rule: the row tracks once the horizontal movement passes the platform's touch slop and is larger than the vertical one, follows the finger 1:1, arms at 40 % of its width (at least 96) with one haptic tick, and commits on a release while armed or on a fling (released within 100 ms of the first move the row sees, 48 moved from touch-down: Slint delivers a press in a list about 100 ms late, so a speed cannot be measured). A vertical drag stays the list's: once a row tracks, the list stops being interactive for that touch. A touch starting in the platform's gesture insets is the system's. Right to left mirrors the directions. Keep, Unkeep and Retry slide back; Hide and Cancel slide out and are held there until the render that removes the row, then its space closes; a refused Cancel springs back. The row moves by its layout padding, never its `x`, which would take it out of the layout that sizes it, so a long body keeps its height. The model's snackbar shows above the composer (a conversation hide's on the list), times out after `TouchSettings::snackbar_ms`, closes when the conversation is left (Back, another conversation picked, the trust settings opened in its place) or a narrow window's list hides it, and its Undo is a 48 x 48 control. An input that will close it takes it off the screen when it is queued, Undo with it, so no Undo can be pressed that the queue would answer after the close; the model's outcome is announced once and moves focus once its rows are drawn -- after a row was taken away, only if focus was inside that row (read from `focus-id`, which every focusable element reports), so a touch swipe leaves focus where it was; after the header's "Hide conversation" always. With no row left focus goes to the conversation's header title, with no conversation left to the list's heading: both take focus and do nothing. Row buttons are 48 x 48 too.

**Text.** Every string comes from `ui-model`'s English table (`placeholder_en`, `UiText`, `fill`). That copy was read by language-culture (relay message 01a12001-199d-75d9-8e8d-cceb01ea9bbf), and a value added later is a marked placeholder until language-culture finalises it. Templates are filled by name, and identifiers are inserted verbatim.

**Bodies.** A message body is drawn from `chat-protocol`'s block tree, the one parse of the remote bytes, flattened by `body.rs` into lines of plain text: headings, code, quotes, list items with their markers, table rows and rules. Inline marks are drawn as their text alone, and no remote-derived text reaches a second parser such as `StyledText`. A link's label stays in place, and its allowlisted destination becomes a separate control labelled with the full destination, with every control character and every character Unicode makes default-ignorable shown as its code point (`<U+202E>`), so no directional control reorders the label. Right-to-left letters in a destination are laid out by the ordinary bidirectional rules, as in any text. The view raises `OpenLink` only when a person activates that control, and `ui-model` checks the scheme again first. An image is a placeholder naming its alt text, or only that it is an image when the alt text is empty or blank, and is never fetched. Each message offers Show source and back: the source is shown in place of the drawn body, its link controls included, and a body past a bound is its source as plain text with no link controls either.

**Accessibility.**
- Every message item, route, connectivity indicator, composer, send control and notice action has a role and a label.
- An item's label is the short author, then the status, then the body. The full `PeerId` is on the author and in the conversation header, in exact form, and never in every item's label.
- Connectivity, the notice and a refused send are polite live regions, each one element. An item's status is not: the window has one announcement, a polite live region, that says what changed since the last render. That covers a message arriving in the open conversation (who sent it, or how many arrived, never the text), a status change on the person's own messages there, and arrivals in other conversations (by title, or how many conversations). Opening a conversation announces nothing. The announcement uses two slots that take turns, so the same sentence twice is still a change.
- Every control has a default action, and Tab reaches each one.

**Refusal screen** (`refusal.rs`, `RefusalWindow` in `app.slint`). The desktop's start-up refusal screen: a window of its own, separate from the app's, given a `RefusalPage` -- the reason as a `UiText` key, the path, and whether Try again is offered. The root decides which refusal it is and what Try again runs. Focus starts on Try again when it is offered, else on Close; Tab runs through the path, Close and Try again; Escape closes. A Try again not offered is not built, so it is out of the focus chain, the tree and the row, and Close takes its place at the end. The reason and the path scroll above the actions, which stay in view down to the window's 320 x 200 minimum; the window states its height because it sizes itself before its wrapped lines are measured. After a Try again that is refused again the root calls `tried_again`, said in a polite live region of two slots that take turns, so the second time is heard too.

**Platform check.** `platform_check()` tells the app, before any window, whether fontconfig loaded. The toolkit opens it at run time, and a host without it runs with no fonts, silently. It asks the font stack's own loader (`yeslogic-fontconfig-sys`'s dlopen result), so its answer and the fonts cannot disagree.

## What it does not prove

The tests read Slint's own accessibility tree. They do not prove:
- that `platform_check` fails on a host without fontconfig: the loader searches the system's library paths, which a test cannot hide;
- that the platform adapter (in the graph since batch 4) exports the tree as these tests read it: the AT-SPI cases are batch 7's;
- that a live region is announced: the tests read what the regions hold, and whether a screen reader speaks it, and speaks a slot that goes from empty to the same sentence, is the platform adapter's (batch 7's AT-SPI cases, and a person with a screen reader);
- layout under the platform's fonts. The testing backend's layout differs from the winit window's: a link control that kept one line's height in the window was sized correctly there. The body was inspected in the rendered window under Xvfb: lists, quotes, monospaced code, tables, a long unbroken word, a long destination. A test holds only the window width;
- text scaling or reduced motion. The colours are chosen for WCAG AA contrast, and the swipe roles' ratios are computed in `app.slint`, but no tool has measured them on the rendered window;
- a swipe on a device. `tests/swipe.rs` drives the window's swipe callbacks with the positions the row's handler would report; that the handler reports them, that the list does not take the touch first, the platform's slop, insets and haptics, and what a screen reader says are the Android build's, checked on a phone;
- copying a `PeerId` through the clipboard. The open conversation's identifier is a read-only, selectable field whose value the tree holds exactly (tested); the copy itself is the platform's;
- a visible scrollbar: the conversation and message lists scroll by wheel and touch, and the toolkit brings a row that takes keyboard focus into view (tested); that a long conversation list leaves the window's minimum height alone is not tested -- the testing backend keeps the window's size.

The trust settings (`human-client-ui.md` §8) open from their own control below the conversation list, never from a message, and show in place of the conversation: this profile's `PeerId` and every trusted one whole, each removal naming its peer, a field for a `PeerId` to trust, and a change waiting for confirmation with its exact `PeerId` and scope. Focus lands on "do not change", so a Return pressed as the question appears drops it; leaving the settings drops it too; the outcome is announced once, wherever it lands, and shown when the settings next open -- except a trust step's on Peers, which is its block's to say wherever its answer lands, and a read's that lands while Peers is on show, which is Peers' trust line's: neither is announced nor shown there (`TrustSettings::outcome_from`; `a_trust_outcome_is_said_where_its_change_was_made`, `a_pending_trust_retried_without_a_write_says_no_nothing_changed`). The conversation they cover is not on screen -- nor is one behind a narrow window's list, however the list came to be shown: its back control, closing the settings, or a resize across the narrow width, read from the window's `pane-shown` at the moment of reading and never kept beside it -- so nothing in it is read -- an arrival, a focus regained -- and a conversation picked in the list beside them closes them, dropping a waiting change, and is read only once shown (`tests/views.rs`). What a person does there reaches the root as `ViewEvent::Trust`, applied like a draft edit before the next take.

Peers (`design/2026-10-22-add-a-peer.md`; `src/peers.rs`) opens from the app's options after Trust, and from Chats' no-reach notice, which shows on Chats at every width while the model's `no_reach()` holds and has no Close, since it describes a state. It shows in place of the conversation as the trust settings do: the addresses newest added first, each with its peer in short, its host and port in the code font, its state and origin in words, Trust on a row needing it and a menu with Copy address and Remove (or why not, on a configuration row); or, when the list cannot be read, the reason in its place with Try again where a retry can mend it. While the trust list is not the daemon's word, no row shows a trust state and Trust stays on each row the list does not turn off, and the line on what trust means gives way to `PeersTrustUnread` with Try again, which reads trust again, or `PeersTrustNotPermitted` without it. A row's Trust opens the trust step alone: step one's controls are drawn only while `step_one_shown` holds. Add an address opens the add page in Peers' place: a multi-line field in the code font (up to sixteen lines, one add; a seventeenth is refused in its own note), its helper, the scan controls the app offers (`View::offer_scans`: the camera on a phone that has one, Open an image… and Paste an image on the desktop, whose reader -- `src/scan_images.rs`, the platform's file dialog or the clipboard's image, read off the window's thread -- is compiled only with the `desktop` feature; an image with no code, or with a code that is no address list, says so under them, focus back on the control used, `the_image_controls_scan_and_an_image_without_a_code_is_said_under_them`), Add, the note where it is about -- under the field, under the scan controls or under Add; a refused add's under the field's helper in three lines, what was not added, the refused line alone in the code font and wrapped whole, then why, its label still the one sentence (`a_refused_line_is_drawn_alone_between_its_words`), and one of the whole add -- too many lines, the device at its bound, the list off -- in the lead and the reason only, its label the two together, a typed one leaving the caret at the field's end with nothing selected (`a_refusal_of_the_whole_add_names_no_line`) -- then step one's result and one step-two block per peer not yet trusted, with the full PeerId, Copy PeerId, Trust and Not now, and Done with several. While a block's Trust awaits its answer its buttons give way to its waiting line beside a progress mark (still under reduced motion), which takes focus; a block decided by Not now keeps its Trust until the page closes; and a line focus is sent to -- the one under Add, a block's state -- is a focusable note. Focus sent to a row after the person's act on it, which a read showed gone, removed elsewhere, goes to the row after its place, else the one before, else Add an address, and `PeerRowGoneAfterAct` is announced first (`a_row_gone_when_focus_returns_is_said_and_focus_goes_after_it`); a target the app placed, the row after a removed one, is moved on unsaid; a request is judged again while its deferred move is pending, so a read that lands in between moves it too, said once (`a_row_gone_before_its_focus_moves_is_said_and_focus_follows`); and focus that has landed in a row -- on it, its menu or a control in it -- when a later read drops that row goes to the same place with `PeerRowGone` said, however focus got there, unless the person has moved focus elsewhere (`a_focused_row_a_later_read_drops_is_said_and_focus_follows`, `a_row_reached_without_an_act_a_later_read_drops_is_said`, `a_dropped_row_focus_moved_from_is_left_alone`). A row's own Remove or Undo a read decides with no focus asked -- a removal left unknown, read again as its snackbar leaves, focus on its Try again then waiting on the row's menu button -- moves focus only where it is on that row, as the decision says and with nothing said; elsewhere it stays (`a_removal_read_back_without_its_row_moves_focus_from_it_unsaid`, `a_removal_read_back_with_its_row_keeps_focus_on_its_menu`, `a_removal_read_back_leaves_focus_moved_elsewhere`). A move still scheduled whose target a second read drops is sent on from the first row's place, said once (`a_scheduled_move_whose_target_a_read_drops_is_aimed_again`); whether focus left with a snackbar's Try again is read from the action's own last focus change and `focus-id` together, either alone able to be stale (`a_stale_focus_id_alone_sends_no_focus_to_the_row_menu`). An Undo the device refuses by name -- its bound, the list off, this device's own address -- says that refusal in its own words, with no Try again (`an_undo_refused_by_name_is_drawn_in_its_own_words_without_an_action`). A row's menu is open only while its row is drawn: the add page or a trust step covering the list closes it, so one Back closes the page (`a_row_menu_open_under_the_add_page_leaves_back_to_the_page`), and so does a read that drops its row, wherever focus is (`a_row_menu_whose_row_a_read_drops_goes_with_it`). Every press reaches the root as `ViewEvent::Peers`, judged by the model when taken; a field edit coalesces as the trust entry does, and Peers' snackbar times out after `snackbar_ms` like the conversation's. A note a person must read whole -- a refusal naming an address -- wraps and never elides, and no wrapped text there sets the page's width, so a long address fits a 320 px window (`tests/peers.rs`), and a row's short PeerId wraps too, so its Trust and menu stay in the window with large text (`a_peers_row_fits_a_narrow_window_with_large_text`).

Show my address, a tonal button first on Peers -- there in its unreadable state too -- opens Show in Peers' place, its title the button's words (`show_draws_a_code_that_reads_back_as_its_lines`): the warning first, focused; then, once the read answers, the code, at least 240 px a side and unsmoothed, one item labelled with how many lines it holds; the same lines as selectable text in the code font; Copy all addresses; and the PeerId alone with Copy PeerId. No address is said with why and what to do, a failed read with its own line, Try again only where a retry may mend it, focus on that line (`show_says_no_address_and_a_failed_read_apart`); Back or Escape closes it, focus on Show my address.

The address code (`src/code.rs`) is drawn for Show and read for a scan: drawn one pixel a module, dark on white with its four-module quiet zone, for the view to scale unsmoothed; read from greyscale or RGBA pixels, or from a PNG or JPEG file's bytes, which are bounded before anything is decoded (32 MiB, 8192 pixels a side, the decoder's allocation), so a hostile image cannot move what reading it costs. It reads the first code that decodes and judges nothing of its text: the model's rules and then the runtime's do.

The code `slint-build` generates allows `unsafe_code` locally, so this crate has no `forbid(unsafe_code)`. The workspace's `deny` still covers every handwritten line.
