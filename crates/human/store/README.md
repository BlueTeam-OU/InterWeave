# store

SQLite implementation of pending_outbound, unread_inbound, kept_inbound, contacts/preferences; deliberately no general durable history API.

**Current status:** Stage 3, active workspace member. The three ADR-0044 states as its only content: pending outbound, unread inbound, and inbound the receiver explicitly kept. Beside them, content-free metadata that cannot reconstruct a deleted body: `settings`, and since schema v5 `contacts`, `contact_routes` and `conversation_index`, each checked column by column. Since v6 each pending row also carries the transport `MessageId` its first send minted and every retry reuses, so a retry after restart is deduplicated by the receiver. Since v7, `read_pairs` records each message read and not kept by its origin and application id alone: a later copy is refused as `AlreadyRead`, a duplicate, so a message read before a restart is not unread again. At most `READ_PAIR_CAP` (4096) pairs are held, per identity since v14, the oldest of that identity evicted in the transaction that records its newest (STATE.md; architect-cto's Q5 ruling). `unkeep` returns the session copy for a re-keep (Q6) and records a pair too. Since v10 (the start window, STATE.md), `contacts.name_key` and an inbound row's `kind` (`text`, `card`, `other`) are derived, content-free columns, each recomputed at open when its version differs, and seven indexes serve the start's reads: a conversation a page at a time (`conversation_page`), the badge's counts (`unread_counts`), the rows this build cannot show (`hidden_inbound`), the contacts without their photos (`contact_directory_page`), and a card's standing by name. Since v11 the kept rows' kind index carries the conversation's columns too, so the conversations a client shows are read from the two kind indexes alone (STATE.md). Since v14 (ADR-0067's clean break, STATE.md §Migrations) every row carries the local identity it belongs to, `local_endpoint_id`, which leads the inbound and read-pair keys and every count and probe index, so each read, bound and count is one identity's; the open takes the first identity's derived id, which the migration gives every older row, rebinding a route that recorded a key to the id that key derives and discarding what no key names, every pending row and every unread card, counted in eight content-free counts in a settings row written only when a count is not zero, which the client reads with `discarded_at_v14` at each open and deletes with `forget_discarded_at_v14` on the person's acknowledgement and on nothing else; one `{peer, label}` pair under two contacts with two keys fails the migration and leaves the store at v13. `verify_shape` refuses any other table, view, or trigger on every open, so the absence of a general history API is enforced rather than merely intended. A client opens it with `HumanStore::open_profile(&ProfilePaths, .., &first_identity, ..)`: `STORE_FILE` in the profile's human directory, judged by ADR-0028's walk up to the trust boundary the paths carry (`/` on the desktop, the app's data directory in an embedded layout); `open(path, ..)` judges up to `/`.
