# Android protects the portable Ed25519 seed with Android Keystore wrapping

**Status:** Accepted for Android first-party implementation

## Context

ADR-0033 requires exact recovery of the existing 32-byte Ed25519 secret. Android Keystore provides strong non-exportable key storage for supported algorithms, but the libp2p Ed25519 seed still must be supplied to the Rust identity implementation and remain recoverable by the portable mnemonic.

## Decision

Store the transport Ed25519 secret on Android only as a versioned authenticated ciphertext wrapped by an AES-256-GCM key generated in `AndroidKeyStore`. Prefer hardware-backed protection when available. Support explicit `background-compatible` and `user-presence` unlock policies. The `user-presence` wrapping key is a TIMED key (A 2026-10-11, plan §20 step 6): generated with `setUserAuthenticationRequired(true)` and `setUserAuthenticationParameters(USER_PRESENCE_WINDOW_S, AUTH_DEVICE_CREDENTIAL | AUTH_BIOMETRIC_STRONG)` — usable for `USER_PRESENCE_WINDOW_S` = 60 s after the person last authenticated with the device credential or a Class-3 biometric, the value SPIKE-009 exercised (D1 generated it, D4 unwrapped inside it across a process kill and a reboot, D5 was refused at 75 s; no start duration was measured), named once by the Keystore adapter and never a configuration setting (`key_unlock_policy` chooses the mode, not the time). The window exists so that the key operation which follows an authentication completes — the start's unwrap, a provisioning seal, a restore, a reseal — and for nothing else: a Keystore key is the app uid's, so the window grants no other application anything; what it grants is an unattended restart of this app's own service within the window of an unlock, which is inside what the `background_restart_requires_user_authentication` diagnostic already says. Outside the window the Keystore refuses with `UserNotAuthenticatedException`; the Service never prompts — the Activity answers the refusal with a device-credential or Class-3 biometric prompt bound to no operation (any success opens the window) and retries the operation, and a denied or cancelled prompt leaves the person offline. That answer is the prompt itself at a launch of the Activity — its creation: a cold start, a new instance, the creation that follows a process the system killed; not a resumption, and not a recreation the system performs for a configuration change — and on the locked notice's Unlock action; at any other continuation of a live Activity — a return from Home or Recents after a cancel, a recreation the system performs for a configuration change — the refusal is answered by the locked notice and its Unlock action, which raises that prompt, and the continuation binds without a prompt only where the window has opened meanwhile. The custody requirement is that no key operation succeeds outside the window and that an authentication is always offered, never that a person who declined is asked again each time they switch back in. The Activity keeps no clock of the window: the key operation's outcome — the unwrap at a start, the seal at a provisioning or a restore — is its only reading of it, so every case starts with the operation and differs only in how its refusal is answered (A 2026-10-20). The per-operation mode (`t = 0`, a `BiometricPrompt` `CryptoObject` bound to each use; as SPIKE-009 D1 built it, Class 3 only and invalidated by every biometric enrollment) is not used: it needs a prompt the Service cannot show, and it is the "biometric on every network operation" alternative this record already rejects. Never silently substitute a different Android-native identity key algorithm.

**The format and the seam (A 2026-10-10, on SPIKE-009's Result 5 and §20 step 6's build).** The wrapped secret is the **IWK1 v1 envelope**: `IWK1 (4) | version 0x01 (1) | policy (1) | iv (12) | ciphertext (32) | tag (16)`, 66 bytes, with associated data `magic | version | policy | PeerId (UTF-8)` — the header is authenticated and never trusted, checked in SPIKE-009's order before any cipher call, and the PeerId is re-derived from the unwrapped seed and compared. The on-disk record is ONE owner-only file under the embedded identity directory, `identity.iwk1` = envelope (66) `|` PeerId (UTF-8, at most 128 bytes), written with an exclusive create at provisioning, under the profile lock: provisioning and restore each take the profile lock without waiting before anything seals and answer `ProfileLocked` while another holder has it — a lock rather than a reserved file name, because the kernel releases it when its holder dies, where a reservation left by a crash would refuse every later provisioning of a profile that never got its identity — so of two racing first runs exactly one seals and its record opens; provisioning refuses when a record exists, and restore is refused while a host runs the profile. The platform cipher is a **seam** (`SeedCipher`: seal, open, retire; `Send + Sync`, its calls may block) the Android Keystore implements in the app's platform crate; its failure set is CLOSED and is contract — `KeyInvalidated`, `KeyMissing`, `UserNotAuthenticated`, `Authentication`, and `Unavailable(String)` for any other platform error, which is returned to the caller for its log and decides nothing (unlock answers "try again", never recovery) — adding a member is a contract change. Unlock yields the profile identity the embedded launch takes, or one of `Unprovisioned`, `RecoveryRequired(cause)`, `UserNotAuthenticated` (stay offline; a user-presence window that has not been opened is not a loss of the key) and `Unavailable`; only `RecoveryRequired` enters recovery, none mints a key over an established profile, and on `KeyInvalidated` or `KeyMissing` the record stays unchanged byte for byte and the identity returns only through its own recovery phrase. The Keystore key is one per (profile, policy), its alias `interweave.iwk1.<profile>.<policy>` computed by the custody path (`KeyRef::alias`), never by the adapter; `seal` replaces the key at its own alias and no other; the custody path retires the profile's other-policy key only AFTER the new record is written (the seam's `retire`, where no key there counts as success), so a write that fails after the seal — a full disk — leaves the record on disk openable rather than a working profile in recovery; a retire that fails is reported as `OldKeyRemains` (the record is written and opens; a pre-change copy may still open until the key is deleted, and `reseal` retries the deletion, even when the policy already matches), never swallowed. A restore after invalidation never reuses the invalidated KEY (the alias is kept; the key under it is new), a restore under the other policy retires the old record, and a record copied from another profile's directory does not unlock as that profile (#256's review, F1 and R1). Restore decides whose record it is from the PeerId field alone and refuses a link as `Unreadable`; a restore under the policy the record already has first TRIES that record — if it opens to the expected PeerId it is kept, nothing sealed (its bytes rewritten owner-only if they were readable by others); if its key is invalidated, missing or another's, the seal proceeds and loses nothing; if the key cannot be asked (`UserNotAuthenticated`, `Unavailable`) it answers `CustodyRefused::Cipher` and writes nothing — so a restore never seals over the key a healthy record opens under (#256's second re-review; 3f2f5414). The record's policy byte is authenticated and authoritative for OPENING; when it differs from the profile's configured `key_unlock_policy`, unlock does not refuse — the host re-seals under the configured policy after a successful unlock and the old record is retired through the same path (step 7's caller builds it; A 2026-10-10 (ii)). Zeroizing the seed is best-effort and is stated as a limit: the plaintext lives in the Java heap as a byte array for one call. A header bit flip that selects the other valid policy asks for that policy's key and is refused as `KeyMissing` when it is absent and as an authentication failure when present — both refusals, both tested.

## Alternatives considered

Plain app-private seed file; generate unrelated Android Keystore EC identity; store the mnemonic; require biometric on every network operation; cloud custody.

## Consequences

The same PeerId/recovery phrase works across platforms. Android gains materially better at-rest protection, but once unwrapped the Ed25519 secret is present in the app process and is not claimed to be hardware-nonextractable.

## Security implications

Keystore/ciphertext failure is fail-closed. User-presence mode intentionally sacrifices unattended restart; the one exception is a restart within `USER_PRESENCE_WINDOW_S` of the person's last authentication, which the Keystore admits unattended (SPIKE-009 D4 process), and 60 s bounds it (A 2026-10-11). Phrase theft remains full identity compromise. Android phrase screens use secure-window protection, an in-app BIP-39 picker and no clipboard path. Standard-v1 Android system backup/device-transfer excludes identity/recovery/configuration and the entire human-store rather than treating platform backup as recovery. Any future explicit message backup follows ADR-0044 and includes only inbound unread/receiver-kept content.

## Operational implications

Device restore/Keystore invalidation may require mnemonic recovery. Protection level should be visible in local diagnostics without exposing secrets.

## Implementation implications

SPIKE-009 validated (closed PASS 2026-10-09, `SPIKES.md`) Android Keystore AES-GCM wrapping, lifecycle, exact 32-byte seed import and the two invalidation signals, within the bounds its Result records; among what it did not establish (`SPIKES.md`'s "Not established" paragraph lists all) — the recovery screen's exfiltration controls (the per-position picker, `FLAG_SECURE`, the IME-free path, the clipboard refusal), the user-presence/stay-reachable restart diagnostic, the client-side clauses of the stage gate (enters recovery, never mints, restores from the phrase), StrongBox and API 34+ reporting (another device), and the D6b re-run isolating the biometric-enrollment invalidation — are §20 steps 7–8's instrumented tests, carried there by name; backup and device-transfer exclusion was measured by SPIKE-008 (B1, B3) (A 2026-10-10). The custody path's host tests over real files with a software cipher seam are step 6's proof; the Keystore implementation of the seam and its device test land with the app shell. Recovery tooling remains stopped-runtime/offline.

## Revisit conditions

Revisit if Android provides a portable/hardware Ed25519 primitive compatible with exact libp2p PeerId recovery or if a future identity-version ADR intentionally changes the transport key format.
