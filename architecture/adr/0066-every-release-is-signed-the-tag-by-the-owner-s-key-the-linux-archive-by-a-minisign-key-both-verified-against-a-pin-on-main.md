# Every release is signed: the tag by the owner's own key, the Linux archive by a minisign key in the release environment, both verified against a pin on main, and an unverifiable release fails closed

**Status:** Accepted — architect-cto's decision of 2026-10-25 (DECISION 01a17326-c5db, on the first release's review), built by devex-tooling on the owner's go-ahead of the same day; ratified by the arming of the pull request that lands this record with the release run that implements it

## Context

The first release, `v0.1.0`, was published on 2026-10-25 (plan §22). What a person could check about it: the APK's signature under the project's Android key and the certificate fingerprint on the page (ADR-0057), and the SHA-256 of every asset, published beside it. The Linux archive had no signature of its own — its page said so in as many words — so its hash, printed on the same page the archive is downloaded from, was the only check, and a page and an archive replaced together verify each other. The tag was signed, by hand, with the owner's personal OpenPGP key (read from the tag object: an annotated `v0.1.0` carrying an OpenPGP signature under the owner's tagger line) — a key every agent account also signs its commits with, so the signature named the owner's account and not the owner; and nothing in the release run asked for it, so an unsigned tag, or one signed by any key at all, ran the same way.

What makes that gap a decision rather than a chore is who can push a tag. Every agent of this repository pushes and tags as the owner's own GitHub account (`packaging/android/README.md`, "Making the key and the environment, once", step 5), so neither the `release` environment's `v*` rule nor its required reviewer can tell an agent's tag from the owner's, and the run's workflow is the tagged commit's own copy. The one guard between a tag and the Android signing key was the reviewer's approval, taken only after checking by hand that the tagged commit is on `main`. A tag whose signature the run verifies against a key the owner alone holds moves the owner's act out of the shared GitHub identity and into a key no agent's account has ever seen.

Two facts bound the design. The Android key must stay where ADR-0057 put it, in the release environment read by one job that builds nothing, because Android installs an update only over the same key; the same shape — a secret the environment holds, a job that signs and nothing else — serves the archive. And the public keys the run verifies against have to live in the tree, where a change to them is a reviewed pull request; but a file in the tree is also in every tagged commit's copy of the tree, so which copy is read decides what an edited commit can do.

## Decision

1. **The tag is signed by the owner's tag key, by hand.** A release tag `v<version>` (ADR-0065 decision 5) is an annotated tag signed with a dedicated OpenPGP key that signs tags and nothing else, made by the owner in the owner's own account; the key never enters an agent's account, a CI secret, the `release` environment or the repository. It is not the owner's personal key, because that key signs every agent account's commits too and so names the account rather than the owner. The release run verifies the signature before anything builds: the `tag` job of `.github/workflows/release.yml`, beside `tools/ci/release_tag.sh`'s version rule, refuses a lightweight tag, an unsigned tag, a tag whose signature does not verify, and a tag signed by any key but the pinned one. The key each account signs its commits with (`CLAUDE.md` §9) verifies no tag: the pin names one key, the tag key. A lost tag key strands no install: a new key is pinned by a pull request and signs the next tag.
2. **The archive is signed with minisign by a key the release environment holds.** The `sign` job of `.github/workflows/release.yml` — the one job that holds secrets, builds nothing and runs only after every check job has passed — signs the Linux archive and its `.sha256` with the minisign secret key kept as an environment secret beside the Android keystore (ADR-0057; `INTERWEAVE_RELEASE_MINISIGN_KEY` and `INTERWEAVE_RELEASE_MINISIGN_PASS`, `packaging/android/README.md`, "The release keys"), and publishes the two signatures, `interweave-<version>-x86_64-unknown-linux-gnu.tar.gz.minisig` and `.tar.gz.sha256.minisig`, as release assets beside them; the `.sha256` alone catches corruption and authenticates nothing, which is why it is signed too. The public key is on the release page with the command that verifies the archive against it; the page's sentence that the archive has no signature goes. The APK's own signature stays what ADR-0057 decision 1 says: the platform's scheme under the Android key, its certificate fingerprint on the page; minisign signs the archive and nothing else.
3. **The pin is a committed file, `packaging/release-keys.toml`**: `[tag]` holds the owner's key as `fingerprint` (the primary key's 40 hex digits) and `public_key` (the armoured block), `[archive]` holds `minisign_public_key`. Changing a key is a pull request to that file, reviewed as any change to `main` is; the file lands with empty values, so every tag fails closed until the owner's keys are in it. A rotation is a new pull request and, for the archive key, a new environment secret; the pin never carries a key that is not in use.
4. **The pin is read twice, and the reading that guards the secrets is main's.** The `tag` job verifies the tag against the tagged commit's own copy of the pin: a first check, with no secret in reach, in the workflow the tagged commit carries. The `sign` job checks out the tip of `main`, asks `main`'s history whether the tagged commit is on it, verifies the tag again with `main`'s verifier and `main`'s pin, and verifies the archive's minisign signatures with `main`'s public key before any upload — so a tag on an older commit is judged by the keys `main` trusts today, a key `main` has dropped signs nothing more whatever commit is tagged, and a signature the page's key cannot verify is never published. What this does not do: a tagged commit whose workflow was edited runs the edited workflow, which can skip the second reading; the environment's required reviewer, approving only a commit that is on `main`, stays what keeps such a run from the keys (`packaging/android/README.md` step 5). The second reading narrows what an approval has to catch to that one question.
5. **Fail closed.** A tag that cannot be verified, a pin that is empty or malformed, a missing minisign secret, or a signature the pinned public key does not verify, each refuses the run before the step that would publish; the run never publishes a release with a missing or unverifiable signature, and never falls back to publishing the hash alone. A dry run (`workflow_dispatch`) stays what it was: it signs nothing, verifies no tag and publishes nothing.
6. **Provenance attestation is additive.** The `publish` job attests build provenance for the APK and the archive (GitHub's artifact attestation, verifiable with `gh attestation verify`): a statement, signed by the platform, that these bytes came out of this workflow on this commit. It rests on the platform's trust, not on a key the owner holds, so it is a second, independent check beside the signatures and replaces neither; a person who trusts the signatures needs nothing from it.
7. **The first release under this record needs the owner's two keys in place first**: the tag key the owner already signs with, and a minisign key pair the owner makes, its secret key as an environment secret and its public key in the pin through a pull request. Until both are on `main`, every tag fails at the first reading, by decision 3; `packaging/android/README.md`'s "The release keys" carries the once-only steps for both (devex-tooling's text).

## Alternatives considered

Keep the hash as the archive's only check: the hash is printed on the page the archive is downloaded from, so it detects a corrupted download and nothing a party who can replace both would do; refused. Sign the archive with the owner's OpenPGP key, by hand, like the tag: the archive exists only at the end of a run on a hosted runner, so a hand signature would mean downloading, signing and re-uploading an asset the run already published, a window in which the page names an unsigned file; refused in favour of a key the sign job holds, which is the APK's shape already. Sign the archive with the Android key: Android's scheme signs APKs, and a JAR-style signature over a tarball is no format any Linux tool verifies; refused. Sign with sigstore keyless (an identity certificate from the run's OIDC token): it is what the attestation of decision 6 already gives, resting on the platform's trust; taken as the additive check, not as the signature. Read the pin from the tagged commit alone: an edited commit then names its own key and the reviewer's approval is the whole guard again; refused, decision 4 reads `main`. Read the pin from `main` alone, in the tag job: that job runs before any secret is in reach, so the cheaper first reading costs nothing and refuses an unsigned tag before the build spends an hour; both readings kept. Store the public keys as environment secrets instead of a file: a change would then be invisible to review and to history; refused. Verify the tag by GitHub's "verified" badge: it names the account's keys, which every agent shares; refused, the pin names one fingerprint.

## Consequences

A release is three signatures and a hash list: the owner's over the tag, the project's over the APK, the project's minisign over the archive, with the SHA-256 of every asset; a person verifies the archive with one command against a key printed on the page, and a deployment (ADR-0055) can pin that key once and verify every later archive it fetches. Tagging is the owner's act in the strongest sense this repository has: an agent, which cannot sign as the owner, can push a tag and the run refuses it. A key rotation is a reviewed pull request and, for the archive key, an environment change, both visible. The cost: one more secret in the environment, one more file whose empty state blocks every release, one more step in the owner's once-only procedure, and a second verifier run per release; and a release on a commit whose workflow was edited still runs that workflow, which decision 4 names rather than pretends away.

## Security implications

What an attacker who can push to the repository as the shared account cannot do: produce a tag signature or an archive signature that verifies against the tree's pinned keys, or an APK signature under the certificate whose fingerprint the owner recorded in the environment and the page prints (ADR-0057), since none of the three keys is in that account's reach. What that account can still do: push a tag the run refuses unsigned; and publish an unvouched release — a tag on a branch commit whose edited workflow drops the checks and the `sign` job, since the `publish` job holds a write token under no environment and no reviewer, or a release created through the API with no workflow at all — whose assets no pinned key vouches for. The defence against that release is verification of its assets, not non-publication: the archive's `.minisig` against the key a deployment or a person took from the tree, the APK's certificate against the recorded fingerprint; a signed tag alone tells nothing apart, since such a release can be created or have its assets replaced on a tag the owner did sign. What one who can replace a published asset gains: a file whose signature the pinned key does not verify, which the page's verify command refuses; replacing the page too, with a key of the attacker's printed on it, passes a person who takes the key from the page and fails a deployment or a person who took it from the tree, which is why decision 3 keeps the key there and Operational implications says to pin it from the tree. What one who holds the `release` environment's secrets gains: a signed archive and a signed APK for any run the reviewer approves — the same as before this record, and the reason the reviewer's approval of decision 4 stays a guard rather than a formality. What one who holds the owner's OpenPGP key gains: a tag the run accepts, on any commit on `main`; the key's custody is the owner's, outside this repository, and its loss or compromise is a rotation through decision 3. The residual accepted: the workflow of a tagged commit is that commit's own, so the second reading of decision 4 is skippable by an edited commit that the reviewer approves; the attestation of decision 6 makes such a run's provenance visible after the fact, not impossible. Minisign is a maintained, single-purpose Ed25519 signature format with no key-server, web-of-trust or expiry machinery; what it verifies is that these bytes were signed by this key, which is the whole claim the page makes.

## Operational implications

The owner, once: make the tag key and the minisign key pair, put the minisign secret key and its password in the `release` environment and both public halves in `packaging/release-keys.toml` through a pull request (a public half is not secret, so an agent may commit it); keep both secret keys backed up off the agents' accounts, since a lost one means a rotation and a page that names a new key, and a tag key given an expiry is re-pinned when it is extended or every tag after the date is refused. Every release: sign the tag, as today; at the reviewer's approval, check the commit is on `main`, as today. What a failed run says: the `tag` job names a refused signature or an empty pin before any build; the `sign` job names the reading that failed — the tag against `main`'s pin, or the archive against `main`'s key — and publishes nothing. A person: the page carries the public key and the verify command; the `.minisig` sits beside the archive; `sha256sum` stays the check for a corrupted download. A deployment pins the public key from the tree, not from the page.

## Implementation implications

The release run is devex-tooling's: `packaging/release-keys.toml` and the verifier that reads it, the `tag` job's first reading, the `sign` job's checkout of `main`'s tip with the second reading of the tag and the archive's signature, the `.minisig` asset, the attestation step in `publish`, the once-only procedure's new steps in `packaging/android/README.md`, and the self-tests beside each script (`tools/ci/`, `CLAUDE.md` §1); the Linux archive's minimum platform rode the same pull request (#446): the floor ruled on 2026-10-25, the build image the `linux` job builds in, and `tools/ci/check_glibc_floor.py` (p2p-network-dev-01's), which `release_linux_archive.sh --glibc-floor` holds every staged program to; its rule is ADR-0065's second 2026-10-25 amendment. Prose that said the archive is unsigned went with that pull request: `packaging/linux/README.md`'s sentence, rewritten by devex-tooling's commit on the same branch with the verify commands, and the release page's "The Linux archive has no signature, so this value is the only check" with the verify command that replaces it (`apps/human-android/release/release-page.md.in`, rust-ui-dev's template, language-culture-en's English, held by `tests/release_page.rs`); `apps/human-android/RELEASE.md`'s "Signing" is confirmed by this record and its Linux paragraph says the archive is signed (this record's commit). ADR-0057's security implications name this record for what the release's integrity rests on. The first release under it is a PATCH (ADR-0065): `v0.1.1`, which also states the archive's minimum platform; plan §22's record names it when it runs.

## Revisit conditions

The platform offering a tag signature check of its own that names one key rather than an account's; a store returning for Android (ADR-0057's revisit), which brings its own signing; a second signer — a release made by someone other than the owner — which needs a key list in the pin rather than one fingerprint; a Windows or macOS artifact (plan §22's carry), whose platform signing is its own decision; minisign ceasing to be maintained, when the archive's format moves to another single-purpose Ed25519 signature under the same pin shape.
