# A user identity is an EndpointId of the node with its own card: a person holds several under one PeerId, and every conversation speaks as exactly one

**Status:** Accepted — the owner's direction of 2026-10-21 ("a user should have multiple network identities"), clarified the same day on the record's first draft: "An EndpointId should match a user identity. One user of the app can have many user identities on the same phone. So for any EndpointId he can add a display_name and a photo", and the shape below — one PeerId per node, the identities its endpoints, the profile per identity kept as the heavier separation for the case that needs it — agreed in the owner's words ("I agree, write in that way"), with the rule added the same hour: "two endpointid are two identities even if they belong to one user. Avoid any ux that can let the user think that is operating with one while operating instead with the other"

## Context

Two identifiers exist and the records keep them apart. The **PeerId** is the node's cryptographic identity: one per profile (ADR-0016), one per concurrently active device (ADR-0043), the hash of the key the 24-word phrase restores (ADR-0033); it is what a connection authenticates, what a broadcast is signed with, what trust is granted to and what routing finds. The **EndpointId** is a configured routing selector under it (ADR-0030, `ENDPOINTS.md`): at most 64 per profile (`MAX_ENDPOINTS`, the schema's bound), registered only by configuration, each held by at most one direct-capable local session through an exclusive lease, never a second PeerId, never an authorization principal; on the wire a remote `source_endpoint` is peer-asserted metadata beside the authenticated `source_peer`. The human clients enable one endpoint, `human` (`human-client-ui.md` §2 step 4), and ADR-0059 let a person keep several cards of their own under that one PeerId as presentation.

The owner's direction is that a person holds several identities and chooses which one speaks. The first draft of this record read "identity" as a whole profile — its own key, PeerId, phrase, daemon and store — and the owner corrected it: the user identity is the EndpointId, each with its display name and photo, many on one phone. What follows is that model, with what it does not give stated beside it.

## Decision

1. **A user identity is a configured EndpointId of the profile together with the card the person gives it**: a display name — a name and an optional surname — and an optional photo, the card of ADR-0059. The node stays one: one PeerId and key, one recovery phrase, one trust set, one human store, one custody, one daemon or embedded runtime, one set of listeners and relay reservations, shared by every identity it holds. On the wire nothing changes: the EndpointId remains a routing selector that grants no trust and is authenticated only by the PeerId it sits under (ADR-0030 A 2026-10-21, ADR-0032); the counterparty learns which identity spoke from the `source_endpoint` the direct protocol already carries. ADR-0059's own cards become **one card per identity**, the identity's presentation (ADR-0059 A 2026-10-21 (ii)) — and what makes an endpoint an identity to the client is not the card but the endpoint's standing: the profile's **first identity** is its authored human endpoint (`human-client-ui.md` §2 step 4; `runtime.android.endpoint` on the phone), and every other identity is an endpoint in the overlay's `added` member, which only the human client's create writes (ADR-0028 A 2026-10-21). Any other configured endpoint — an agent's (ADR-0055), one authored for another use — is a route the client lists among no identities and offers to no one, whatever its label. The card row is the identity's presentation: created with the identity, and recreated at the next open with the route label as its name when the store was discarded (ADR-0060 decision 6), so a client always holds its first identity and every added one, named by its label until the person writes a name.

2. **Creating an identity is configuring an endpoint.** Registration stays configured-only (`ENDPOINTS.md`): a data-plane session cannot mint an endpoint by naming one. The client creates, renames and removes an identity through the administrative boundary — on the desktop over the admin connection, on Android through the embedded host's configuration path, the same seam that writes the stay-reachable choice — and enabling, disabling and the default live in ADR-0028's endpoint overlay (A 2026-10-11). The identities a node holds are capped by the profile's 64-endpoint bound (`MAX_ENDPOINTS`, `config.schema.yaml`'s `max=64`; no per-profile key exists, and `ENDPOINTS.md`'s table row says so since this record), authored and added together, the add method refusing at it by name. The administrative methods that add a configured endpoint, remove an added one and set an endpoint's `advertise` are p2p-network-dev's to shape, under ADR-0017's minor rule, and what the add method adds persists in ADR-0028's endpoint overlay — amended with this record (A 2026-10-21) to carry an added endpoint's definition beside the enabled and default deltas, so that `config.yaml` stays authored and unrewritten and the limit counts authored and added together; until the add method lands, no second identity exists on either platform — an endpoint authored by hand in `config.yaml` is a route, never an identity (decision 1), on the desktop as on Android, where the profile is app-private and `runtime.android.endpoint` is one field. Each identity the client presents holds **its own endpoint lease**: one local data session per identity — one IPC connection each on the desktop, one in-process session each on Android — inside the one runtime, so a client holding N identities holds N leases and the lease rules of `ENDPOINTS.md` hold unchanged.

3. **A conversation speaks as exactly one identity.** A direct conversation is keyed `{local EndpointId, remote PeerId, remote EndpointId?}`; everything it sends — messages, cards, receipts — leaves from that identity's lease, so the counterparty's `source_endpoint` names it, and it never changes identity. A channel conversation belongs to one identity too, but broadcast authorship is PeerId-only (ADR-0030): the identity travels as the `from_endpoint` display hint HUMAN-CHAT.md defines, unauthenticated beyond the PeerId, and the record promises nothing more for it. A new conversation speaks as the identity in front, named before the first send (decision 9: nothing asks which identity, since a chooser that could pick another identity while this one is in front is the confusion the owner's rule forbids), and every conversation shows it in its details and beside the composer. A client holding one identity has no identity in front to switch from: it names the identity only where it is asked for (the profile and identity settings), and the controls of decision 9 appear with the second identity. Two identities of one person are two identities to the client as much as to the counterparty (the owner's rule): nothing the person does under one is done under the other, and no surface may let them act as one while believing they act as the other — decision 9 says how. The profile's default endpoint (ADR-0030) is the identity a peer-only send reaches, and the person chooses it among their identities.

4. **A contact is one remote identity, held by the local identity that accepted it**: a route `{PeerId, EndpointId}` with the name and photo of the card accepted on it, under the local EndpointId whose conversation the card arrived in; the same counterparty accepted by two of the person's identities is two contacts, one per identity, and neither identity sees the other's — every rule of this decision is scoped to the identity in front's own contacts. Two endpoints of one PeerId are two identities and two contacts; the contact page shows the PeerId and says which other contacts of this identity share that node, and the client never merges them on its own and never splits one route in two. Routes of one person on other devices — other PeerIds, ADR-0043 — may be grouped under one contact by the person, never by the client, and a contact holds at most one route per PeerId. Accept on a route already under one of this identity's contacts updates that contact; Accept on a route this identity does not hold creates one, whatever another identity holds; Move moves the one route. A direct message that reaches an identity from a route it holds no contact for is titled by the short PeerId, never by a name another identity accepted. This replaces the rule of the same morning that a PeerId never ends under two contacts (ADR-0059 A 2026-10-21 (ii) withdraws it).

5. **What two identities of one node share is said, not hidden.** They share the PeerId and the node's addresses, so a counterparty who holds two of them sees one node — the same PeerId beside both contacts — and the network, a relay both use and the LAN see one device. The identity settings and the contact page say so in plain words. Two more things they say: every identity's endpoint carries `advertise: false` — a created one from its creation, the authored `human` one from the provisioning and every example profile that declares it, which plan §30 changes, and on an existing profile from an `advertise` delta in ADR-0028's endpoint overlay, which the client asserts at every open — every acquisition of the identity's lease, a reconnect after a daemon restart included — before it takes that lease, for each identity whose effective value is true — so no window exists in which a listed-and-leased identity answers a directory query; an assertion that fails refuses the lease and the client says so, rather than taking a lease the directory could list — through `admin.endpoints.set_advertise` on the desktop, the third method p2p-network-dev shapes beside add and remove, and through the embedded host on Android (ADR-0028 A 2026-10-21; `config.yaml` stays unrewritten, and plan §30 step 1 widens the desktop upgrade test's no-rewrite assertion to allow exactly that delta in the endpoint overlay) — and the client offers no control to change it, so the endpoint directory (ADR-0031) lists none of a person's identities to a trusted peer; and an identity's label is no secret from a peer the node trusts — any such peer that learns or guesses it can address it. The endpoint's own policy could narrow that (ADR-0030: narrows, never widens), but no control sets it in plan §30: an identity inherits the node's trust, the settings say so, and a per-identity reach subset is a revisit condition of this record. The separation for a person who needs two identities that no counterparty can link is **a second profile**: its own PeerId, phrase, daemon and store, which the desktop runs today as a second daemon and a second client, and the phone cannot (one embedded runtime, ADR-0041); even then both profiles leave from the host's addresses, so the network-level limit stays. The record names that form for that case and makes it no stage of its own.

6. **Recovery restores the node, not the identities.** The 24-word phrase restores the key and PeerId (ADR-0033) and ADR-0043's restore warning applies to the node. Identities are configuration — the endpoint list and its overlay — and store content — their cards: carried by the desktop's configuration export, by nothing on Android today, and by the device-to-device backup of ADR-0060 decision 8 only if its record says so.

7. **Every action has a command-line form** (ADR-0059 decision 9): list the identities the client holds, create one, rename it — the display name on its card, never the EndpointId, which keys its conversations and contacts for life — set its photo, set the default, remove an added one — always confirmed with the list of what goes: its endpoint, deleted from the overlay's `added` member through the administrative remove method p2p-network-dev shapes beside the add (its label free to be added again, as a new identity, the client saying before the add that counterparties may still hold a contact on that route with the old card's name and photo until they accept the new identity's card — the transport cannot withdraw a contact a counterparty accepted), its conversations and their messages, pending outbound deleted and attempted no further (a row that may have reached is named as such, RETENTION.md §2), its contacts and its card; no undo; never offered on the default until another identity is the default; the first identity is never removed, only turned off, which disables its endpoint and keeps it listed as off — allowed once another identity is enabled, the composed-profile check asking for one enabled identity rather than the authored one (ADR-0028 A 2026-10-21, plan §30) — and name the identity on every conversation and contact command.

8. **Automated clients are unchanged**: an agent's client holds the endpoint ADR-0055 shapes for it, which is a route and not a user identity and carries no card.

9. **The client operates as one identity at a time, and says which, everywhere.** The one store carries the local EndpointId on every conversation (`conversation_index`), every contact (`contacts`) and every own card (`own_cards`, STATE.md), and the client shows only the identity in front: its conversations, its contacts, its card, its default. Switching identity is one explicit act — a control that names the identity in front on every screen that can send, share, accept, create or delete, and the composer names it beside the send control — and the switch changes everything shown at once — these controls exist from the second identity on, a client with one identity showing none of them; there is no mixed list, no search across identities, no suggestion from one identity's contacts in another's chooser, and no action whose identity is implied by state the person cannot see. A notification names the identity it arrived on and opening it switches to that identity visibly before anything is shown; on a lock screen the client shows only the redacted form, whatever preview setting `human-client-ui.md` §10 allows after the unlock, and that form names no identity, since the identity's name may be what the person is hiding; the switch happens on opening, after the unlock; a share, an Accept and a new conversation run under the identity in front and nothing else. The Android service's one persistent notification names the node, since there is one runtime. The command-line client names the identity on every command that acts (decision 7) and, with more than one identity held, defaults to none.

## Alternatives considered

- **An identity is a whole profile** (this record's first draft). Rejected as the everyday form: a phone would run one runtime per identity — listeners, relay reservations, Kademlia membership, custody and a foreground service each — for a separation the network does not give, since every profile on the host shares its addresses. Kept as the heavier form of decision 5 for the person who needs unlinkability against a counterparty.
- **Several personas under one endpoint** (ADR-0059's cards as they stood). Rejected: a counterparty cannot address one persona, a conversation's identity would be a client-side flag the wire does not carry, and a reply would reach whichever persona the person had in front.
- **Hidden sub-keys under one PeerId.** Rejected by ADR-0016 and ADR-0043, and nothing here needs them.
- **Per-identity signatures above transport**, so that a broadcast's `from_endpoint` is authenticated. Deferred: ADR-0030's revisit condition, with no consumer asking yet.
- **A second installation of the app per identity.** Rejected as the design; it stays a person's workaround.

## Consequences

ADR-0030 is amended with this record (a use of the label above transport, nothing changed in what the transport authenticates); ADR-0059 is amended a second time the same day (one card per identity, a contact per remote identity, the one-contact-per-PeerId rule withdrawn); ADR-0041 is amended (the service holds one lease per identity in its one runtime). `human-client-ui.md` §2 step 4, §3, §4 and §13, STATE.md and CLAUDE.md §5 carry the inherited sentences; plan §30 names the work as Stage 22, opened on the owner's word; SPIKE-012, which measured two runtimes in one service for the first draft, is withdrawn. The transport, the wire and every contract under `architecture/contracts/` are unchanged except `ENDPOINTS.md`: its directory sentence names `advertise` as the effective value with the overlay applied (this record), its resource table's configured-endpoints row reads 64 with no per-profile default (ADR-0026 A 2026-10-21), and its registration sentence gains the administrative path when p2p-network-dev lands the add, remove and set_advertise methods, with ADR-0028's overlay amended to hold what the add method adds and the `advertise` delta of an authored identity.

## Security implications

Nothing changes on the wire, so nothing weakens there: trust, admission and authorship stay the PeerId's. The risks are the client's. A send under the wrong identity — or any act under one identity the person believes they take under another, which the owner's rule forbids by name — is answered by binding the conversation to one identity for life, by the client operating as one identity at a time with that identity named on every acting surface from the second identity on, and by the explicit, visible switch (decisions 3 and 9). A person misled about who a contact is — two contacts shown as two people when they are one node — is answered by the contact page showing the PeerId and the identity in front's shared-node note (decisions 4 and 5); the reverse, two same-name contacts on different PeerIds, stays told apart by the short PeerId (`human-client-ui.md` §13). An impersonation of one of a person's identities by another endpoint of the same node is the same person and no attack. The broadcast `from_endpoint` is a hint a counterparty may forge within its own PeerId, as HUMAN-CHAT.md already says, and the client renders it as such. The configured-endpoint limit and the lease rules keep the per-identity cost bounded; an attacker holding the device sees every identity, as every file.

## Operational implications

One runtime, one notification, one phrase: a phone with several identities costs what a phone with one costs, plus a lease and a queue per identity. An operator adds an identity as an endpoint is added today, until the administrative method lands. The default endpoint is a choice the person sees as "which identity a stranger reaches".

## Implementation implications

The work is plan §30's (Stage 22), rust-ui-dev's in the shared crates and the three clients, with the administrative add, remove and set_advertise methods p2p-network-dev's; `human-client-ui.md` §13 gains the acceptance criteria when the stage opens. STATE.md's `conversation_index`, `contacts` and `contact_routes` gain the local EndpointId — existing rows backfilled with the `human` endpoint, the one identity a client holds before this record, and a route's value bound to its contact's by a composite foreign key — and `own_cards` is keyed by it in the §Logical tables review. No spike is needed: every piece — several leases in one runtime, a session per lease, `source_endpoint` on every direct message — exists and is tested.

## Revisit conditions

When per-endpoint authorship above transport is wanted (ADR-0030's revisit); when a person asks that one identity be reachable to a subset of the node's trusted peers (the endpoint's own policy, ADR-0030, with a control the client does not have today); when a person asks for identities on the phone that no counterparty can link, which is a second runtime in the one service — the measurement the withdrawn SPIKE-012 described; when a backup should carry identities (ADR-0060 decision 8); when the configured-endpoint limit binds.
