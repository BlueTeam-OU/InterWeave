# Every endpoint is a key pair, and its EndpointId is derived from the public key exactly as the PeerId is from the node's; trust is per endpoint

**Status:** Accepted — the owner's direction of 2026-10-28, given in three parts on the record this supersedes in part: "each user identity is a endpointId and that endpointId should be derived from the endpoint keypair (same key algorithm, same hashing algorithm if used)"; "an endpointid is calculated the same way for all type of endpoint human and ai agent (cli, mcp, human, ecc)"; "trust is per identity (endpointid)"; and, on the cost of the change, "we have not an installed userbase, only agent-fabric that we can manage by updating at the same time and recreating the ids". Supersedes in part ADR-0030 (an EndpointId is no longer a label), ADR-0061 decisions 1, 2, 7 and 8 and its one trust set, and ADR-0063 decisions 1, 2, 4 and 6 (the key is the endpoint's, and a changed key is another endpoint); each is amended to point here. Built by Stage 22 (plan §30), which opens on the owner's word.

## Context

Two identifiers exist under one node. The **PeerId** is the node's cryptographic name: the libp2p multihash of its Ed25519 public key, written as the base58btc string every record and every wire frame carries (`IDENTITY-RECOVERY.md`: one profile owns one Ed25519 identity key and one derived PeerId; `crates/api/transport-api/src/ids.rs`: a canonical PeerId is `12D3KooW` followed by 44 base58btc characters). The **EndpointId** was, until this record, a name: a lowercase ASCII label of 1 to 64 bytes an operator wrote into the profile's configuration, "stable while configured, but not cryptographically derived" (`ENDPOINTS.md`), a routing selector under the PeerId that proved nothing (ADR-0030). ADR-0061 then made a user identity an EndpointId with a card, and ADR-0063 gave each user identity an Ed25519 signing key of its own, carried and proved by the card — but the label and the key were unrelated: an identity's name on the wire was whatever the configuration said, and its key was a fact of the card alone. An automated client's endpoint (ADR-0055) had a label and no key at all.

That left a gap the owner named on reading ADR-0063's summary ("user identities have their own separate Ed25519 keys tied to contact cards, not EndpointIds"): a counterparty could not tell from the wire that the endpoint it was talking to was the identity whose card it held, since the EndpointId said nothing about the key, and two identities of one node shared one trust set, so trusting a peer for one trusted it for all. The owner's rule closes both: an endpoint is a key pair, its EndpointId is that key's PeerId-style name, and trust is held per endpoint.

The cost that would normally stop such a change — every configured endpoint, every fixture vector, every contact route and every rendered profile carries an EndpointId — is not paid here: there is no installed user base, only the fleet's agents, which the fabric updates at one time and whose identities it recreates (the owner's word). This record is therefore a clean break with no compatibility window, on the owner's word.

## Decision

1. **Every endpoint is an Ed25519 key pair, whatever client kind holds it.** A human identity, a command-line client's endpoint, the Claude Code Channel bridge's endpoint and an automated client's endpoint are one kind of thing: a configured endpoint whose key pair was generated with it from the system's CSPRNG, never derived from the node's transport seed, so that a node's phrase restores the node and not its endpoints (ADR-0063 decision 1, which this record generalises from user identities to every endpoint). The key pair is the endpoint; its public key is the endpoint's cryptographic name.

2. **The EndpointId is derived from the endpoint's public key exactly as the PeerId is from the node's**: the same libp2p multihash over the same protobuf encoding of the Ed25519 public key — the identity hash, since an Ed25519 key is short enough that libp2p hashes nothing — written in the same canonical base58btc text, 52 characters beginning `12D3KooW`. An EndpointId is, byte for byte, what the endpoint's key would be as a PeerId; `ENDPOINTS.md` states the grammar, which replaces the label grammar whole. Consequences the derivation fixes: an EndpointId is unique by construction within a node and across nodes (two equal ids are one key); it cannot be chosen, only generated; a hand-written id is refused at configuration load and at every administrative add (`EndpointIdNotDerived`, named in `ENDPOINTS.md`); and every byte bound a label met, the EndpointId meets — 52 is under the 64-byte ceiling `ipc/hello` and every payload budget were computed with, so no ceiling moves.

3. **A configured endpoint names its key, not an id.** The profile's endpoint entry (`ENDPOINTS.md` §Configured endpoint set, `config.schema.yaml`) carries the key's reference — the sealed key file under the state root, `<state_dir>/endpoint-keys/<EndpointId>.key`, the directory ADR-0063 decision 2 named `identity-keys/` renamed for its wider subject, in the same `IDK1` envelope, under the same custody (the store key's level, ADR-0060 decision 3; the Keystore alias namespace `interweave.idk1.<profile>.<EndpointId>` on Android) — and the daemon or embedded host derives the id from the public key at load; an entry whose key file is missing or unreadable loads in the **key-missing state** of decision 5 (its lease and routes stay, it signs nothing), and the only refusals at load are an entry that names an id instead of a key, an id in a file's header that does not derive from the key beside it, and an id that collides with another entry's. Everything else the entry carried stays: `enabled`, `advertise`, `allowed_client_kinds`, `inbound` and `outbound`, and the endpoint overlay's `added`, `enabled`, `default` and `advertise` members (ADR-0028). What a person or an operator types to pick an endpoint — today's `human`, `fabric-control`, `gzcoord` — becomes a **local alias**, a display name of the configuration and of the clients' command lines that never reaches the wire, carries no uniqueness beyond the profile and proves nothing, the way a contact's name is local (ADR-0059); a client's `--endpoint` and the identity list accept the alias or the id, the client resolving an alias from the profile's configuration it already reads (the desktop and the command-line client read `config.yaml` and the overlay, a rendered deployment's client the file the renderer wrote), while `ipc/hello` and every wire field take the id alone.

4. **An endpoint key is minted where the endpoint is created, and the deployment can mint one with no daemon.** The human client creates an identity by generating its key through the administrative boundary (ADR-0061 decision 2, the add method taking the public key, or the reference of a key file the client sealed, and returning the derived id — the private key never crosses the IPC, ADR-0063 decision 2); `transportctl endpoint init --profile <name> [--alias <alias>]` mints a key pair under the state root with no daemon running and prints the EndpointId, as `identity init` does for the node (ADR-0055 decision 4), so that a deployment that renders profiles — the fleet's — mints each account's endpoint keys on the host, reads the ids back, and records them in its own roster in place of labels; a rendered `config.yaml` references the key files it minted. The fabric's record of its carrier (agent-fabric ADR-064) names its endpoints by label today and changes with this record, by proposal to fabric-coordinator; nothing of that record is cited here.

5. **The contact card's key is the endpoint's key, and the receiver checks the derivation.** `card.identity_key` (ADR-0063 decision 3, HUMAN-CHAT.md §Contact card) is the public key of the endpoint the card is sent from, and a receiver verifies, beside the signature, that the key derives the `source_endpoint` the card arrived on; a card whose key does not is malformed (stored nowhere, shown nowhere, counted under HUMAN-CHAT.md's malformed rule). So a card cannot present one endpoint's name under another endpoint's key, an identity cannot be impersonated by another endpoint of the same node, and the fingerprint a person compares (ADR-0063 decision 1) is a fingerprint of the EndpointId's own key. ADR-0063 decision 4's **key change** cannot arise: a different key is a different EndpointId, a different route and, under ADR-0061 decision 4, another identity of that node, which the proposal says in those words; the key-change proposal, the `--accept-key-change` flag and the replace-the-key-in-the-route rule are withdrawn (ADR-0063 amended). A lost or refused key is ADR-0063's key-missing state, now one rule for every endpoint: the endpoint holds its lease and its routes, since the lease is configuration, signs nothing, and the client says so; the way out is a **new identity** — a new key, a new EndpointId, its card shared again — never a new key under the old name, which no longer exists, so ADR-0063's silent first key (A 2026-10-24, 2026-10-27), which minted a key under an unchanged name, is withdrawn: a missing key is always the key-missing state, said. An added identity in that state is removed with its conversations and contacts under ADR-0061 decision 7 once the new one exists; the first identity, which is never removed, is turned off and keeps its conversations and contacts readable under it, and the new identity becomes the default — the authored entry stays authored and unrewritten, and the new identity lands in the overlay's `added` member like any other.

6. **Trust is per endpoint.** The person's trust acts — allow, revoke, the Trust screen, `trust list|set` — are the identity in front's (ADR-0061 decision 9), and each identity holds its own trusted set, written as its endpoint's `inbound` and `outbound` subset (`ENDPOINTS.md`). The node's allow-list stays what ADR-0028 makes it — `trust.allowed_peers` in `config.yaml`, plus the trust overlay's added peers, minus its revoked ones, bounded by `MAX_ALLOWED_PEERS` and FATAL past it — and stays the transport's admission list: every endpoint's set is a subset of it, an endpoint entry that carries no subset inherits it (`inherit_profile_trust`, the option the contract keeps, which is how a rendered profile and today's profiles read), and the human client keeps the node's list equal to the union of its identities' sets, adding a peer to the list when the first identity trusts it and removing it when the last one stops. An endpoint-less trust call — `admin.trust.set {peer, allowed}` and `transportctl trust allow|revoke` as they are, ADR-0055 decision 4 — writes the node's list and reaches every endpoint that inherits; the endpoint dimension of those methods is for an identity's own set. Trusting a peer in identity A admits it for A's endpoint alone; B neither sees nor admits it until B trusts it; untrusting in A removes A's admission, and the node drops the peer from its transport set only when no endpoint trusts it. What this does not reach is said: admission at the connection is the node's (a peer trusted by any endpoint may connect, and is refused per endpoint at the route), and **broadcast stays node-wide** — subscriptions, publication admission and the ingress bucket are the PeerId's (ADR-0029, ADR-0030), so a channel's publishers are trusted by the node, not by an identity; a channel conversation still belongs to one identity (ADR-0061 decision 3) for what it shows, not for what it admits. `admin.trust.set` and `admin.trust.list` gain the endpoint dimension as an IPC minor in p2p-network-dev's lane, the contract text architect-cto's.

7. **A clean break, in the release that builds it.** No compatibility window: a profile whose endpoint entries carry ids rather than keys is refused at load with the reason named; the label grammar leaves `ENDPOINTS.md`, and every fixture vector that carried a label (`fixtures/endpoints/`, `fixtures/direct-v2/`, `fixtures/ipc-v2/`, `fixtures/config/`, `fixtures/human-chat-v2/`) is regenerated under this record's grammar — a protocol change by decision, not a drift. The versions say the break: the endpoint-id and endpoint-config schemas go to `2.0.0`, every schema that `$ref`s the endpoint-id (the direct, IPC, endpoints and human-chat families, among them `ipc/hello-response`, `ipc/send-params`, `ipc/endpoint-list`, `direct/dedup-key`, `endpoints/message-received`, `human-chat/envelope`) takes a major in the same batch, the direct protocol becomes `/interweave/direct/3.0.0` and the IPC major `3` (ADR-0017's rule for a shape no older reader tolerates), so that a node of the release before this one and a node after it fail at the protocol or the handshake, by version and by name, never frame by frame. Until that batch lands, `1.0.0` and the label are the wire, as `ENDPOINTS.md` and HUMAN-CHAT.md say in place. The release that carries it is the next MINOR under ADR-0065 (a breaking change below 1.0), its notes naming the break; the fleet's profiles are re-rendered with keys and its ids recreated at the update, as the owner directed.

8. **What stays.** One node, one PeerId, one phrase, one store, one custody, one runtime (ADR-0061 decision 1); at most 64 endpoints per profile, `MAX_ENDPOINTS`; configured-only registration and the lease model (`ENDPOINTS.md`); the card as the identity's presentation (ADR-0059, ADR-0061); what two endpoints of one node share, the PeerId and the addresses, said and not hidden (ADR-0061 decision 5); the EndpointId as peer-asserted routing metadata on the wire, authenticated by the PeerId's connection and, with a card, by the endpoint's own signature — the transport still grants no trust to an EndpointId.

## Alternatives considered

- **Keep the label and bind the key to it through the card alone** (the state before this record). Rejected by the owner: the name on the wire said nothing about the key, so a node could present any of its keys under any of its labels, and the identity a counterparty held was two unrelated facts.
- **Derive only a user identity's id, and keep labels for automated and operator-authored endpoints.** Proposed by architect-cto and rejected by the owner: one derivation for every endpoint kind, so that no endpoint is a name and the fleet's agents are endpoints like any other.
- **A different text form for the derived id** — the lowercase base32 multibase form of the key, which would have fitted the old lowercase grammar, or a hex fingerprint. Rejected: the owner asked for the PeerId's own construction, "same key algorithm, same hashing algorithm if used", and one form means one parser, one fixture family and one thing a person reads; the base32 form of a libp2p-key CID is 65 characters, one over the ceiling, and a fingerprint is not a key's name.
- **A compatibility window** (both grammars accepted for a release, the old form mapped to a new key). Rejected on the owner's word that no installed base exists; a window would have kept the label grammar alive in every parser for no user.
- **Trust per identity by a separate allow-list per endpoint with the node's list beside it.** Rejected: `ENDPOINTS.md` already has the per-endpoint `inbound`/`outbound` subsets and the rule that they narrow and never widen; the union as the node's set is the smallest change that makes the person's view the rule.
- **Per-identity broadcast trust.** Rejected for now: broadcast authorship, subscription and admission are PeerId-only by ADR-0029 and ADR-0030, and changing them is a wire change this record does not make; the limit is stated in decision 6.

## Consequences

ADR-0030 is amended: an endpoint identifier is derived from the endpoint's key and is the one thing on the wire that names an identity's key, still peer-asserted as routing metadata and still no authorization principal. ADR-0061 is amended: decisions 1, 2, 7 and 8 read "a key pair whose id is derived" where they read "a configured label", the one trust set becomes the union of the identities' sets, and a renamed identity renames its alias and never its id. ADR-0063 is amended: the key is the endpoint's, the directory is `endpoint-keys/`, the key change is withdrawn, and `identity new-key` becomes the creation of a new identity. ADR-0055 is amended: an automated client's endpoint is a key the deployment mints with `transportctl endpoint init`, its id in the roster. `ENDPOINTS.md` carries the grammar, the derivation, the alias, the refusal and the per-endpoint trust rule; HUMAN-CHAT.md §Contact card the derivation check; STATE.md the `endpoint-keys/` directory and `own_cards` keyed by a derived id; `config.schema.yaml` the entry by key with its alias; LOCAL-IPC.md the trust methods' endpoint dimension when that minor lands. Every fixture family that carries an EndpointId is regenerated once, by the lane that owns it, under `verify_fixture_vectors.py`. Stage 22's Activate list widens by the transport-api EndpointId type and grammar, the fixtures, the profile entry by key, `transportctl endpoint init` and the trust minor, all p2p-network-dev's and first in the order, since nothing above them can be built against a label.

What becomes harder: a person can no longer read an endpoint's purpose from its id on the wire (`human`, `gzcoord`); the alias carries that locally and the card carries it to a counterparty. A deployment that rendered endpoint names now mints keys per endpoint per account and keeps the ids, one more secret per endpoint under the account's state root.

## Security implications

The EndpointId becomes a commitment to a key: a card received on an endpoint is refused unless its key derives that endpoint, and a counterparty holding an identity's card can verify a later card against the id. A message is not verifiable by its EndpointId: a frame's id is the key's name by construction, the lease that sends under it is configuration and proves no possession of the key, and a same-node client holding that lease sends as the endpoint — until ADR-0064 signs frames under the endpoint's key, the id on a message proves only what ADR-0030 said, that the authenticated node claimed it. An impersonation across the endpoints of one node — presenting identity A's name with identity B's key, or the reverse — is detectable at the receiver, which it was not. Trust per endpoint removes the silent widening in which trusting a peer for one identity trusted it for every identity of the node; the node's union set still admits the connection, and the refusal is at the route, so an untrusted-for-this-identity peer learns `no_route`, the coarse answer the direct protocol already gives (ADR-0005), and nothing about which identities exist. What is not changed: the transport authenticates the PeerId and nothing above it; an EndpointId on a frame is still asserted by the sending node, verified only where a signature under its key arrives (the card today, ADR-0064's layer later); broadcast trust and admission stay node-wide; unlinkability between two identities of one node is not gained, since they share the PeerId (ADR-0061 decision 5). One more long-term secret per endpoint lives under the store key's custody, with ADR-0063's limits: once unwrapped it is in the process's memory, and an attacker holding the device holds it. A lost key is a lost identity, as it was; this record removes the one path that let a changed key keep a name.

## Operational implications

An operator sees `endpoint-keys/` under the state root with one sealed file per endpoint, and an EndpointId that reads like a PeerId. A profile is written with key references and aliases, never ids; `transportctl endpoint init` mints a key and prints the id for a rendered deployment, `endpoints list` shows alias and id. A rendered deployment keeps the ids it read back and re-renders a profile when it adds an endpoint; the fleet's thirty accounts are re-rendered once at the release that carries this record, their ids recreated. A backup that does not carry `endpoint-keys/` (a platform backup never, ADR-0060 decision 8; the device-to-device transfer only when its record says so) restores a node whose endpoints have no keys, which is the key-missing state for each, resolved by new identities: the recovery flows say so, as ADR-0063 had them say for identities.

## Implementation implications

p2p-network-dev, first and in its own PR: the `EndpointId` type and grammar in `transport-api` (a derived id, constructed from a public key or parsed from its canonical text, never from a label), the fixture vectors of every family that carries one, the profile entry by key reference with its alias and the loader's derivation and refusals, `transportctl endpoint init` and `endpoints list`, the trust methods' endpoint dimension (an IPC minor under ADR-0017, the text architect-cto's), and the union-of-endpoints `PeerTrustPolicy` with per-endpoint `inbound`/`outbound` as the rule. rust-ui-dev: the key minted on identity creation through the admin add, `endpoint-keys/` and the alias in the shared crates, the card's derivation check in `chat-protocol`, the withdrawn key-change flow and the new-identity flow in its place, the Trust screen and the trust verbs per identity, `--endpoint` by alias or id. rust-services-dev: the bridge's endpoint by key reference and the plugin's configuration. fabric-coordinator, by proposal: the renderer mints endpoint keys per account and the roster carries ids. architect-cto: this record's amendments, the contracts, the plan's §30 Activate and order. Nothing is built before Stage 22 opens on the owner's word.

## Revisit conditions

When ADR-0064 is accepted (the endpoint key becomes the root of the agreement keys and the multi-device device list, and the derivation check extends from the card to every signed frame); when per-identity broadcast trust is wanted (a wire change to ADR-0029/ADR-0030's PeerId-only authorship); when a second key algorithm joins Ed25519 for the node (the derivation follows the PeerId's for that algorithm); when an installed base exists and a grammar change would need the window this record refused.
