# Every user identity has its own signing key, and the contact card carries and is signed by it

**Status:** Accepted — the owner's direction of 2026-10-21 ("A matter is peer level encryption and another should be the end2end encryption"; "do it", on the recommendation that the card carry an identity key now and the full layer follow as a proposed record, ADR-0064)

## Context

What is encrypted today is the link: Noise authenticates the PeerId and encrypts each peer connection with ephemeral keys, a relay carries ciphertext, and a broadcast is signed by the PeerId and encrypted only hop by hop among the trusted peers that forward it (`transport/libp2p/SECURITY.md`, "the per-hop Noise, trusted-forwarder plaintext boundary"; group encryption "still deferred"). The key belongs to the node. A user identity (ADR-0061) is an EndpointId under that node with a card (ADR-0059), and nothing cryptographic is the identity's own: two identities on one phone share one Noise key, a card is bound to the PeerId it arrived on and to nothing else, and the records say in as many words that an identity is "authenticated only by the PeerId" (ADR-0032's revisit, "a higher-level application identity system"; ADR-0059's, "an application identity layer with a stronger binding than the PeerId").

End-to-end encryption at the identity level is a layer above the transport, decided as ADR-0064 in proposed state. What cannot wait is the one field a card ships with: once cards are exchanged without an identity key, every contact made before the layer has to be re-exchanged when it arrives. This record gives each identity a key now and puts it in the card.

## Decision

1. **Every user identity has an identity key pair**, Ed25519, generated with the identity from the system's CSPRNG — never derived from the node's transport seed, so that the same identity can later live on a second node (ADR-0064) and a node's phrase restores the node, not the identities. The public key is the identity's cryptographic name; its fingerprint (the first 8 bytes of the SHA-256 of the public key, shown as 16 lowercase hex characters) is what a person compares. Because the node's phrase restores the node and not the identities, a restore onto a state root that holds no `identity-keys/` directory — fresh state — gives every identity a new key, and every recovery flow says so before it takes the phrase, with the consequence that counterparties will see a key change (`IDENTITY-RECOVERY.md` §Restore semantics item 12, `human-client-ui.md` §9; A 2026-10-21). Outside the recovery flow a missing key file is a loss, not a first key (A 2026-10-24): the build makes a key silently only for an identity that has never shared its card — `card_shared_at` absent on every conversation that speaks as it, the one record this device holds, since the identity's own public key lives nowhere once its file is gone and a store discard, which clears that record too, is itself a confirmed loss — and otherwise the identity enters a key-missing state in which the person confirms the new key, told that counterparties will see a key change; the same holds when the whole `identity-keys/` directory is missing on a root that is otherwise there. A key file refused at open, or one the private read refuses as not private (then with no offer to tighten it, since it may already have been read), goes only on that confirmation: the old file is removed and the new key created after it — the Keystore alias is one per identity, so a new seal destroys the old wrapping key — and a failure between the two leaves no file, which the next open reads as the key-missing state and never as a silent new key, since the share record stands; the client never shows a key made that it cannot open; an `identity-keys/` directory the client's own user owns with a loose mode it makes owner-only itself before that step, while a link or another user's directory there is refused with the fix named and no new key, since the client neither follows nor replaces a path someone else placed: a record a newer build wrote (an unsupported version or an unknown custody) is offered the update first with the new key beside it, a platform cipher's refusal is offered a retry first, and nothing is kept aside, since one sealed file per identity at its path is the rule.

2. **The private key's custody is the store key's (ADR-0060 decision 3), not the seed's seam.** One sealed file per identity, `<state_dir>/identity-keys/<EndpointId>.key`, beside the store key under the state root and the trust boundary (ADR-0028), in an envelope of its own — magic `IDK1`, version, the EndpointId and the public key as associated data, so an identity-key record and a seed record can never authenticate in each other's place, and the seed seam's one-alias-per-policy retirement never touches it. On Android the wrapping key is an `AndroidKeyStore` AES-256-GCM key in its own alias namespace, `interweave.idk1.<profile>.<EndpointId>`, at the `background-compatible` level, since the identity must sign and later decrypt without a person present; on the v1 desktop the file is owner-only under ADR-0038's `filesystem-only` floor. The record names its custody (a custody field in the header, under the associated data) and that custody is a floor, never a choice (A 2026-10-22, rust-ui-dev's question on the desktop file): a platform that holds a wrapping key refuses at open, by name, a record sealed at the `filesystem-only` floor, as a downgrade — the person is told and creates a new key, a key change to counterparties — and a desktop refuses a Keystore-sealed record as unreadable here. One re-seal exists, upward only: when a platform adopts a stronger custody for its own records — the desktop joining ADR-0038's SPIKE-007 envelope, as the store key does under ADR-0060 decision 3 — it re-seals the identity-key files it holds at that moment, atomically, in the same adoption step, and nothing else; a record is never re-sealed at open, never downward, and never on arrival from another device, so a key file copied between devices never rides on the weaker platform's protection. The open check is the same five refusals on every platform — another magic (a seed record), a version this build does not read, a custody this build does not know, an EndpointId other than the file's name, a public key that is not the secret's — with the AEAD's authentication on top where a wrapping key exists. Remove of an added identity (ADR-0061 decision 7) deletes its key file and its Keystore alias with the rest (A 2026-10-21, rust-ui-dev's question on the criteria): the key is the identity's and goes with it, a counterparty keeps the contact it accepted, and an identity later created on the freed label is a key change to them. A Keystore invalidation leaves the identity with no key: the client says so, and the person creates a new one, which the counterparty sees as a key change (decision 5). Nothing of the key enters the human store, a backup, a log or IPC; an export is ADR-0064's.

3. **The contact card carries the identity's public key and is signed by it.** HUMAN-CHAT.md §Contact card gains two required members, `card.identity_key` (the 32-byte Ed25519 public key) and `card.signature` (the 64-byte Ed25519 signature) — their base64 form, the canonical bytes the signature covers (a fixed prefix, then the name, surname, photo media type, photo hash, the sender's PeerId and the source EndpointId, each length-prefixed, the names in NFC) and the strict verification rule are HUMAN-CHAT.md's and defined there alone; the envelope schema (`human-chat/envelope` 2.2.0) requires both. The PeerId and EndpointId inside the signed bytes bind the card to the route it is sent from, so a card lifted from one node cannot be replayed from another. A card whose key or signature has the wrong length, or whose signature does not verify over the bytes the receiver reconstructs from the envelope and the connection it arrived on, is **malformed**, one fixed reason per fault, dropped and counted as HUMAN-CHAT.md says. The card stays bound to the authenticated `source_peer` as ADR-0059 decision 1 says; the key is what the card additionally proves, not a substitute for the connection.

4. **A contact records the identity key.** `contact_routes` gains `identity_key`, absent until a card is accepted on the route (a typed contact, and every route from before this record, has none), set by the first accepted card, which records the key and is no change; a contact page shows the fingerprint beside the PeerId. Two cards from one route with the same key are one identity; a route whose key differs from the recorded one is a **key change**: the proposal says so in plain words before Accept — the person may accept the new key, which replaces the old one in that route and nothing else, or decline — and the client never accepts a changed key on its own. A card with the same identity key from a different PeerId is the same identity on another node (ADR-0064's multi-device case): until that record lands the client treats it as a new route the person may group under the contact by hand (ADR-0043), and says the key matches.

5. **What the key proves today, and what it does not.** It proves that whoever sent this card holds the identity's private key, and that a later card from the same route is the same identity or a declared change. It encrypts nothing yet, authenticates no message, and grants no trust: trust stays the node's allow-list on the PeerId (ADR-0012). Until ADR-0064 lands, the key is a name a person can compare, not a channel.

6. **Every action has a command-line form** (ADR-0059 decision 9): show an identity's fingerprint, show a contact's, and the key-change decision on a proposal.

## Alternatives considered

- **Derive the identity key from the node's seed and the EndpointId.** Rejected: the phrase would restore it, but the identity could never move to a second node without cloning the node's key, which ADR-0043 forbids; independence is the point of the layer.
- **Wait and add the key with ADR-0064.** Rejected by this record: every contact made before it would carry no key and would have to be re-exchanged; the field is cheap now and expensive later.
- **An X25519 key now.** Rejected: agreement keys and prekeys are the protocol's, chosen with it (ADR-0064); a signing key is what a card needs and what every protocol can authenticate its agreement keys with.
- **The card unsigned, the key a plain member.** Rejected: an unsigned key proves possession of nothing, and the binding to the route is what stops a card from being replayed from another node.

## Security implications

The identity key is a second long-term secret per phone, sealed at the store key's level with its own envelope and alias namespace and under the same limits as the seed: once unwrapped it is in the app's process memory, and an attacker holding the device holds it. The signature binds name, surname, photo (bytes and media type) and route, so a card replayed from another node fails to verify and a card tampered in flight (impossible under Noise, but the envelope should not rely on it) fails too. The key change is the one new user-facing security event: a changed key may be a reinstall or an impersonation, and the client cannot tell them apart, so it says both and lets the person decide, as every messenger with safety numbers does. The fingerprint is 64 bits, enough to compare by eye, not to be ground against a target's; a full-key compare is ADR-0064's verification screen. Nothing here changes what the transport authenticates or admits.

## Operational implications

A new identity costs one key generation and one sealed file; a card is about 165 bytes longer on the wire (two base64 members and their names). An operator sees an `identity-keys/` directory beside the store key under the state root; no backup carries it today — a platform backup never (ADR-0060 decision 8), and the device-to-device transfer only when ADR-0064's record says so — so until then no backup moves it — a desktop state root copied by hand carries the sealed file, as the store key's does — and a lost key is a new identity key.

## Implementation implications

rust-ui-dev: the key pair and its custody in the shared crates — sealed as the store key is (ADR-0060 decision 3): its own IDK1 envelope and alias namespace, the Android wrapping key reached through the embedded host as the store key's is, never the seed's custody seam; the owner-only file on the desktop — the card's members and signature in `chat-protocol`, the fixture vector, the contact's `identity_key` and the key-change proposal, the fingerprint on the identity and contact pages and in the command-line client. p2p-network-dev: nothing on the wire. HUMAN-CHAT.md §Contact card holds the canonical bytes and the verification rule; `tools/checks/verify_fixture_vectors.py` recomputes the vector. The work rides plan §29 steps 1 and 2.

## Revisit conditions

When ADR-0064 is accepted (the key becomes the root of the protocol's agreement and the multi-device device list); when a verification screen compares full keys; when the owner wants the identity key restorable from a phrase of its own. And when SPIKE-007's passphrase envelope lands on the desktop (ADR-0038): the adoption step re-seals the identity-key files in the same step as the store key (ADR-0060 decision 3), each in its own envelope as decision 2 keeps them (A 2026-10-22), and that step's criterion is written then.
