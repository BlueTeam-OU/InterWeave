# Every InterWeave version is a Semantic Versioning 2.0.0 version, and one release version names every artifact of a release

**Status:** Accepted — the owner's direction of 2026-10-23 ("from here ahead interweave will follow semver 2.0.0"); the declared public API in decision 2 and the mechanics in decisions 3 to 6 are architect-cto's reading of it, revised at the owner's word.

## Context

Until now the project had release mechanics without a versioning rule. The release run (`.github/workflows/release.yml`) takes a tag `v<MAJOR>.<MINOR>.<PATCH>` on `main`, refuses a pre-release or a leading zero, and passes the bare triple to the archive and APK scripts, which name the files with it and check it against the APK's `versionName`; nothing says what the three numbers mean. Every first-party crate carries `version = "0.0.0"`, the plugin manifest ships `"version": "0.0.0"` in every release so `claude plugin update` reports nothing to update (`packaging/claude-plugin/INSTALL.md`), and the Android `versionName` is a hand edit before the tag. The wire has its own versions already — IPC v2's negotiated `{major, minor}` (`LOCAL-IPC.md`), each schema's `x-contract` version under ADR-0049, the profile-format marker of ADR-0028 — and none of them is the release version. The first tagged release is near (Stage 19, plan §22), and a fleet deployment (ADR-0055) will upgrade and roll back by version, so what a version promises has to be decided before the first one exists. Semantic Versioning 2.0.0 requires the project to declare its public API (its §1); that declaration is this record's substance.

## Decision

1. **Every version InterWeave publishes is a Semantic Versioning 2.0.0 version** (`MAJOR.MINOR.PATCH`, optional pre-release identifiers after `-`, optional build metadata after `+`, precedence as that specification's §11 defines it), and **one release version names every artifact of one release**: the Linux archive and the programs in it, the Android APK and its `versionName`, the Claude Channel plugin's manifest `version`, and every first-party crate's `version`. The git tag is `v` followed by the version; the release run derives the version from the tag and refuses an artifact whose own version differs, as it already refuses an APK whose `versionName` differs.

2. **The public API the version speaks for is what a conforming peer, client, profile or script of the previous version relies on**: the wire protocols in their `active` contracts (`/interweave/direct/2.0.0`, the broadcast topic grammar, the envelope and HumanChatV2, the connectivity protocols) and the behaviour the prose promises for them; IPC v2's method table, its request and result shapes and its negotiation; the profile, configuration and state formats a daemon reads (`config.yaml`, the overlays, the store, the profile-format marker); the `LocalDataSession` binding; the command-line clients' verbs, arguments, output shapes and exit codes (`transportctl`, `interweave-human`); the bridge's tool surface and plugin settings; and the release artifacts' names and layout as `install.sh` reads them. A change after which such a thing of the previous version fails, misreads or is refused is MAJOR; a backward-compatible addition is MINOR; a change that corrects behaviour without changing what is relied on is PATCH. Documentation, tests, tooling and the dependency graph are not the public API; a dependency bump that changes nothing relied on is PATCH.

3. **Initial development is `0.MINOR.PATCH`** (the specification's §4): the public API is not yet stable, and until `1.0.0` a change that would be MAJOR raises MINOR and is said in the release notes as breaking. `1.0.0` is cut on the owner's word, when the owner declares the public API of decision 2 stable; nothing in the stage plan cuts it by itself.

4. **The internal version schemes stay their contracts' own, and the release version follows from them, never the reverse.** IPC v2's `{major, minor}` is negotiated on the socket and advances by `LOCAL-IPC.md` §Version negotiation's rule; a schema's `x-contract` version (a `MAJOR.MINOR.PATCH` by ADR-0049's meta-schema, independent of the wire version it describes) advances by its family's rule — for the `ipc` family ADR-0017's (its Decision and its amendments, the 2026-10-01, 2026-10-07 and 2026-10-09 ones among them, and `LOCAL-IPC.md` §Version negotiation), the other families having no written rule yet beyond this specification's precedence; the profile-format marker (ADR-0028 A 2026-10-20) is one integer `N`, never lowered, every raise refusing older builds. A change that raises IPC's major or a schema's MAJOR, or that a conforming reader of the previous release cannot take, makes the release MAJOR (MINOR before `1.0.0`); a change that raises one of their minors makes the release at least MINOR; a raise of the profile-format marker makes the release MAJOR after `1.0.0` and MINOR before, since the previous release can no longer read the profile, and the release notes name it as a rollback boundary; a release's version says nothing about which of them moved — the contracts and the release notes do.

5. **The version lives in one committed place and is checked, not copied by hand.** The workspace's `[workspace.package] version` in the root `Cargo.toml` is the release version, inherited by every first-party crate (`version.workspace = true`), reported by every program's `--version`, and the single source the APK's `versionName`, the plugin manifest's `version` and the archive's names are produced from or checked against; the commit that sets it precedes the tag, as the APK rule already requires, and the release run refuses a tag whose version is not the workspace's. The Android `versionCode` is not a version: it is a counter the platform orders installs by, raised by one for every APK published, pre-releases included, and never derived from the version.

6. **Pre-release and build metadata.** A tag may carry pre-release identifiers (`v0.4.0-rc.1`); the release run publishes it marked as a pre-release and never as the latest release, the archive, APK and plugin carry the full version, and the identifiers follow the specification's grammar (dot-separated, no leading zeros in numeric ones). A tag carries no build metadata; a program's `--version` may append `+<short commit id>` and comparison ignores it, as the specification says.

## Alternatives considered

Calendar versioning (`2026.10.1`) would date a release without saying whether an upgrade is safe, which is the one thing a fleet rolling back needs from the number. A version per artifact (the daemon at one number, the APK at another) would make "which release is the phone on" a table instead of a string, and every compatibility statement a matrix. Leaving the versions at `0.0.0` until a stable API exists was the state of the tree, and it is the state the owner ended: the plugin's updater could not see an upgrade, the archive's name said nothing, and the first release would have taught the fleet nothing about the second. Deriving the Android `versionCode` from the version (`MAJOR×10⁶ + …`) was considered and refused: a pre-release and its final share a derivation or collide, and the platform wants a counter.

## Consequences

The root `Cargo.toml` gains a workspace version and every first-party crate inherits it (one mechanical change across the manifests, with the Cargo.lock it implies); the plugin manifest and the Android `versionName` become produced or checked values, so `claude plugin update` sees a new version at each release and the hand edit before a tag stops being a step; `release.yml` admits a pre-release tag and marks the release accordingly; the release notes say, per release, which contracts moved. Every reviewer of a PR that touches decision 2's surfaces now has one more question: does this change the public API, and does the next version's number say so — the plan's §22 record names the version each release ships under and why. Cost: the first release after this record is a MINOR of `0.y.z` whatever it contains, and the breaking changes still ahead in initial development are MINORs that must be read in the notes, not from the number.

## Security implications

None directly. A version names a release; it authenticates nothing — the archive's and APK's SHA-256 on the release page and the APK's signature do (ADR-0057). What the rule removes is a class of mistaken trust: a fleet that reads "the same version" as "the same contracts" is right only if decision 1 holds, which the release run enforces rather than a person remembering.

## Operational implications

An upgrade or a rollback is judged by version precedence first and by the profile-format marker second: the marker (ADR-0028) is what refuses a daemon older than the profile it finds, the version is what the operator reads; the upgrade and rollback Validate rows (`human-client-packaging.md` §9, plan §22) cite the version they were run across, and `packaging/linux/DEPLOYING.md` gains an upgrade and a rollback section naming the versions of the recorded run when one is made (p2p-network-dev's). A pre-release is what the stage host runs before the production host does, named so in the tag.

## Implementation implications

The root manifest's workspace version and the crates' inheritance, and `release.yml`'s tag rule and pre-release marking, are devex-tooling's with p2p-network-dev's release scripts (`tools/ci/release_linux_archive.sh`, `release_android_apk.sh`: accept the full grammar, check against the workspace version); the plugin manifest's version is rust-services-dev's (`packaging/claude-plugin/build.sh` writes it from the release version); the Android `versionName` and `versionCode` rule is rust-ui-dev's (`apps/human-android/android/app/build.gradle.kts`); `--version` on `transport-daemon`, `transportctl`, `interweave-human` and `claude-channel` reports the workspace version with the commit id as build metadata. Each landed with a test that fails when its value and the workspace's differ, all of them on `main` by 2026-10-24 (the workspace version and the tag check #394, `transport-daemon`'s and `transportctl`'s `--version` and the APK rule #386, the plugin manifest and `claude-channel`'s `--version` #398, `versionName` from the workspace and `interweave-human`'s `--version` #404, the archive script's grammar #402), and the owner cut the first tag, `v0.1.0`, on 2026-10-25 (A 2026-10-25); its run's outcome and what the release page carries are plan §22's record, not this one's.

## Revisit conditions

The owner declaring the public API stable (`1.0.0`); a second organisation deploying InterWeave, which turns decision 2's "previous version" into a population; a store distribution (ADR-0057's revisit), whose own version rules would be read against decision 5.
