# ADR-0041 — amendment history

### Amendment 2026-10-10 — The person's stay-reachable choice is a persisted overlay in the state directory; config.yaml stays the authored default

**Trigger.** Stage 17 steps 2–4 (rust-ui-dev's `feat/android-app-shell`): the Service reads `runtime.android.availability_mode` at start, and the person's switch had three candidate homes — rewriting `config.yaml`, a platform preference with the profile field as its first value, or an overlay as trust has (rust-ui-dev's question of 2026-10-10).

**Ruled.** The overlay, for the reason trust got one (ADR-0028 A 2026-10-07): the daemon and the host never rewrite an authored file, and a platform preference beside a profile field is two sources that disagree exactly where this record's "explicit user opt-in" must be provable. `config.yaml`'s field stays the authored default (foreground-only when absent); the person's act writes an overlay entry in the profile's state directory under the trust boundary, owner-only, the profile's state under ADR-0044; one write path — the embedded host's API on the lifecycle seam, which an administrative IPC method would call if a desktop surface ever had the mode (none does, so no method and no minor now); one effective reading in `profile-config` (overlay, else config) that the Service's start decision, `background_restart_requires_user_authentication` and the diagnostic all use; off removes the entry, absence being the default; the host signals a change and the Service restarts in the new mode. Built (p2p-network-dev-01's `feat/android-runtime-side`, a3e2e27b and b5222406, InterWeave #254): the overlay is `<state>/availability-overlay.json`, owner-only (0600), holding exactly `{"availability_mode": "stay-reachable"}` — off removes the file, and `foreground-only` is not a value it can hold — read through the one private reader `profile-config` shares with `trust-overlay.json`; a present overlay that cannot be trusted (not private, or not that shape) refuses `EmbeddedHost::start`, as the trust overlay's does, the refusal naming "the availability overlay" and the cause, since read as absent it would revoke the person's opt-in without their knowing; the change signal is `interweave_transport_embedded::Ended::AvailabilityChanged(mode)` from `EmbeddedHost::wait_shutdown_requested`, fired when the effective mode differs from the one the host started in; `AndroidRuntimeConfig::background_restart_requires_user_authentication` takes the effective mode as its argument.

**Not ruled.** A profile that forbids persistent reachability (the config field as a ceiling an operator sets): today it is a default. Raised when a deployment needs it.

### Amendment 2026-10-10 — Network access is a runtime permission on API 37+: the Activity asks before binding, the denied state opens the store without a network, a reachable Service posts one notification and ends

**Trigger.** rust-ui-dev measured on the Pixel 9a (API 37, j59) that `android.permission.INTERNET` is `prot=dangerous`: a fresh install does not hold it, `EmbeddedHost::start` fails with `EPERM`, and with `pm grant` it starts; `ACCESS_LOCAL_NETWORK` is runtime too. The shell bound the Service on first launch, so the start failed before any dialog, and the window said the app would connect when the service started — which it never would (01a12704). human-client-android.md had no permission journey.

**Ruled.** The journey as rust-ui-dev proposed it, with the three product answers: (1) with network denied the window opens the STORE without a network — the Service starts in a network-denied posture, store and view hub open, no runtime, no lease, not a foreground service — because the person's own kept and unread messages are theirs to read without a network; the store is NOT opened read-only (the supply's review: ADR-0044's read deletes the unread row unless kept, so reading and Keep are local writes that must work), nothing sends or joins, and Service ownership stays one Service (it owns a store and no runtime in that posture); (2) a stay-reachable Service restarted without the permission posts ONE notification (network access is off) and ends, never silently and never in a loop, since the person opted into reachability and the notification is the honest signal; (3) the journey lives in human-client-android.md as its own section, which the client builds to. The state is the ui-model's `network_denied`; its words are language-culture-en's. p2p-network-dev's `EmbeddedRefused::NetworkDenied` is the runtime's half, planned (today the `EPERM` surfaces as `Internal`). Steps 4 and 5's platform behaviour (process death on revoke; the `START_STICKY` restart) is expected and listed in the acceptance matrix to verify on the device; stay reachable requires `POST_NOTIFICATIONS`, since its one notification is the honest signal.

### Amendment 2026-10-19 — Play's remoteMessaging use case is narrower than the platform's; the Play-policy condition is met at the Stage 19 submission, specialUse the fallback

**Trigger.** rust-ui-dev-01, building §20 step 10's store-listing check (OBSERVATION `01a1527e-2ff3-769f-ad19-05e8fdb49036`), read Play's foreground-service page (Play Console Help answer 13392821) and the platform's "Foreground service types" page (last updated 2026-10-16) on 2026-10-19. The platform defines `remoteMessaging` as "Transfer text messages from one device to another. Assists with continuity of a user's messaging tasks when they switch devices." Play's row for `TYPE_REMOTE_MESSAGING` reads "Relay text communication to another device" with the example of a web client paired by QR code, and its demo video must show the person initiating a transfer between the phone and an external client. InterWeave's service keeps the person reachable for OTHER peers' messages while backgrounded; it does not relay the person's own messages between their own devices. The manifest on `main` (e254aaba) declares `remoteMessaging` and `FOREGROUND_SERVICE_REMOTE_MESSAGING` at targetSdk 36; Play's use-case list is stated non-exhaustive and a hand-entered use case is allowed. Both pages were re-read by the records' holder the same day and the quotations hold.

**Ruled.** The category stands: the platform's definition fits a serverless messenger (a text message IS transferred from one device, the peer's, to another, this phone, and the service is what receives it), and the gap is in the second sentence of the platform's definition and in Play's example alike — both describe the person's own cross-device continuity — not in the type's first sentence, which is the category's name. The declaration therefore states the use case by hand and honestly — reachability for peers' text messages with no server, deferral meaning unreachable — and the record's "Play-policy validation" is read as what it can only be: Play's acceptance of that declaration, which happens at the store submission in Stage 19 (§22), not in Stage 17. Step 10 quotes both texts with the date read and records the gap; it records the target-SDK half of SPIKE-008's P1 as closed by step 3's device run and leaves the Play half open by name, so the plan's step 10 wording changes from "closing" to "stating" the condition. No build claims Play-store background reachability before acceptance; sideloaded and other-store builds never depended on it. The fallback if Play refuses is `specialUse` with its `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explanation (Play: "in limited scenarios, if your use case meets the other characteristics required for foreground service usage"), a manifest and declaration change the architecture does not see; this record's revisit condition "Play policy disallows the selected service category" fires only if Play refuses both.

**The duration criterion (same day, rust-ui-dev-01's OBSERVATION `01a15283-5324-7b88-ba79-f6f57f74e6f2`).** Play's Device and Network Abuse policy (answer 13315670, read 2026-10-19 by both) allows an FGS permission only if the use, among four other criteria, "runs only for as long as necessary to complete the task", and its Do/Don't table repeats it. Stay reachable has no task end but the person's. Ruled into this amendment rather than left to the check: the declaration states the task as it is — reachable for as long as the person keeps the switch on, ended by them, by the app's stop or by the OS — since an open-ended, person-ended task is what serverless reachability is and no shorter statement would be true; the criterion binds `specialUse` equally, so the fallback is for the TYPE question only and does not escape it. It is the likeliest ground for a refusal, and is named as such in the store check.

**Not ruled.** The wording of the Play declaration and the demo video: rust-ui-dev's and language-culture's, in the Stage 19 store listing. Whether a Play reviewer accepts a hand-entered use case for a P2P messenger: unknowable before submission, which is why the condition is left open rather than declared met.

### Amendment 2026-10-19 — The Play-policy half is withdrawn: F-Droid only, no Google Play services (ADR-0056)

**Trigger.** The owner, 2026-10-19, after the first amendment of the day had worked out a Play declaration: "Interweave will go only on f-droid phone and must not use google play services." ADR-0056 records the distribution decision.

**Ruled.** The `remoteMessaging` condition of this record is the target-SDK half alone, closed by plan §20 step 3's first instrumented run on an API 34+ device; the type stays on the platform's definition and Android's own enforcement. No Play declaration is written, no Play review is awaited, and `specialUse` is no longer a fallback for a store's refusal. The first amendment's quotations and reasoning stay in this history as what was established about Play's texts on that day, since they were read and the gap in them is real; they bind nothing. The revisit trigger that read "Play refuses both" now reads "Android's platform rules disallow the type for this use". Plan §20 step 10 becomes F-Droid metadata and the inclusion-policy check (ADR-0056 decision 5); human-client-android.md and human-client-packaging.md §6 inherit the wording.

**Not ruled.** Whether the project's own release page offers the APK F-Droid built (§22's); the F-Droid recipe's toolchain pin (Stage 19's, with devex-tooling). (Both moot since ADR-0057 the same day: no store, the release page is the distribution.)

### Amendment 2026-10-21 — One embedded runtime per active identity in the one service; stay-reachable per identity, a change restarting that identity's runtime alone

ADR-0061 (the owner's direction of 2026-10-21 that a person holds
several network identities) has the Android app host one embedded
`TransportRuntime` per identity the person has set active, inside the
one foreground service this record chose, each with its own `human`
EndpointId lease, listeners, custody and network-change handling, under
one persistent notification naming the active identities. Two sentences
of this record read as one runtime: "the service owns the `human`
EndpointId lease while active" (one lease per active identity now) and,
from A 2026-10-10, "a change while running restarts the service in the
new mode" — which, read with several runtimes, would restart every
identity's runtime for one identity's choice. Ruled with ADR-0061: the
stay-reachable overlay is per identity (its file under that identity's
profile state directory, as before), a change restarts that identity's
runtime alone, and the service's own lifecycle follows the most
reachable mode any active identity holds. The bound on active
identities and the measurement of several runtimes in one service are
ADR-0061 decision 2's and SPIKE-012's; the raised finding was #335's
blind review's F7.
