# Android human client embeds TransportRuntime in a foreground service

**Status:** Accepted; platform-specific amendment to ADR-0015/0032/0037

## Context

The desktop standalone-daemon model maps poorly to Android background/process rules. Android nevertheless needs the same PeerId/EndpointId/network semantics and, when the user asks to remain reachable, a user-visible lifecycle owner independent of the Activity window.

## Decision

The Android first-party app embeds the Rust `TransportRuntime` inside an Android foreground service host rather than launching a standalone daemon or exposing local TCP/UDS IPC. The UI talks to the runtime through the neutral `LOCAL-CLIENT` in-process adapter. The service owns one endpoint lease per user identity the person holds while active, in its one embedded runtime (A 2026-10-21, ADR-0061: a user identity is an EndpointId with its card, several under the node's one PeerId; the `human` lease of the first reading is the first identity's).

Continuous background reachability is explicit user opt-in and uses the current Android `remoteMessaging` foreground-service category subject to SPIKE-008 target-SDK/Play-policy validation. **The Play-policy half of that condition is withdrawn (A 2026-10-19, the Play half withdrawn; ADR-0056, superseded by ADR-0057: no store, no Google Play services):** the condition is the target-SDK half alone, closed by plan §20 step 3's first instrumented run on an API 34+ device; the type stays on the platform's definition ("Transfer text messages from one device to another", read 2026-10-19) and Android's own enforcement of foreground-service types and permissions; no store declaration is written and no store review is awaited. What was worked out for a Play submission earlier the same day — the hand-entered use case, the person-ended task against Play's "as long as necessary" criterion, `specialUse` as the fallback — is history (history/0041-amendments.md, A 2026-10-19), not a rule. Foreground-only mode is supported. On API 37+ `INTERNET` is a runtime permission (A 2026-10-10): the Activity asks for network access before it binds the Service, a denial opens the store without a network in a Service that runs no runtime and holds no lease (reading, Keep and Unkeep work as ADR-0044 defines; nothing sends or joins), and a stay-reachable Service restarted without the permission posts one notification and ends (`human-client-android.md` §Runtime permissions). Where the opt-in LIVES (A 2026-10-10): `runtime.android.availability_mode` in the profile's `config.yaml` is the authored default, never rewritten by the host or the runtime; the person's choice is a persisted overlay in the profile's state directory under the trust boundary (the trust overlay's sibling, ADR-0028), written through one embedded-host call on the lifecycle seam, read as one effective mode (overlay, else config) by everything derived from it; turning it off removes the entry; a change while running restarts the service in the new mode. No centralized push wake-up dependency is added. `stay-reachable` may be combined with `user-presence` key unlock, but that combination must expose `background_restart_requires_user_authentication=true` and must not claim automatic reachability after process/service restart. **The diagnostic reads the policy IN FORCE, never the configured one (A 2026-11-05):** its inputs are the effective availability mode and the authenticated policy byte of the record on disk when the start's custody step ends — the record the reseal wrote when it wrote one (a success, `OldKeyRemains`, and `Storage(Unsynced)`, each reported after the new record replaced the old), else the record the start opened; the policy ADR-0042 makes authoritative for opening, and the one the next open will be judged under — and the configured `key_unlock_policy` is not among them. So a successful policy change is in force from the start that made it; under `Unsynced`, as under `OldKeyRemains`, the diagnostic reads the new record while the other policy's key remains after the write, so the pending change stays shown by name (ADR-0042 A 2026-11-05's second clause) until a later reseal retires that key — and since the rename may not survive a crash, a start that finds the old record back reads that record. When the start has not opened the record — the unlock answered `UserNotAuthenticated` and the person is offline until they unlock — the policy in force is the policy byte the record's header carries, which the custody path parses before any cipher call; it is authenticated only by the open, so until then it is a reading, and a byte forged to the other policy misreports a restart that the record would then refuse to open anyway (ADR-0042: both refusals tested), while a `UserNotAuthenticated` refusal is answered by the user-presence key alone, so in the locked state the two readings agree. The two policies differ while a reseal is pending (ADR-0042 A 2026-11-05), and a diagnostic read from the configured policy then says the opposite of what a restart does: it claims the screen lock is needed while the record still opens without it, and is silent while it is needed. The configured policy reaches the status model only as the pending change, shown by name beside the diagnostic with the refusal's reason; when the reseal has succeeded the two agree and the diagnostic reads as before. No retry control is offered for a pending reseal: every start retries it; the reseal runs before the host takes the profile lock, so a retry while the host runs would be a restart of the service, which under `user-presence` costs the person an Unlock prompt; and the one class a person can act on, a refused write, is retried by the start that follows the freed space. When the app gains a control for the unlock policy, that control's own apply is the retry.

## Alternatives considered

Standalone daemon process; loopback TCP daemon; Kotlin/JVM networking implementation; WorkManager as permanent socket owner; FCM-backed wakeup; make Android foreground-only.

## Consequences

Network protocols remain identical to desktop, but the local process boundary differs. Activity recreation does not imply transport restart while the service lives. Service/process loss makes the endpoint offline; no mailbox appears.

## Security implications

Android in-process data/admin separation prevents confused-deputy wiring but cannot sandbox arbitrary code execution within the same APK process. Remote event handlers are constructed without admin capability. OS service state and notification interactions are local platform events, not network authority.

## Operational implications

A persistent notification is visible while stay-reachable mode runs. Android/OEM/background policy may still stop the process; the product must present availability honestly.

## Implementation implications

Build a Rust Android runtime adapter plus minimal platform glue for Service/notification/network callbacks. Do not reuse desktop socket keepalive inside the process; service/session lifetime revokes leases directly.

## Revisit conditions

Revisit if Android adds a better first-class persistent P2P/messaging execution primitive, Android's platform rules disallow the `remoteMessaging` type for this use (A 2026-10-19, the Play half withdrawn; a store's policy is no longer a trigger, ADR-0056), or process isolation becomes necessary enough to justify an Android Binder/service-process architecture.
