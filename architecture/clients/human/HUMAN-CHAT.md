# HumanChatV2 application envelope

Status: **first-party application protocol design; not part of transport v2**. Supersedes the HumanChatV1 envelope **before any implementation exists** (ADR-0050); the v1 media type is not implemented and is not a compatibility alias.

The prose here is normative for **behaviour**. The envelope is also defined as JSON Schema at [`../../contracts/schemas/human-chat/`](../../contracts/schemas/human-chat/) — normative for **shape** (ADR-0049). That schema is deliberately OPEN: unknown fields are ignored for forward compatibility within v2, so closing it would break the property this version number exists to provide.

The desktop and Android human clients and the Claude bridge need an interoperable message envelope while the generic transport remains payload-agnostic. V2 makes the text markdown — the same source serves a human renderer and a model context — and adds a bounded compression fallback so document-sized messages fit the transport payload ceiling.

## Media type

```text
application/vnd.interweave-human-chat+json;v=2
application/vnd.interweave-human-chat+json;v=2;ce=br
```

The first form is the raw UTF-8 JSON envelope. The second is the **same envelope, whole, brotli-compressed** (RFC 7932); `ce=br` is the only defined value and any other `ce` parameter value is malformed. There is no reliable content sniff for brotli, so the parameter is load-bearing: a receiver selects the decode path from the media type, and a payload that fails that path is malformed.

## Envelope

Conceptual canonical fields:

```text
{
  "v": 2,
  "kind": "text",
  "app_message_id": "<32 lowercase hex chars = 16 bytes>",
  "text": "<UTF-8 markdown>",
  "reply_to": "<app_message_id>?",
  "sent_at_ms": <diagnostic integer?>,
  "from_endpoint": "<EndpointId>?"
}
```

Rules:

- UTF-8 JSON, bounded so the encoded payload — after compression when compression is used — remains <= the transport effective payload limit;
- `v`, `kind` and `app_message_id` are required in every envelope; `kind` is `text` (the envelope above, where `text` is required too) or `contact_card` (§Contact card, A 2026-10-21, ADR-0059), and an envelope of any other kind is malformed — rejected locally, with no network effect, as a wrong `v` is. For `kind: text`, `text` is required and every other field is optional and marked `?` above. `text` may be the empty string — the field's presence is required, its length is not bounded from below, and absence is malformed while emptiness is not;
- `app_message_id` is exactly 16 CSPRNG-generated bytes encoded as **32 lowercase hexadecimal ASCII characters** (`^[0-9a-f]{32}$`); uppercase, prefixes, separators, other lengths and non-canonical encodings are invalid. It is application reply/retention identity, not DirectMessageV2 dedup identity;
- `reply_to`, when present, uses the same canonical 32-lowercase-hex grammar. The referenced message does **not** need to exist locally; an unknown reference does not reject the envelope or trigger network lookup, and the UI may render a neutral placeholder (its wording language-culture's, in the client's label table);
- `sent_at_ms`, when present, is an integer Unix-epoch millisecond value in `0..253402300799999` (through `9999-12-31T23:59:59.999Z`). Values outside that closed interval are malformed. An in-range value is display/diagnostic only and never trust/replay/freshness/order authority; receivers may suppress or annotate implausible display times without changing transport/application acceptance;
- direct transport metadata is authoritative for `source_peer` and peer-asserted `source_endpoint`; any conflicting application `from_endpoint` is ignored for routing/authority;
- on broadcast, `from_endpoint` is an explicitly **unauthenticated display hint** because transport broadcast origin is PeerId-only;
- unknown fields are ignored for forward compatibility within v2 bounds;
- **a member name that appears more than once in any object makes the envelope malformed**, including inside a field this version does not model. JSON permits the duplicate and does not say which copy wins; implementations take the first, the last, or refuse. A sender controls both copies, so any rule that picks one lets the same bytes mean different things to a person's client and to whatever logs, filters or bridges them — and an ambiguity parked inside an ignored field is ambiguous for the later version that reads it, whose only chance to refuse it was this one. Refusal is the only rule under which every reader agrees. JSON Schema validates a parsed document and cannot express this, so it is stated here and enforced by the decoder;
- attachments, edits, reactions, typing indicators, delivery/read receipts, and multi-device sync are not part of HumanChatV2.

A later richer chat protocol can version independently of transport.

## Text is markdown

`text` is **CommonMark 0.31.2**, plus exactly two extensions taken from the GitHub Flavored Markdown specification, version **0.29-gfm**: its `table` and `strikethrough` grammars. Nothing else from GFM is included — task lists, autolinks, and footnotes are outside the subset and render as literal text.

Both the core version and the extension grammars are pinned deliberately. CommonMark is versioned, and tables and strikethrough are not part of it; implementations disagree about whether a given source is a table, a strikethrough, a link destination, or literal text. That disagreement happens *before* the rules below can be applied to the parse, so naming the dialect is a prerequisite for the security bounds, not documentation polish.

The subset is not extensible within v2: a construct outside it renders as plain text, never as active content.

- **Raw HTML is never parsed or rendered as HTML.** Inline or block HTML is displayed as literal text.
- **Link schemes are allowlisted**: `https` and `mailto`. A link in any other scheme (including `javascript:`, `file:`, `data:`) renders inert as plain text.
- **Referenced remote images are never fetched automatically.** A human client renders an explicit user-triggered placeholder; an agent-facing consumer treats the reference as inert data. Fetching on receipt would leak IP, presence, and read timing to a third party and silently defeat the ADR-0044 read-state model.
- **Bounds**: block nesting and inline nesting each at most **16** levels deep, counted separately — a block level is one blockquote or one list, a list and its items counting as one (clarified 2026-10-01, plan §17); an inline level is one emphasis, strong, strikethrough, link (autolinks included) or image, nested inside another, the innermost counted (A 2026-10-01: the inline bound was unstated, and a `**` run up to the 196,608-byte ceiling built a tree ~49,000 levels deep — nested `![`, ~32,000 — whose drop overflowed a 2 MiB thread stack and aborted the process; a peer's message must never do that, so the bound is the contract's, not a renderer's); tables at most **256 body rows** (the header row excluded) and **32 columns**. Input beyond a bound is malformed markdown for rendering purposes and falls back to plain-text display of the source; it does not reject the envelope.
- **Render cost must stay linear** in input size; a renderer must not superlinearly amplify pathological input.
- **The raw markdown source is always available** to the receiving user, independent of how it rendered.

Plain-text rendering of the source is legal degradation for a minimal client. No capability negotiation or fallback field exists.

Remote content cannot trigger trust/config changes, commands, link opening, downloads, recovery operations, or admin actions — rendering inside the subset does not weaken the ADR-0032 boundary.

## Contact card

A `contact_card` envelope (A 2026-10-21, ADR-0059) is the sender's own card — what they say their name is — sent to one counterparty on the person's explicit action, and bound at the receiver to the authenticated `source_peer` of the direct message it arrived in. It names nobody but the sender and carries no identifier a person chose: its identity is the authenticated `source_peer` and, since ADR-0063, the identity key it carries and is signed by.

```text
{
  "v": 2,
  "kind": "contact_card",
  "app_message_id": "<32 lowercase hex chars = 16 bytes>",
  "card": {
    "name": "<UTF-8>",
    "surname": "<UTF-8>?",
    "photo": { "media_type": "image/png" | "image/jpeg", "data": "<base64>" }?,
    "identity_key": "<base64 of 32 bytes, Ed25519 public key>",
    "signature": "<base64 of 64 bytes, Ed25519 over the canonical card bytes>"
  },
  "sent_at_ms": <diagnostic integer?>,
  "from_endpoint": "<EndpointId>?"
}
```

Rules:

- `card`, `card.name`, `card.identity_key` and `card.signature` are required; `text` is absent (present, the envelope is malformed: a card is not a message with a caption), and so is `reply_to` (present, malformed: a card answers nothing). `sent_at_ms` and `from_endpoint` keep their `kind: text` semantics. Unknown members inside `card` are ignored like unknown envelope fields, the identifier-looking ones included: the card binds to the direct message's `source_peer` and, of what it says about itself, to its identity key alone (ADR-0063), whose signature the receiver verifies.
- `name` and `surname` are each 1 to **64** Unicode scalar values after NFC normalisation, with no control character (`Cc`), no format character (`Cf`) and no line or paragraph separator; outside that, malformed. They are displayed as plain text, never as markdown.
- `photo.data` is RFC 4648 §4 standard base64, padded, with no whitespace and no other alphabet; anything else is malformed. The photo carries pixels and nothing else (A 2026-10-21, ADR-0059 decision 5): the sender re-encodes it and strips every metadata block — EXIF, XMP, GPS, embedded thumbnails, the file name — before it enters the card; a receiver treats any metadata that arrives as absent and shows none of it. `photo`, when present, is **at most 24,576 bytes decoded** (so that the card, base64 and envelope included — at most about 34.8 KB — fits the 49,152-byte hard payload ceiling raw), of media type `image/png` or `image/jpeg` and nothing else, and decodes to **at most 256 × 256 pixels**. A card over the byte bound or with another media type is malformed; a photo that fails to decode, or decodes larger than the pixel bound, is discarded by the receiver and the card is kept without it. A receiver decodes a photo only after the person accepts the card (ADR-0059 decision 5), with a memory-safe decoder, and never fetches anything for a card.
- `identity_key` and `signature` are required (A 2026-10-21, ADR-0063): the key is the sending identity's 32-byte Ed25519 public key, the signature its 64-byte Ed25519 signature over the canonical card bytes, defined here and nowhere else: the ASCII bytes `interweave-card-v1` (18 bytes, no length prefix), then six fields each as `u16be(len) || bytes` in this order (the identity key itself is not among them: the signature is verified under it, which binds it) — `name` and `surname` as UTF-8 after NFC normalisation (the form the bounds are checked in; the receiver normalises before it verifies), `surname` absent as length 0; `photo.media_type` as ASCII, absent as length 0; the SHA-256 of the decoded photo bytes (length 32), absent as length 0; the sender's PeerId as its multihash bytes; the `source_endpoint` as UTF-8 — the receiver taking the last two from the connection the card arrived on, never from the envelope; both members are RFC 4648 §4 standard base64, padded, no whitespace, no other alphabet, as `photo.data`; verification is strict as `ed25519-dalek`'s `verify_strict` defines it — a small-order public key and a small-order R are refused by its checks, a non-canonical S by its scalar decoding, which the parser's build keeps canonical (the crate's `legacy_compatibility` feature off in its graph), and a non-canonical public-key encoding is refused in effect: one that decodes to a small-order point by the check, any other by failing verification (the small-order-key vector is frozen on #343; the small-order-R and non-canonical-S ones are in the fixture list below and land with plan §29 step 1's parser; the non-canonical key has no vector of its own) — and a key that is not 32 bytes decoded, a signature that is not 64, or one that fails to verify, is malformed (one fixed reason each); the card stays bound to `source_peer`, and the key is what it additionally proves; the key is recorded with the route and a changed key on a known route is a proposal the person decides (`human-client-ui.md` §3);
- a card received over broadcast is ignored, not malformed: the publisher is authenticated but broadcast is not the channel a card is sent on (ADR-0059 decision 2).
- a received card is inbound content under RETENTION.md until the person acts on it — unread until shown, gone at process exit once shown and not accepted — and is written to the contact store only on their acceptance (ADR-0059 decision 3); it has no Keep: Accept is its only durable outcome, and RETENTION.md's Keep rule carves it out (A 2026-10-21). A card changes no trust and no route policy.
- the kind is on the wire from plan §29 step 1, which lands the parser's acceptance; the frozen card vectors are frozen on #343 ahead of the parser (`fixtures/human-chat-v2/human-chat-v2-contact-card.json`, recomputed by `verify_fixture_vectors.py` once it lands), so step 1's parser is held to them from its first commit; until then every current client rejects a card as an unknown kind, locally and silently, and no client sends one.
- compression (§Compression) applies to a card as to any envelope, and a compressed one is accepted under the same ceilings; an already-compressed image gains little from it, so under a profile whose configured `max_payload_bytes` (TRANSPORT.md; its range is `config.schema.yaml`'s) is below the card, the sending client offers to send the card without its photo, and a card that still does not fit is too large under §Compression's rule, refused before any send.

## Compression

Compression is a **fit fallback, never a default** (ADR-0050):

- the sender MUST send the raw form whenever the encoded envelope fits the effective transport payload limit (`max_payload_bytes`);
- only when the raw encoded envelope exceeds that limit MAY the sender send the whole envelope brotli-compressed as `;ce=br`;
- if the compressed form still exceeds the limit, the message is too large: no chunking, no multi-message reassembly, no automatic downgrade;
- **a raw envelope larger than the 196,608-byte decompressed ceiling below is too large before compression is considered.** Compressibility does not extend the ceiling: a repetitive 300 KB document compresses well under the payload limit, but every conforming receiver aborts it mid-decode, so sending it would be conforming and universally unacceptable at once. The legal range for compression is `max_payload_bytes < raw <= 196,608`;
- receivers accept both forms regardless of size; the constraint binds the sender.

Receiving `;ce=br`:

- stream-decode under a hard decompressed ceiling of **196,608 bytes** (4 × the 49,152-byte transport payload ceiling, set by ADR-0050), aborting mid-stream as soon as the output would exceed the cap — exactly 196,608 bytes decode, the next one does not;
- there is deliberately **no declared uncompressed-length field** — a declared length would be peer-asserted metadata the cap must override anyway;
- the decompressed bytes must be a valid raw-form envelope; all envelope validation runs on the decompressed bytes.

Decompression happens **above transport, once**, in the shared application-protocol library used by the desktop client, the Android client, and the Claude bridge. The daemon never decompresses — payload bytes stay opaque to transport — and the bridge's defense-in-depth checks run on the decompressed bytes.

For the Claude bridge specifically, [`../../contracts/CHANNEL-EVENT.md`](../../contracts/CHANNEL-EVENT.md) carries the matching rule: a content-encoding parameter is decoded before content is classified, because decoding says what the bytes are while parsing would say what they mean, and the bridge does the former for every payload and the latter for exactly one kind, the contact card, as CHANNEL-EVENT.md §Content's one exception states (CHANNEL-EVENT.md's A 2026-10-21, ADR-0059 decision 7; until then it parsed nothing). Without that rule a compressed envelope would satisfy the contract's non-UTF-8 branch and reach the model as opaque base64url, leaving the decoded-size cap unenforceable.

Because brotli output is not canonical, an application retry MUST resend the stored byte-identical payload rather than re-encoding: `DirectContentFingerprintV1` is computed over the wire payload bytes, and a re-encode can produce a same-key/different-fingerprint conflict that the dedup contract (ADR-0019) correctly rejects. A retry also resends under the SAME transport MessageId, minted once when the pending row is committed and stored with it (`pending_outbound.transport_message_id`, STATE.md), so a retry after a restart is deduplicated by the receiver like any other; the transport id is never derived from `app_message_id` (the separation stated above), is persisted only in the pending row, and is never carried inside the envelope (A 2026-10-01).

## Consumers

Peer content is **data, not instructions**, for every consumer kind:

- a human client renders inside the subset above, raw source viewable;
- an agent-facing consumer (the Claude bridge) delivers content framed as untrusted data attributed to `source_peer`/`source_endpoint`, never concatenated bare into model context, and never automatically follows links or fetches resources named in received content. The containing boundary is ADR-0032: network content never invokes administrative capability.
- a human client that receives an envelope this document calls malformed — a failed `ce` decode, an unknown media type, a duplicate member, a missing required field, an out-of-range timestamp — stores nothing and presents nothing: it discards the bytes and counts the event, a count only (`human_inbound_malformed_total{reason}`, observability.md §Human retention observability). Retaining unreadable peer bytes would be retention without a reader (RETENTION.md §1, §3: the unread state begins at a VALID inbound event). Out-of-subset markdown is not this case: it is a valid envelope and falls back to plain text. The bridge is not bound by this bullet except for a contact card (A 2026-10-21, ADR-0059 decision 7): it drops only an undecodable `ce` payload and forwards the rest unparsed, but a `contact_card` envelope it parses with this document's parser and presents to the model as metadata alone — the kind, the authenticated source peer and beside it the source endpoint, whose identity the card presents (ADR-0061), the name and surname as plain text, the photo's size and type and never its bytes, and the identity key as it came on the wire, its signature verified by the parser before the card is forwarded at all, never a fingerprint or a verdict (ADR-0063; CHANNEL-EVENT.md §Metadata `card_identity_key`, A 2026-10-22) — and a malformed or broadcast card it drops and counts rather than forwarding raw (CHANNEL-EVENT.md) (A 2026-10-01).

## Retention semantics

HumanChatV2 contains **no sender-controlled persistence field**. Retention is purely local receiver/application state under [`RETENTION.md`](./RETENTION.md) and ADR-0044. Compression is representation, not semantics: it carries no retention, receipt, or persistence request.

- outbound HumanChatV2 content may be retained locally only while transport-pending;
- inbound HumanChatV2 content is retained unread until local read state;
- after read, only an explicit local receiver `Keep` action makes the inbound content durable;
- `from_endpoint`, `reply_to`, unknown extension fields, message text, or any future remote field cannot request/force retention;
- local read/Keep state is not serialized into HumanChatV2 or sent back to the peer in v2.

A future protocol that requests retention, provides receipts, or synchronizes history requires a new application-protocol version/ADR rather than an ignored v2 extension convention.

## Fixture cases

Phase-1/application fixtures include at least:

- valid ID: `00000000000000000000000000000000`;
- invalid IDs: uppercase hex, 31/33 characters, `0x` prefix, hyphenated UUID form and non-hex text;
- valid diagnostic timestamps `0` and `253402300799999`; values outside that closed interval are rejected as malformed HumanChatV2 metadata;
- `reply_to=11111111111111111111111111111111` with no matching local message remains a valid inbound message and renders without lookup/rejection;
- markdown subset: raw HTML displayed literally; a `javascript:` link rendered inert; a remote image reference producing no fetch; block nesting depth 17, inline nesting depth 17 and a 33-column table falling back to plain-text display without envelope rejection;
- sender-side sizing: a raw envelope over 196,608 bytes is rejected as too large even when it compresses under the payload limit;
- contact card (A 2026-10-21, ADR-0059): a valid card with name, surname and a photo at the bounds, accepted and bound to the source peer, presenting the identity of its source endpoint (ADR-0061), its signature verifying under the frozen test-only identity key over the canonical bytes with the fixture's PeerId and endpoint (ADR-0063; the vector carries the key pair, labelled test-only, recomputed by `verify_fixture_vectors.py`); a card whose signature was made for another PeerId, malformed; a card with a 31-byte key, malformed; a card with its name changed after signing, malformed; a card whose name arrives in a non-NFC form and verifies after normalisation, accepted; a card signed under a small-order public key, malformed; a card whose signature carries a small-order R, malformed, and a card whose signature carries a non-canonical S, malformed — each over the valid card's canonical bytes under its test-only key pair and built so that a verifier lacking the check accepts it, so the case's test then fails: the R vector has R the identity point's encoding and S recomputed as H(R‖A‖M)·a mod ℓ, a the secret scalar (the clamped first half of the seed's SHA-512, never the seed itself) (a replaced R with the original S fails the equation under every verifier and tests nothing); the S vector is the valid signature with S replaced by S plus the group order (both land with plan §29 step 1's parser); a card whose `identity_key` is unpadded or URL-safe base64, malformed; a card with `text` or `reply_to` present, malformed; a card whose photo is over 24,576 decoded bytes or of a third media type, malformed; a card carrying an identifier-like member inside `card`, accepted with the member ignored; a card with whitespace or the URL-safe alphabet in `photo.data`, malformed; an envelope of an unknown kind, malformed; and, a sender-side case rather than a wire vector (plan §29 step 2's, not the parser's), a photo chosen with a GPS block and a camera serial leaving the sender with neither;
- compression, decode direction only: a frozen compressed vector decoding to a frozen raw envelope, and a cap-violating input whose decode MUST abort mid-stream. The encode direction is **not** fixture-testable because brotli output is non-canonical; conformance pins what a receiver must do, not which bytes an encoder must emit.
