# Android transport-key custody

Status: architecture/design only.

## Constraint

The network identity is fixed to an exact exportable 32-byte Ed25519 secret so BIP-39 entropy encoding can recover the same PeerId. Android Keystore should therefore protect the key **at rest** without changing the Ed25519/libp2p identity format.

## Selected v1 Android design

Do not generate a different Android-native signing identity. Instead:

1. generate/import the normal 32-byte Ed25519 secret under the existing identity contract;
2. generate an AES-256 wrapping key in `AndroidKeyStore`;
3. prefer hardware-backed TEE/StrongBox storage when the device supports the required AES-GCM key properties, but do not make StrongBox availability a correctness requirement;
4. encrypt the 32-byte Ed25519 secret with authenticated AES-GCM under the Keystore key;
5. persist only the versioned ciphertext/envelope and public expected PeerId in app-private storage;
6. unwrap into process memory only while the Rust transport service needs the identity;
7. zeroize best-effort temporary secret buffers after import/runtime shutdown.

**The envelope, the record and the seam (ADR-0042 A 2026-10-10; built in `crates/transport/embedded/src/custody.rs`, §20 step 6).** The ciphertext is the IWK1 v1 envelope — `IWK1 (4) | version 0x01 (1) | policy (1) | iv (12) | ciphertext (32) | tag (16)`, 66 bytes, associated data `magic | version | policy | PeerId (UTF-8)`; the header is checked in SPIKE-009's order before any cipher call and never trusted. The record is one owner-only file, `<identity dir>/identity.iwk1` = envelope `|` PeerId (UTF-8, at most 128 bytes), written with an exclusive create at provisioning under the profile lock — the lock is taken without waiting before anything seals and `ProfileLocked` is answered while another holder has it, so of racing first runs exactly one seals and its record opens; the recovery flow takes that lock itself, before the first word, and hands it to provisioning or restore (§Recovery below; a flow that holds no lock is given one by the seal, as the crate did before the handover); a second provisioning is refused, and restore is refused while a host runs the profile. The platform cipher is the `SeedCipher` seam (seal, open, retire; `Send + Sync`, calls may block) with a CLOSED failure set — `KeyInvalidated`, `KeyMissing`, `UserNotAuthenticated`, `Authentication`, `Unavailable(String)` — the Keystore implementing it in the app's platform crate; the Keystore key is one per (profile, policy), alias `interweave.iwk1.<profile>.<policy>` computed by the custody path (`KeyRef::alias`); `seal` replaces the key at its own alias and no other, and the custody path retires the profile's other-policy key only AFTER the new record is written, so a failed write leaves the record openable and a failed retire is reported (`OldKeyRemains`: the record opens, a pre-change copy may still open until the key is deleted, `reseal` retries); a restore after invalidation never reuses the invalidated key (the alias is kept; the key under it is new), a restore under the other policy retires the old record, and a record copied from another profile's directory does not unlock as that profile; restore decides whose record it is from the PeerId field alone and refuses a link as `Unreadable`, and a restore under the policy the record already has first tries that record: kept if it opens to the expected PeerId (nothing sealed; its bytes rewritten owner-only if others could read them), the seal proceeding if its key is invalidated, missing or another's, `CustodyRefused::Cipher` and no write if the key cannot be asked — a restore never seals over the key a healthy record opens under.

**Reseal and the policy byte (ADR-0042 A 2026-10-10 (ii)).** `reseal` wraps the profile's seed again under the policy the profile is configured with — the first-run path, a policy change, or a retry of a retire that failed — writing the new record before retiring the other-policy key. The record's policy byte is authenticated (it is in the associated data) and governs OPENING: unlock uses the record's policy, whatever the profile's configured `key_unlock_policy` says; when the two differ, unlock does not refuse — after a successful unlock the host reseals under the configured policy and the old record is retired through the same path. A refusal would strand a profile whose operator changed the policy; a silent read would leave the configured policy a dead letter; the reseal is the migration (built by §20 step 7's caller). A restore of a healthy user-presence record opens it first, so it needs an open authentication window or answers `CustodyRefused::Cipher(UserNotAuthenticated)` and writes nothing: step 7 prompts for authentication before the restore. Zeroizing the seed is best-effort: the plaintext lives in the Java heap as a byte array for one call, a limit, not a zeroization claim.

The Android Keystore wrapping key is non-exportable; the Ed25519 secret necessarily becomes available to the Rust process after unwrap because rust-libp2p needs the exact portable key material. Therefore this improves at-rest extraction resistance but is **not** an HSM/non-exportable Ed25519 identity claim.

## Unlock policies

Two explicit policies are supported:

### background-compatible

Keystore wrapping key does not require per-operation biometric confirmation. This allows a user-enabled foreground service to restart/unlock while Android permits it. Device/app storage and Keystore protections are the at-rest boundary.

### user-presence

Keystore unwrap requires current device credential/strong biometric authorization. If the process dies, background reachability cannot resume until the user authenticates locally, except within `USER_PRESENCE_WINDOW_S` of the last authentication (ADR-0042 A 2026-10-11). This intentionally trades availability for stronger local-use control.

The key is a timed key (ADR-0042 A 2026-10-11): `setUserAuthenticationParameters(USER_PRESENCE_WINDOW_S, AUTH_DEVICE_CREDENTIAL | AUTH_BIOMETRIC_STRONG)`, `USER_PRESENCE_WINDOW_S` = 60 s — the value SPIKE-009 exercised (D1, D4, D5); no start duration was measured — a constant the Keystore adapter names, never a setting. The window lets the key operation that follows an authentication complete (the start's unwrap, a provisioning seal, a restore, a reseal) and grants nothing else: a Keystore key is the app uid's, so no other application gains by it, and the unattended restart it admits within 60 s of an unlock is inside the diagnostic below. Outside the window the Keystore refuses (`UserNotAuthenticatedException`); the Service never prompts — the Activity shows a device-credential or Class-3 biometric prompt bound to no operation, any success opens the window, and the operation follows; denied or cancelled leaves the person offline. The per-operation mode (a `BiometricPrompt` `CryptoObject` per use) is not used.

The UI must show this tradeoff rather than silently weakening user-presence policy after a restart. The combination `availability_mode=stay-reachable` plus `key_unlock_policy=user-presence` is valid, but it has a mandatory derived diagnostic `background_restart_requires_user_authentication=true`: after process/service restart the endpoint cannot become reachable until local user authentication succeeds — an authentication within the last `USER_PRESENCE_WINDOW_S` counts (ADR-0042 A 2026-10-11). The UI must not describe that configuration as continuously reachable across restart.

## Recovery

The portable 24-word recovery phrase remains the disaster-recovery path and represents the same 32-byte secret. It is never stored by the app after display/import. Phrase display/import requires explicit local flow with the transport service stopped/profile exclusively locked — the flow takes the profile lock once, before the first word is shown or picked, and HANDS it to the seal (provision, restore) it ends in; it is never released and retaken, since the gap would let the service start the profile and refuse the seal after the person has entered all 24 words, and two first runs racing through that gap is what the lock exists to refuse; the seal BORROWS the flow's lock and never consumes it, so a refused provision or restore leaves the flow still holding it for the read-back through unlock and for a retry, and the flow releases it only when it ends (#303 rounds 2 and 5, Q9); `expected_peer_id` verification remains mandatory under ADR-0033. Where no record survives (a fresh install), the flow takes `IDENTITY-RECOVERY.md`'s phrase-only path: the derived PeerId is displayed in full and the person confirms it is the one they recorded before an empty record is initialised; the confirmed value is the expected PeerId the restore verifies against, and nothing is typed or scanned (decided 2026-10-19, §20 steps 7–8). A record that is present but names no readable PeerId is NOT "no record": it is an established profile's, whose contacts, trust and messages it still holds, so the phrase-only path is never offered over it and the custody path refuses to seal over it, writing nothing — the same fail-closed rule as a record naming another identity; recovery shows the identity as lost and names the OS clear-data route, as when the phrase is lost (decided 2026-10-19 on #303's review; the embedded crate's `restore` conforms to this, not the reverse). A record refused for its SHAPE — a damaged magic, length or mode — whose PeerId field is intact names that PeerId: the recovery flow reads it without the cipher (the custody crate's public reader of the field, whatever the envelope's state) and restores only a phrase that derives it; the cipher is never asked to decide whose record it is (#303 round 2, Q8).

### Recovery UI hardening

Android recovery screens are treated as private-key surfaces, not ordinary text forms:

- recovery runs in the app's own Activity (amended 2026-10-19: a dedicated non-exported Activity/task with `android:excludeFromRecents="true"` was the first wording and stays allowed); the window sets `FLAG_SECURE` before any phrase material can be rendered and keeps it set until a frame without phrase material has drawn, and on API 33+ `setRecentsScreenshotEnabled(false)` for the same span; no intent, extra or deep link from outside the app starts a phrase flow. The release harness must verify that phrase material never appears in screenshots, screen recording/non-secure displays, or Recents/task snapshots on supported Android versions;
- phrase import uses an **in-app BIP-39 word-list picker** for each of the 24 positions. Standard v1 does not offer a free-text 24-word field and therefore does not require a third-party IME to observe the phrase;
- if an implementation temporarily invokes an IME for word filtering/accessibility, it requests no suggestions/autocorrect and `IME_FLAG_NO_PERSONALIZED_LEARNING`, but this is defense in depth rather than a guarantee that an arbitrary IME behaves correctly;
- there is **no clipboard copy/paste path** for the full phrase or individual phrase words in standard v1, even after an explicit gesture;
- accessibility announcements, analytics, crash reports, debug logs, saved-instance state, notification text, UI test snapshots, and application telemetry must never contain phrase words. A screen reader speaking the focused word control's own label is not an announcement: it is the screen the person made secure, read aloud at their request, and without it a blind person could neither back up nor restore. No live region, announcement, hint or error text carries a word (ux-designer's Q2, 2026-10-19);
- phrase words and derived seed material are removed from the UI/view-model state immediately after successful verification/import or cancellation, subject to normal best-effort memory-zeroization limits. A stopped Activity (a phone call, a switch away) is neither: the words stay in process memory only, never in saved-instance state, and are gone on finish, cancellation, completion or process death, so an interruption does not cost the person the 24 words they were entering (ux-designer's Q1, 2026-10-19).
- the phrase is SHOWN on-device as well as imported (`human-client-ui.md` §9): at creation, before the transport service first starts, and on demand with the service stopped and the profile lock held, the words re-derived from the unwrapped seed for that screen only and subject to every rule in this list; beside the words the screen shows the PeerId they derive to, the value a later restore confirms against;
- an on-demand display is preceded by a device-credential or Class-3 biometric prompt whatever the profile's `key_unlock_policy`: under `background-compatible` the Keystore would otherwise hand the seed to whoever holds the unlocked phone, and the phrase is the whole transport identity (ADR-0033). The prompt is bound to no operation; a denied or cancelled prompt shows nothing; it is not re-asked on resume of the same Activity instance, and a new instance is a new display with its own prompt (decided 2026-10-19, §20 step 8).

Restoring a phrase on a second device is migration/disaster recovery, not permission to run the same PeerId concurrently on multiple devices.

### Android backup and device-transfer policy

Standard v1 does **not** use Android Auto Backup, cloud backup, or device-to-device transfer as an identity or human-message recovery mechanism. Packaging must set an explicit backup posture and explicit extraction rules rather than relying on platform defaults:

- the wrapped identity envelope, expected PeerId record, wrapping metadata, recovery-flow temporary state, transport configuration/trust material, and human SQLite database are excluded from both cloud backup and device-transfer extraction;
- standard-v1 packaging sets `android:allowBackup="false"` and also supplies explicit Android 12+ `android:dataExtractionRules` plus Android 11-and-lower `android:fullBackupContent` rules as defense in depth. The Android 12+ rules explicitly exclude the sensitive/human-store domains from both `cloud-backup` and `device-transfer`, because `allowBackup=false` alone is not treated as a portable guarantee that every manufacturer disables device-to-device transfer;
- restoring/reinstalling the APK without a valid local Keystore wrapping key and identity envelope never creates a partial identity restore or silently generates a replacement for an established profile; onboarding reports the profile as unconfigured/recovery-required;
- The human-store is not uploaded or transferred by Android system backup in standard v1. A future explicit encrypted application backup may include message content only from inbound unread/receiver-kept records under ADR-0044; pending outbound is excluded from portable backup. Any broader cloud backup/synchronization is a separate application feature with its own encryption, privacy, replay and threat-model ADR.

## Failure behavior

- Keystore key missing/invalidated -> fail identity unlock; do not generate a replacement silently for an established profile;
- ciphertext/authentication failure -> fail closed;
- expected PeerId mismatch after unwrap -> fail closed;
- user-presence denied/cancelled -> remain offline, with the diagnostic and the action that raises the prompt again; a launch of the app's Activity by the person is presence, so on a `user-presence` profile outside `USER_PRESENCE_WINDOW_S` the Activity raises the prompt before it binds the service (the same order the identity flows keep for their own start), and only a cancel leaves the person offline — the diagnostic alone, with no way to authenticate, is never the resting state (amended 2026-10-19). A launch is the Activity's creation — a cold start, a new instance, or the creation that follows a process the system killed, which has no live Activity — not its resumption, and not a recreation the system performs for a configuration change: a return to a live Activity from Home or Recents after a cancel raises no prompt by itself, keeps the locked notice and its Unlock action, and binds without a prompt only where the window has opened meanwhile, which the Keystore decides by admitting or refusing the unwrap — the Activity keeps no clock of the window, and every case starts with the key operation; a recreation for a configuration change continues the live Activity as a return does. ADR-0042 (A 2026-10-20) records the one case this takes out of "the Activity answers the refusal with a prompt": a refusal at a return, or at any other continuation of a live Activity, is answered by the notice and its Unlock action, which raises the operation-free prompt, while a refusal at a launch or on Unlock is answered by the prompt itself — the custody requirement is that no key operation succeeds outside the window and that an authentication is always offered, never that the person who declined is asked again each time they switch back in;
- hardware-backed capability absent -> use Android Keystore software/TEE availability per platform policy, report protection level diagnostically; do not change PeerId;
- any other platform error (`Unavailable`) -> returned to the caller for its log, decides nothing: unlock answers "try again", never recovery; the record is untouched (ADR-0042 A 2026-10-10).
