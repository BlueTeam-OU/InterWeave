## the owner's direction of 2026-10-28: a user identity IS an EndpointId derived from the identity's own key pair as the PeerId is from the node's (same algorithm, same multihash); trust is per identity (EndpointId); no installed user base, so a clean break (the fleet updated at once, ids recreated) — ADR-0067 to write after the owner confirms my reading

Owner's words, 2026-10-28: "each user identity is a endpointId and that endpointId should be derived from the endpoint keypair (same key algorithm, same hashing algorithm if used)"; "trust is per identity (endpointid)"; "we have not an installed userbase, only agent-fabric that we can manage by updating at the same time and recreating the ids". Supersedes: ENDPOINTS.md "stable while configured, but not cryptographically derived"; ADR-0061 d1/d2 (identity = configured label + card; one trust set); ADR-0063 (identity key carried by the card, label unrelated); ADR-0030 (label semantics). My reading, stated to the owner, awaiting confirmation: ADR-0067 — identity EndpointId = multihash of the identity's Ed25519 public key as PeerId is of the node's, written in lowercase multibase (base32 libp2p-key CID form) so it fits the lowercase-ASCII 1..64 grammar (PeerId's base58 form would not); a counterparty verifies card.identity_key derives the source_endpoint (no impersonation across a node's endpoints); automated-client endpoints and operator-authored routes stay labels (not identities, no card); trust per identity = each identity's own trusted set, the node's transport set their union, each endpoint narrowing to its identity's set (ENDPOINTS.md's narrowing rule); no compatibility window (the owner's word); the fleet's ids recreated at the update.

**How to apply:** write ADR-0067 as a new record (substance change), amend 0030/0061/0063 and ENDPOINTS.md, HUMAN-CHAT.md card verification, STATE.md identity-keys file naming; Stage 22 builds it.
