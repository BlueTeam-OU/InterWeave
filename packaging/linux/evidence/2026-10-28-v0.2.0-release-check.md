# Release check: v0.2.0's archive passes the control-plane cases, 2026-10-28

The acceptance architect-cto named for the fleet's control plane over
InterWeave (REQUEST 01a17c02, item 3) is a tagged release whose
`interweave-human` passes the cases of `tests/automated-client` that
prove it. This record checks the published v0.2.0 Linux archive
against the keys pinned on `main` (ADR-0066), then runs those cases
against the archive's own programs. Every statement below is either
quoted output or listed under "What this does not show".

## The cases, against the archive's programs

The test sources are the tag's: an existing worktree of this
repository, checked out detached at `v0.2.0`. The variable names the
extracted `bin/` by its absolute path, and it is set for
`tests/automated-client` alone. In `tests/desktop-e2e`,
`claude_channel.rs` and `user_units.rs` start programs the archive's
`bin/` does not hold, and `workspace_binary` refuses them while the
variable is set.

```
$ git checkout --detach v0.2.0
$ INTERWEAVE_PACKAGE_BIN=$R/interweave-0.2.0-x86_64-unknown-linux-gnu/bin \
    cargo test --locked -p interweave-automated-client-tests \
    --test control_plane --test two_hosts -- --test-threads 1
test the_carrier_and_the_control_cli_share_one_profile_and_leave_no_row ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 10.22s
test a_listener_on_the_overlay_literal_keeps_its_connection_past_the_close_window ... ok
test two_hosts_talk_over_the_overlay_and_redial_when_its_link_returns ... ok
test without_the_static_entry_the_two_hosts_never_connect ... ok
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 18.34s
```

With the variable set, the daemon, `transportctl` and `interweave-human`
come from that directory, or the case fails by name. `tests/support`'s
`package_binary` has no fallback, which
`a_named_package_without_the_program_fails_rather_than_falls_back`
pins. The two-host cases see the directory inside their namespaces,
which mount it at its own path.

## What this does not show

- Who signed the tag, and where. The quoted output shows that the
  pinned key made the signature, not whose hand or account used it.
- Who gave the `release` environment's review. The approval quoted
  above is recorded under the owner's GitHub account, which every
  agent of the fleet also acts as. This session asked the owner for
  that approval and did not give it.
- The APK. It was built, signed and published by the same run, and
  nothing here installs or runs it.
- A host other than this one, or a second machine for the two-host
  case (ADR-0055 decision 5b's limits).
- A fresh install from the archive into an empty account.
  `install.sh` was not run; the programs ran from the extracted `bin/`.
- The fabric's own carrier process. The case's carrier is the suite's
  `Client`, on the same endpoint, client kind and data socket.
