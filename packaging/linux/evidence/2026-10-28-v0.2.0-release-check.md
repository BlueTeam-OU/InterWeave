# Release check: v0.2.0's archive passes the control-plane cases, 2026-10-28

The acceptance architect-cto named for the fleet's control plane over
InterWeave (REQUEST 01a17c02, item 3): a tagged release whose
`interweave-human` passes the cases of `tests/automated-client` that
prove it. This record checks the published v0.2.0 Linux archive
against the keys pinned on `main` (ADR-0066), then runs those cases
against the archive's own programs.

- Tag: `v0.2.0`, annotated, on `32ade966` (#487's merge), signed by the
  owner in the owner's own account with the pinned tag key.
- Release run: 40568434157. Every job passed. The `release`
  environment's required review (`approved andreabenetton release`,
  the run's approvals) was given under the owner's account before the
  signing jobs ran; this session, which asked the owner for it, did
  not give it. Published 2026-10-28T07:32:22Z.
- The check ran in this account (`p2p-network-dev-01`) on
  develop-qzapp, Fedora, minisign 0.12, from the scratch directory the
  assets were downloaded to.

the tag verified with plain gpg:

```

gpg:               imported: 1
$ GNUPGHOME=<fresh> git -c gpg.program=gpg verify-tag v0.2.0
gpg:                using EDDSA key 220728A8B44731A93CFF8969FA651DF333C31A0C

$ git rev-parse v0.2.0^{commit}
32ade966cff892f124cb2adb412960e9984c7148
```

The `[unknown]` is the fresh keyring holding no trust for the key, as
it should. The user ID is still the placeholder (#487's review, F2,
the owner's to change), and the pin is the fingerprint.

## The cases, against the archive's programs

The test sources are the tag's (a worktree detached at `v0.2.0`). The
variable names the extracted archive's `bin/` by its absolute path,
and it is set for `tests/automated-client` alone: in
`tests/desktop-e2e`, `claude_channel.rs` and `user_units.rs` start
programs the archive's `bin/` does not hold, and since this record's
change `workspace_binary` refuses to start one while the variable is
set.

```
$ git checkout --detach v0.2.0
$ INTERWEAVE_PACKAGE_BIN=<extracted>/interweave-0.2.0-x86_64-unknown-linux-gnu/bin \
    cargo test --locked -p interweave-automated-client-tests \
    --test control_plane --test two_hosts -- --test-threads 1
test the_carrier_and_the_control_cli_share_one_profile_and_leave_no_row ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 10.22s
test a_listener_on_the_overlay_literal_keeps_its_connection_past_the_close_window ... ok
test two_hosts_talk_over_the_overlay_and_redial_when_its_link_returns ... ok
test without_the_static_entry_the_two_hosts_never_connect ... ok
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 18.34s
```

With the variable set, the daemon, `transportctl` and `interweave-human`
each come from that directory or the case fails by name: `tests/support`'s
`package_binary` has no fallback, pinned by
`a_named_package_without_the_program_fails_rather_than_falls_back`. The
two-host cases see the directory inside their namespaces, which mount
it at its own path.

## What this does not show

- The APK: it was built, signed and published by the same run, and
  nothing here installs or runs it.
- A host other than this one, a second machine for the two-host case
  (ADR-0055 decision 5b's limits), or a fresh install from the archive
  into an empty account (`install.sh` was not run; the programs ran
  from the extracted `bin/`).
- The fabric's own carrier process. The case's carrier is the suite's
  `Client` on the same endpoint, client kind and data socket.
