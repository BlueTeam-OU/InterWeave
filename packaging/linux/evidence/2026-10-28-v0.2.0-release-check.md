# Release check: v0.2.0's archive passes the control-plane cases, 2026-10-28

The acceptance architect-cto named for the fleet's control plane over
InterWeave (REQUEST 01a17c02, item 3) is a tagged release whose
`interweave-human` passes the cases of `tests/automated-client` that
prove it. This record checks the published v0.2.0 Linux archive
against the keys pinned on `main` (ADR-0066), then runs those cases
against the archive's own programs.

The check is the script below, run once from the top. Its trace
(`set -x`, `PS4='$ '`) follows: every command as the shell ran it, in
order, then its output. The only edit to the trace is that the
account's home directory is written `~`. The trace ends with the
script's exit status, which `echo "exit=$?"` printed after it.

- The repository it reads is a clone of this one, and `origin/main`
  there is fetched first. The key files are `main`'s copies, written by
  `git show origin/main:...`.
- The cases run from a second, clean worktree of the same repository,
  checked out detached at the tag.
- `INTERWEAVE_PACKAGE_BIN` is set for that one `cargo test` alone,
  naming the extracted archive's `bin/` by its absolute path.

## The script

```bash
#!/usr/bin/env bash
# The v0.2.0 release check, run once from the top; its trace is the record.
# Usage: release_check.sh <tag> <repository clone> <worktree for the cases>
set -euo pipefail
TAG=$1 REPO=$2 TREE=$3
PS4='$ '
set -x
whoami
hostname -s
grep -E '^(NAME|VERSION)=' /etc/os-release
minisign -v
R=$(mktemp -d)
git -C "$REPO" fetch --quiet origin
git -C "$REPO" fetch --quiet origin tag "$TAG"
git -C "$REPO" show origin/main:tools/ci/release_keys.py > "$R/release_keys.py"
git -C "$REPO" show origin/main:packaging/release-keys.toml > "$R/release-keys.toml"
RUN=$(gh run list -R BlueTeam-OU/InterWeave --workflow release.yml --branch "$TAG" --limit 1 --json databaseId -q '.[0].databaseId')
gh run view "$RUN" -R BlueTeam-OU/InterWeave --json conclusion,jobs -q '"run: \(.conclusion)", (.jobs[]|"\(.conclusion)  \(.name)")'
gh api "repos/BlueTeam-OU/InterWeave/actions/runs/$RUN/approvals" -q '.[] | "\(.state) \(.user.login) \([.environments[].name]|join(","))"'
mkdir -m 700 "$R/gnupg"
python3 "$R/release_keys.py" "$R/release-keys.toml" tag.public_key | GNUPGHOME="$R/gnupg" gpg --batch --import
GNUPGHOME="$R/gnupg" git -C "$REPO" -c gpg.program=gpg verify-tag "$TAG"
git -C "$REPO" rev-parse "$TAG^{commit}"
cd "$R"
gh release download "$TAG" -R BlueTeam-OU/InterWeave -p "interweave-${TAG#v}-x86_64-unknown-linux-gnu.tar.gz*"
A="interweave-${TAG#v}-x86_64-unknown-linux-gnu.tar.gz"
PK=$(python3 release_keys.py release-keys.toml archive.minisign_public_key)
minisign -V -P "$PK" -m "$A"
minisign -V -P "$PK" -m "$A.sha256"
sha256sum -c "$A.sha256"
cp "$A.sha256" tampered.sha256
sed -i '1s/^./0/' tampered.sha256
if minisign -V -P "$PK" -m tampered.sha256 -x "$A.sha256.minisig"; then echo "TAMPERED COPY ACCEPTED"; exit 1; fi
tar -xzf "$A"
BIN="$R/${A%.tar.gz}/bin"
"$BIN/transport-daemon" --version
"$BIN/transportctl" --version
"$BIN/interweave-human" --version
cd "$TREE"
git status --porcelain
git checkout --quiet --detach "$TAG"
git rev-parse HEAD
INTERWEAVE_PACKAGE_BIN="$BIN" cargo test --quiet --locked --ignore-rust-version -p interweave-automated-client-tests --test control_plane --test two_hosts -- --test-threads 1
```

It was run as
`release_check.sh v0.2.0 <a clone> <a clean worktree>`.

Reading it:

- `[unknown]` and gpg's "not certified" warning mean only that the
  fresh keyring holds no trust for the key. The check is the
  fingerprint the signature names, which is the pin.
- The tamper control prints `Signature verification failed`. The
  script stops with `TAMPERED COPY ACCEPTED` if that check ever passes,
  and it did not.
- The cases' harness is the tag's, `v0.2.0`: the trace's worktree is
  checked out at it. There, with `INTERWEAVE_PACKAGE_BIN` set, the
  cases start the daemon, `transportctl` and `interweave-human` from
  that directory, or fail by name. `tests/support`'s `package_binary`
  has no fallback
  (`a_named_package_without_the_program_fails_rather_than_falls_back`),
  and nothing under `tests/automated-client` calls `workspace_binary`
  (`git grep workspace_binary v0.2.0 -- tests/automated-client` finds
  nothing). The two-host cases' namespaces mount the directory at its
  own path (`an_absolute_package_directory_is_mounted_as_named`). All
  three are as of `v0.2.0`.
- `workspace_binary`'s refusal while the variable is set, and its test
  `workspace_binary_refuses_under_a_package`, came after the tag, in
  the change that adds this record. They guard later runs, not this
  one.

## What this does not show

- Who signed the tag, and where. The trace shows that the pinned key
  made the signature, not whose hand or account used it.
- Who gave the `release` environment's review. The approval is
  recorded under the owner's GitHub account, which every agent of the
  fleet also acts as. This session asked the owner for that approval
  and did not give it.
- The APK. It was built, signed and published by the same run, and
  nothing here installs or runs it.
- A host other than this one, or a second machine for the two-host
  case (ADR-0055 decision 5b's limits).
- A fresh install from the archive into an empty account.
  `install.sh` was not run; the programs ran from the extracted `bin/`.
- The fabric's own carrier process. The case's carrier is the suite's
  `Client`, on the same endpoint, client kind and data socket.
- The cases' individual names. `cargo test --quiet` prints their
  counts, one and three, and the test files at the tag hold those
  four cases.
