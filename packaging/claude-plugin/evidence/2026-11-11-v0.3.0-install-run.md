# INSTALL.md followed from the v0.3.0 release run's archive, 2026-11-11

architect-cto asked (REQUEST 01a1cb87) for `packaging/claude-plugin/INSTALL.md` to be followed as written, from the
Linux archive of release run 43022897948, before the v0.3.0 page is published, on an account with no InterWeave state.
The run covered the marketplace add, the plugin install, a session that registers the channel, and one message in and
one reply out against a second profile. This record gives each step's command and outcome, what the document says
that the archive does not do, what the archive does that the document did not say, and what was not run.

### How "an account with no InterWeave state" was stood in for

This login cannot create an account, and its own account runs the fleet's live `gzcoord` daemon and client. So
every step ran with a **scratch `HOME`** (an empty directory, mode 0700) and a **private `XDG_RUNTIME_DIR`** under
the login's own `/run/user/<uid>`. Claude Code's configuration started empty under that `HOME`, with
`~/.local/bin/claude` a link to the login's 2.1.322 binary. The environment was cleared to `HOME`, `USER`,
`LOGNAME`, `LANG`, `SHELL`, `TERM`, `PATH`, `XDG_RUNTIME_DIR` and `DISABLE_AUTOUPDATER`. Three steps could not run
as written:

- **Step 5's `systemctl --user enable --now`.** The user manager cannot read unit files under a scratch `HOME`.
  Each daemon ran instead as a transient unit of the real user manager:
  `systemd-run --user --unit=j65-interweave-daemon-<profile> -p Type=exec -p UMask=0077 --setenv=HOME=… --setenv=XDG_RUNTIME_DIR=… ~/.local/bin/transport-daemon --profile <profile>`.
  That is the template's `ExecStart` and its main properties. `journalctl --user -u` read those units.
- **Step 7 as root in the host's `/etc`.** The session ran under bubblewrap with a private `/etc`: every host entry
  bound read-only, and `/etc/claude-code` a scratch directory holding the host's own `managed-settings.json` (copied
  unchanged: `disableSideloadFlags`, the fleet's managed hooks, `pluginConfigs`) plus step 7's
  `managed-settings.d/interweave.json`, byte for byte as INSTALL.md gives it. This is the shape an administrator who
  adds the drop-in to this host would leave. It is SPIKE-001 S22's mechanism (`s22_org_channels.private_etc`).
- **Step 8's interactive session.** Not run. The session was the "Without a terminal" form.

and 3?" to the `claude` PeerId (default endpoint). The session is settled once no `init` lacks its `result`, and only
then is stdin closed. Each session reported `claude_code_version` `2.1.322`, `permissionMode` `default`, and server
`plugin:interweave:interweave` `connected`.

## What the document says that the 0.3.0 archive does not do

- **Step 4 before step 5.** Read in order, step 4's `transportctl … trust allow` comes before the daemon exists. It
  answers `transportctl: no daemon is running for profile "peer2"` with exit 3 (measured on a stopped profile). The
  step's first sentence allows either order, and its command needs the second. INSTALL.md now says so.
- **Step 8, `status` under `log`.** Inside the stand-in's bubblewrap, `status` had `log.file: null`,
  `log.file_error: directory_not_private`, and `profile_desired_channels: {"unknown":"ConfigDirUnguarded"}`. Both
  come from the stand-in, not the archive. In bubblewrap's user namespace `/` and `/home` are owned by uid 65534
  (`stat` inside and outside, recorded in the session). The same bridge binary, driven over stdio outside bubblewrap
  against the same daemon, reported `log.file` at `~/.local/state/interweave/profiles/claude/claude-channel/claude.log`,
  `level` `info`, and `profile_desired_channels: {"as_configured":[]}`. A host whose step 7 is a real root-written
  file has no such namespace. That was not measured here.

## What the archive does that the document did not say

1. **Step 4's ordering**, above.
2. **A peer must be told this profile's address, and loopback is refused.** Trust names no address. `peers add`
   with `127.0.0.1` was refused `special_use`, so on one host the profiles need the host's LAN address. INSTALL.md
   step 4 now says so.
3. **The install's notice about `log_level`.** `claude plugin install` without `--config log_level` ends `1 userConfig
   option not yet set`, and `configure` lists `log_level` as `not set`. The bridge then ran at `info` (`status` →
   `log.level: info`, both inside and outside bubblewrap). INSTALL.md step 6 now says so.
4. **A human client shows only its chat envelope, and its endpoint must be held.** Runs 1 to 3. INSTALL.md has a new
   subsection under step 8, "A peer that is a human client".
5. **`uninstall.sh` stops every profile's units of the account.** Following "Removing it" under the scratch `HOME`,
   the script fell back to `/run/user/<uid>`, the behaviour its own header describes for a shell that reaches no
   manager. It stopped and disabled every `interweave-*@` instance there, which here were this login's live
   `interweave-client@gzcoord` and `interweave-daemon@gzcoord`. They were down from 17:16:24Z to 17:16:48Z, when
   `systemctl --user enable --now` on both brought them back. The unit templates and binaries under the real home were
   untouched, because the script removes files from `HOME`. On a real account this is the script working as written.
   What INSTALL.md lacked is that it takes down every profile's daemon and client, not only `claude`'s. INSTALL.md
   "Removing it" now says so. The 24 s outage is this run's doing, not the archive's.

None of these is a defect in the archive's build, so no OBSERVATION goes to devex-tooling.
