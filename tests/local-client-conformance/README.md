# local-client-conformance

The same LocalDataSession/LocalAdminPort conformance suite runs against every platform binding: the direct in-process one (Stage 12, the Android embedded adapter's core), the desktop IPC one (Stage 13), the in-memory fake the human client is built against (Stage 14, `tests/local-client-fake`), and the embedded host the Android service runs (Stage 17, `crates/transport/embedded`).

The checks are generic functions over the neutral binding traits in `interweave-local-client-api` (`DataSessionBinding`, `DataSessionPort`, and for administration `AdminBinding`, `AdminPort`), in `src/lib.rs`, one per item of [`contracts/LOCAL-CLIENT.md`](../../architecture/contracts/LOCAL-CLIENT.md) §7. A binding passes by running each against a sender and a receiver it composed:

- `tests/in_process.rs` — the in-process binding, over two runtimes composed from profiles and connected over real sockets on the host's private address.
- `tests/over_ipc.rs` — the IPC adapter: `ipc-client` to `ipc-server` to the in-process binding (Stage 13).
- `tests/fake.rs` — the in-memory fake: the same generic functions (Stage 14, plan §17 (2)). What a fake cannot honour is `tests/local-client-fake/README.md`'s to say.
- `tests/embedded.rs` — the embedded host (Stage 17, plan §20 step 1): two `EmbeddedHost`s started from provisioned profiles under app data directories whose parent every walk to `/` refuses, connected over real sockets on the host's private address, the checks driven on the host's own executor. Beside them, gate (d)'s row: a private directory under the platform's `files/` is refused by the host's runtime root, where the walk alone accepts it.

Items 9 and 10 (A 2026-10-03, #175) are generic too: `ready()` resolves on what waits and takes nothing, beside the direct message that is its positive control, and a session is owed one `ServerState` at open and no second without a change. Several changes coalescing into one pending state needs a binding to drive a change, so each binding shows it with its own means: the fake through `set_health` in `tests/fake.rs`, the in-process registry in its unit tests, `ipc-client` against a scripted server. The in-process runner also checks that its `ready()` is woken -- by a delivery, a revocation and the stop -- well inside its one-second recheck, so a test cannot pass on the recheck alone. Item 10's route begin (A 2026-10-09) is generic as well -- `a_route_begin_is_owed_the_peers_path`, run by all four runners. The decline below IPC 2.4 is not: each binding shows it by its own means -- the fake's and the in-process runner's own tests, the IPC server's unit test and the IPC client's. Its reconnect clause (`reconnected`) needs the pair's connection dropped and restored, which only the fake can drive on demand (`FakeNode::disconnected`, `FakeNode::connected`): it is shown there and in the composition's unit tests, and live between daemons over a real circuit by `tests/desktop-e2e/tests/relayed_path.rs`, whose relayed peer's daemon restarts.

Item 7's structural half is the traits themselves: a data session has no method yielding administrative authority. Its runtime half -- the admin port's own capabilities, the notice a revocation owes the holder, and the endpoint overlay's runtime rules (disabling revokes and never rebinds; a default must be able to receive; that the overlay survives a restart is the composition's own test, `crates/transport/composition/tests/endpoint_overlay.rs`) -- is generic over `AdminBinding` since Stage 13 (plan §16 (2)), so every binding runs it. What only one binding can show stays beside it: the in-process runner checks that an ended or cancelled session leaves nothing held, through the runtime's own diagnostics.

Item 13, bootstrap-address administration (ADR-0062, IPC 2.7), is generic and run by all four runners as `bootstrap_addresses_answer_alike_at_every_binding`: the capability refusals, an out-of-bound address included, each refusal by name as an answer (`own_peer` among them), added / unchanged / removed with what the next list and the next trust read show, and the authored entry each runner's profile carries refused `authored` (A's static entry for B; the fake's through `FakeNode::author_bootstrap`). What no runner can show is named on the function: a port that predates the capability (ipc-client's scripted daemon pins it below 2.7) and the special-use classes past loopback (the composition's and the daemon's tests). Item 14, the show side, `admin.peers.own_addresses` (ADR-0062 decision 4, IPC 2.8), runs beside it as `own_addresses_are_what_an_add_takes`, the item's cross-check: refused without `admin.peers`, the node's own `PeerId` on every row, and its first row added on the other node. Its control, a loopback-only node answering no listen row, is the composition's `a_loopback_only_node_shows_no_listen_row`, as the item places it: each runner's subject here is one node of a pair connected over a private interface, and the fake answers a fixed private listener. What it cannot show on a host without a public address -- a confirmed external row, a circuit row, the relay-only rule -- is the selector's unit tests in `transport-libp2p`. The all-or-none add, `admin.peers.add_addresses` (ADR-0062 decision 4, IPC 2.9), runs beside them as `a_list_is_added_all_or_none_at_every_binding`: refused without `admin.peers` whatever the list holds, a list of none or of 17 `InvalidArgument`, a list with a grammar, an own-`PeerId` (`own_peer`) or a special-use line refused naming that line -- every line's grammar first, then `own_peer`, then the special-use floor -- with none of its lines written, and a good list taken whole, a row per line, present and repeated lines `unchanged`. LOCAL-CLIENT.md §7 item 13 carries it; the bound and an `enabled: false` provider are the composition's tests.
